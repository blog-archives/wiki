## Q1

agents 之间是怎么交互的

### Answer

Agents(主 agent 与 subagent)之间的交互主要通过两种机制:**spawn(生成子 agent)** 和 **消息传递(SendMessage/turn.complete)**。

---

### 1. 生成子代理:`agent.spawn`

主 agent 循环通过 `Task`/`Agent` 工具调用生成 subagent,插件也可以通过 `$.agent.spawn` 编程式地生成后台 subagent [mods/types/claude-code.d.ts:2655-2667]。`AgentSpawnInput` 定义了 spawn 时传递的关键字段,包括 `parentAgentId`(标识调用发生在哪个循环)、`parentModel`/`permissionMode`(父级继承给子级的状态)、`fork`(是否为父级上下文的分支)等 [mods/types/claude-code.d.ts:268-310]。

Spawn 调用最终会 resolve 为 `AgentSpawnResult`,包含子 agent 的 `agentId` 和其运行的 `model`,或者 `{ deny }` 拒绝生成 [mods/types/claude-code.d.ts:323-345]。

每个 agent 实例都被记录为一个 `AgentInfo` 结构,其中 `parentId` 标记谁生成了它,`spawnedBy` 标记是哪个插件触发的生成(区分"origin axis"),`name` 是 SendMessage 寻址用的标识符 [mods/types/claude-code.d.ts:117-154]。

### 2. Fork:上下文继承

`fork: true` 的 spawn 会继承父级的上下文和模型 [mods/types/claude-code.d.ts:296-299]。在 `agents-md` 插件中可以看到具体的实现示例:`agent.spawn` 的 `fork` hook 会把父 loop 已经"给过"的 nested 文件集合复制给 fork 出来的子 loop,避免重复附加 [mods/agents-md/hooks/register.ts:168-177]。

### 3. 结果回传:`turn.complete`

子 agent 的应答通过它自己的 `turn.complete` 事件传回,插件可以通过匹配 `agentId` 来等待并接收该结果 [mods/types/claude-code.d.ts:312-322]。文档中给出的示例展示了插件如何用一个 `got[agentId]` 映射来接收此异步结果 [mods/types/claude-code.d.ts:2686-2696]。

### 4. 跨会话/跨 agent 消息:SendMessage

除了 spawn-child 关系外,`CHANGELOG.md` 中记录了 `SendMessage` 工具,使 Claude Code 的多个 session/agent(包括跨机器的 Remote Control session)之间可以互相寻址发消息,`ListAgents` 用于发现对方 [CHANGELOG.md:1783-1784] [CHANGELOG.md:1794-1796]。这是与父子 spawn 关系平行的一种"同级/team"通信机制,例如 agent teams 中 teammate 向 leader 汇报状态 [CHANGELOG.md:2125]。

### 5. 实际编排示例:code-review 插件

`plugins/code-review` 展示了主 agent 如何编排多个并行子 agent 协作完成任务——先后 launch 多个 haiku/sonnet/opus subagent 做不同职责的检查,再对结果进行汇总过滤 [plugins/code-review/commands/code-review.md:14-55]。这是"多 agent 并行 + 结果聚合"这一交互模式的具体应用,并非底层机制本身,但很好地说明了 agent 间协作的实际用法。

## Q2

主 agent 创建 subagent 之后，当有问题需要用户决策时，谁负责和用户交互

### Answer

由**主 agent 所在的会话/UI** 负责与用户交互,不是 subagent 自己弹窗。CHANGELOG 中明确记录了这一行为:后台 subagent 遇到权限询问时会在主 session 中弹出提示,并标明是哪个 agent 在问,Esc 只拒绝该工具调用而不影响主循环 [CHANGELOG.md:2664]。

---

### 权限询问(Permission Prompt)路由到主 session

- `Changed background subagents to surface permission prompts in the main session instead of auto-denying; the dialog shows which agent is asking, and Esc denies just that tool` [CHANGELOG.md:2664]。这说明:
  - subagent 本身不直接和用户交互,它没有自己独立的用户输入通道;
  - 当 subagent 的工具调用需要权限决策(`ask`)时,该决策请求被"冒泡"到主 agent 的会话界面;
  - 弹窗会标注是哪个 subagent 在请求,用户可以针对该请求单独拒绝(Esc),而不会打断主 agent 或其他 subagent 的运行。

这与你之前了解的 `ClassicResult.permissionDecision`/`PermissionRequestDecision` 等权限相关字段一致——权限判定结果最终经由 hook 链路作用于对应的 tool call 上 [mods/types/claude-code.d.ts:1024-1027]。

### 通知机制:agent 面板中的"needs input"

除了权限弹窗,后台 agent 还会通过 `Notification` hook 上报 `agent_needs_input` 事件,提示用户去查看/回应该 subagent(`claude agents` 面板会显示状态) [CHANGELOG.md:2481]。这表明 subagent 需要用户决策时的另一种路径是异步通知,由用户主动切换到对应 agent 的视图去回复,而不是同步阻塞弹窗。

### AskUserQuestion 工具

如果是 subagent 想向用户提出选择题(而非权限询问),CHANGELOG 中提到 `AskUserQuestion` 对话框机制,这类问题同样通过 UI 层弹出对话框呈现给用户,并可配置 idle 超时 [CHANGELOG.md:2432]。

### 小结

| 场景 | 谁负责与用户交互 | 依据 |
|---|---|---|
| subagent 触发权限询问(ask/allow/deny) | 主 session 的 UI 弹窗,标明来源 agent | `CHANGELOG.md:2664` |
| subagent 需要用户关注但非阻塞 | 后台通知 + `claude agents` 面板 | `CHANGELOG.md:2481` |
| Agent 主动提问(结构化选择) | `AskUserQuestion` 对话框 | `CHANGELOG.md:2432` |

## Q3

主 agent 创建 subagent 之后，当有问题需要用户决策时，谁负责和用户交互

### Subagent 需要用户决策时，交互如何路由到主 Agent

本图追踪 Claude Code 中 subagent 触发权限询问/需要用户输入时，请求如何汇聚到主 agent 所在会话 UI 而不是由 subagent 自己弹窗。关键路径见 [1c] 权限提示冒泡到主 session，[2b] agent 归属追踪，[3a] 非阻塞通知面板，[4a] 结构化提问工具。

#### 1. 工具调用触发权限询问，冒泡到主 session

引擎级 tool.call → tool.check → PermissionRequest 流水线，subagent 与主 agent 共用同一套权限决策链路，最终由主 session UI 弹出询问

##### 1a. tool.call 事件触发 (`claude-code.d.ts:3222`)

引擎准备执行工具时触发,next(e) 会依次跑完 hooks、权限提示、工具本身

```text
'tool.call': ToolCallInput;
```

##### 1b. tool.check 决定是否可执行 (`claude-code.d.ts:3234`)

在 mode 判定 ask 之前跑完 tool.call 与 PreToolUse hooks,决定 allow/deny/ask

```text
'tool.check': ToolCheckInput;
```

##### 1c. PreToolUseDecision.ask (`claude-code.d.ts:6404`)

决策为 ask 时,文本作为理由呈现给用户——这一决定不区分调用方是主 agent 还是 subagent

```text
ask: string;
```

##### 1d. PermissionRequest hook 触发 (`claude-code.d.ts:6037`)

权限请求最终作为一个 classic hook 事件发出,携带 tool_name/tool_input,交由 hook 链路给出 PermissionRequestDecision

```text
hook_event_name: 'PermissionRequest';
```

##### 1e. PermissionBehavior 三态 (`claude-code.d.ts:6006`)

无论请求来自哪个 agent,最终都归约为这三种行为之一,ask 会走到 UI 弹窗

```text
behavior: 'allow' | 'deny' | 'ask';
```

##### 1f. 变更记录:后台 subagent 权限提示上浮 (`CHANGELOG.md:2664`)

明确记录了行为:subagent 的权限询问不再自动拒绝,而是显示在主 session 中,标明来源 agent,Esc 只拒绝该次调用

```text
Changed background subagents to surface permission prompts in the main session instead of auto-denying
```

#### 2. spawn 时记录 agent 归属，供权限提示标注来源

AgentSpawnInput/AgentInfo 的 parentAgentId/parentId/name 字段,是弹窗能标注'哪个 agent 在问'的数据基础,属于 spawn/agent 生命周期管理的一部分

##### 2a. AgentSpawnInput 定义关键字段 (`claude-code.d.ts:268`)

spawn 子 agent 时传入的字段,parentAgentId 标识发起调用的循环,permissionMode 从父级继承给子级

```text
parentAgentId, parentModel, permissionMode, fork
```

##### 2b. AgentInfo 结构记录归属 (`claude-code.d.ts:117`)

每个 agent 实例的 parentId/spawnedBy/name 使权限弹窗、通知面板可以标注具体来源 agent

```text
parentId 标记谁生成了它, spawnedBy 标记触发插件, name 用于 SendMessage 寻址
```

##### 2c. AgentSpawnResult resolve (`claude-code.d.ts:323`)

spawn 调用最终 resolve 出的 agentId,是后续权限询问/通知定位来源 agent 的关键标识

```text
agentId 和其运行的 model,或 { deny } 拒绝生成
```

#### 3. subagent 需要关注但非阻塞：Notification 通知面板

与同步权限弹窗并行的另一条路径,subagent 通过通知让用户主动切换视图去回应,而不是阻塞主循环

##### 3a. agent_needs_input 通知 (`CHANGELOG.md:2481`)

后台 agent 上报需要输入的状态,用户通过 claude agents 面板发现并回应,而非同步阻塞弹窗

```text
agent_needs_input event surfaced via Notification hook, claude agents panel shows status
```

#### 4. Agent 主动结构化提问：AskUserQuestion

当 subagent(或主 agent)想向用户提出选择题而非权限询问时的独立机制,同样呈现在 UI 层

##### 4a. AskUserQuestion 对话框 (`CHANGELOG.md:2432`)

结构化选择题通过该工具弹出对话框呈现给用户,由 UI 层统一处理,不由 subagent 自建交互通道

```text
AskUserQuestion dialog mechanism with configurable idle timeout
```

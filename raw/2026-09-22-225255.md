## 一次工具发现与调用经过哪些环节

在 codex-rs 中，一次完整的工具发现（discovery）与调用（dispatch）流程主要经过以下环节：

---

### 1. 构建阶段：Tool Planning / Registry / Router

每个 turn 开始前，`built_tools()` 会调用 `build_tool_router()`,汇总 MCP、动态工具、扩展工具等来源，生成 `ToolRegistry` 和 `ToolRouter` codex:1814-1823 。

`finalize_tool_router()` 负责在注册表基础上做最终整理：过滤 `hosted_specs`、应用命名空间覆盖、判断是否启用 Code Mode / Tool Search 等 codex:348-368 。

动态工具（`DynamicToolSpec`）与扩展工具（`ExtensionToolAdapter`）分别通过 `append_dynamic_tool_runtimes` 和 `append_extension_tool_executors` 注册进 `ToolRegistry` codex:1370-1401 codex:1422-1450 。

### 2. 工具发现（Deferred Discovery / tool_search）

若启用 `search_tool_enabled`，`append_tool_search_executor` 会注册 `tool_search` 工具，供模型在运行时主动检索被“延迟”注册（deferred）的工具 codex:369-404 。

`ToolSearchHandler::handle_call` 实现了具体的检索逻辑：解析 query/limit 参数，通过 BM25 搜索引擎查找匹配的 `search_infos`,返回 `ToolSearchOutput`（可加载的工具规格列表） codex:190-227 。

搜索工具的 spec 描述（供模型理解用途）由 `create_tool_search_tool` 生成 codex:16-105 。测试用例 `tool_search_returns_deferred_dynamic_tool_and_routes_follow_up_call` 展示了模型先调用 `tool_search` 找到工具、再调用该工具的完整流程 codex:1066-1112 。

### 3. 模型发起调用：ToolCall 构建与路由

模型返回 `function_call` 后，`ToolRouter::build_tool_call()` 将其转换为内部 `ToolCall` 结构（`tool_name` / `call_id` / `payload`），随后经 `dispatch_tool_call_with_code_mode_result_inner` 组装成 `ToolInvocation`，最终交给 `ToolRegistry::dispatch_any_with_state` codex:345-380 。

### 4. 实际调度与执行（Dispatch）

`dispatch_any_with_state` 是核心调度函数，依次完成：

1. 查找对应 `CoreToolRuntime`（`self.tool(&tool_name)`），若找不到返回 "unsupported call" 错误 codex:536-558 
2. 校验 payload 类型是否与工具匹配（`matches_kind`） codex:570-586 
3. 执行 `run_pre_tool_use_hooks`，可被 hook 阻断（`Blocked`）或修改参数 codex:588-639 
4. 通知工具开始（`notify_tool_start`），若不是 MCP 工具 codex:642-647 
5. 通过 `handle_any_tool` 真正调用 `tool.handle(invocation)`，得到 `AnyToolResult` codex:789-821 
6. 执行完成后运行 `run_post_tool_use_hooks`，记录 analytics、遥测（otel tags）等 codex:683-719 

### 5. Code Mode 中的嵌套调用

若使用 Code Mode（沙箱脚本中调用工具），`delegate.rs` 中的调度循环通过 `DispatchMessage::InvokeTool` 处理嵌套调用请求，等待 cell 就绪后 `tokio::spawn` 异步执行 codex:165-221 。

### 6. 调用轨迹记录（Trace）

每次调度均可被 `rollout-trace` 系统记录：`record_started` 写入 `ToolCallStarted` 事件，包含 requester（模型 vs code cell）、工具类型（`dispatched_tool_kind`）等元数据 codex:200-277 。

---

## Notes

- 整体流程可概括为：`build_tool_router()`（构建注册表+路由）→（可选）`tool_search` 发现 deferred 工具 → 模型发出 `function_call` → `ToolRouter::build_tool_call` → `dispatch_any_with_state`(pre-hook → handle → post-hook) → trace 记录。
- `codex-rs/tui/src/app/app_server_events.rs` 中的 `DynamicToolCall` 处理是 TUI 层针对动态工具（如 fork_thread 等)的请求转发逻辑,与 core 侧的 `ToolRegistry`/`ToolRouter` 调度机制是不同层面（客户端 vs 引擎侧),关联性有限，仅供参考。

    for spec in dynamic_tools {
        match spec {
            DynamicToolSpec::Function(tool) => {
                let Some(handler) = DynamicToolHandler::new(tool) else {
                    tracing::error!(
                        "Failed to convert dynamic tool {:?} to OpenAI tool",
                        tool.name
                    );
                    continue;
                };
                registry.register_external(Arc::new(handler));
            }
            DynamicToolSpec::Namespace(namespace) => {
                for tool in &namespace.tools {
                    let DynamicToolNamespaceTool::Function(tool) = tool;
                    let Some(handler) = DynamicToolHandler::new_in_namespace(namespace, tool)
                    else {
                        tracing::error!(
                            "Failed to convert dynamic tool {:?}.{:?} to OpenAI tool",
                            namespace.name,
                            tool.name
                        );
                        continue;
                    };
                    registry.register_external(Arc::new(handler));
                }
            }
        }
    }

impl ToolSearchHandler {
    async fn handle_call(
        &self,
        invocation: ToolInvocation,
    ) -> Result<Box<dyn crate::tools::context::ToolOutput>, FunctionCallError> {
        let ToolInvocation { payload, .. } = invocation;

        let args = match payload {
            ToolPayload::ToolSearch { arguments } => arguments,
            _ => {
                return Err(FunctionCallError::Fatal(format!(
                    "{TOOL_SEARCH_TOOL_NAME} handler received unsupported payload"
                )));
            }
        };

        let query = args.query.trim();
        if query.is_empty() {
            return Err(FunctionCallError::RespondToModel(
                "query must not be empty".to_string(),
            ));
        }
        let limit = args.limit.unwrap_or(TOOL_SEARCH_DEFAULT_LIMIT);

        if limit == 0 {
            return Err(FunctionCallError::RespondToModel(
                "limit must be greater than zero".to_string(),
            ));
        }

        if self.search_infos.is_empty() {
            return Ok(boxed_tool_output(ToolSearchOutput { tools: Vec::new() }));
        }

        let tools = self.search(query, limit)?;

        Ok(boxed_tool_output(ToolSearchOutput { tools }))
    }

pub(crate) fn create_tool_search_tool(
    searchable_sources: &[ToolSearchSourceInfo],
    default_limit: usize,
    source_listing: ToolSearchSourceListing,
) -> ToolSpec {
    let properties = BTreeMap::from([
        (
            "query".to_string(),
            JsonSchema::string(Some("Search query for deferred tools.".to_string())),
        ),
        (
            "limit".to_string(),
            JsonSchema::number(Some(format!(
                "Maximum number of tools to return. Defaults to {default_limit}."
            ))),
        ),
    ]);

    let source_section = match source_listing {
        ToolSearchSourceListing::Include => {
            let mut source_descriptions = BTreeMap::new();
            for source in searchable_sources {
                source_descriptions
                    .entry(source.name.clone())
                    .and_modify(|existing: &mut Option<String>| {
                        if existing.is_none() {
                            *existing = source.description.clone();
                        }
                    })
                    .or_insert(source.description.clone());
            }

            let source_descriptions = if source_descriptions.is_empty() {
                "None currently enabled.".to_string()
            } else {
                let reserved_name_bytes = source_descriptions.keys().fold(
                    source_descriptions.len().saturating_sub(1),
                    |reserved, name| reserved.saturating_add(2).saturating_add(name.len()),
                );
                let mut description_budget =
                    MAX_TOOL_SEARCH_SOURCE_DESCRIPTION_BYTES.saturating_sub(reserved_name_bytes);
                let mut rendered = String::new();
                for (name, description) in source_descriptions {
                    let separator_bytes = usize::from(!rendered.is_empty());
                    let required = separator_bytes.saturating_add(2).saturating_add(name.len());
                    if required
                        > MAX_TOOL_SEARCH_SOURCE_DESCRIPTION_BYTES.saturating_sub(rendered.len())
                    {
                        continue;
                    }

                    if !rendered.is_empty() {
                        rendered.push('\n');
                    }
                    rendered.push_str("- ");
                    rendered.push_str(&name);

                    if let Some(description) = description
                        && description_budget >= 2
                    {
                        rendered.push_str(": ");
                        description_budget -= 2;
                        let bounded_description =
                            take_bytes_at_char_boundary(&description, description_budget);
                        rendered.push_str(bounded_description);
                        description_budget -= bounded_description.len();
                    }
                }
                rendered
            };
            format!(
                "\n\nYou have access to tools from the following sources:\n{source_descriptions}\n"
            )
        }
        ToolSearchSourceListing::Omit => "\n\n".to_string(),
    };

    let description = format!(
        "# Tool discovery\n\nSearches over deferred tool metadata with BM25 and exposes matching tools for the next model call.{source_section}Some of the tools may not have been provided to you upfront, and you should use this tool (`{TOOL_SEARCH_TOOL_NAME}`) to search for the required tools. For MCP tool discovery, always use `{TOOL_SEARCH_TOOL_NAME}` instead of `list_mcp_resources` or `list_mcp_resource_templates`."
    );

    ToolSpec::ToolSearch {
        execution: "client".to_string(),
        description,
        parameters: JsonSchema::object(
            properties,
            Some(vec!["query".to_string()]),
            Some(false.into()),
        ),
    }

async fn handle_any_tool(
    tool: &dyn CoreToolRuntime,
    invocation: ToolInvocation,
    call_state: Option<&ToolCallState>,
) -> Result<AnyToolResult, FunctionCallError> {
    let call_id = invocation.call_id.clone();
    let payload = invocation.payload.clone();
    let output = tool.handle(invocation.clone()).await?;
    let post_tool_use_payload =
        CoreToolRuntime::post_tool_use_payload(tool, &invocation, output.as_ref());
    let result = AnyToolResult {
        call_id,
        payload,
        result: output,
        post_tool_use_payload,

        && invocation.turn.config.memories.disable_on_external_context

            invocation.session.services.state_db.as_deref(),
            invocation.session.thread_id,
            "tool_output",
        )

## Q2
tool search 具体是一个怎么样的过程或调用，模型传入的参数是什么，他是依据什么会作出需要查询工具的判断；BM25 搜索引擎是什么，工具的匹配方式是什么
### Answer
## 简要回答

`tool_search` 是一个模型可直接调用的特殊工具（`ToolSpec::ToolSearch`），模型传入 `query`（必填）和 `limit`（可选，默认8）两个参数 codex:16-32 。模型是否调用它，取决于系统提示中该工具自身的 `description` 文字提示，明确告知模型"有些工具没有预先提供，需要用 `tool_search` 去搜索" codex:93-95 ——这是纯 prompt 驱动的判断，代码层面没有额外逻辑强制模型调用它。工具匹配使用的是 BM25（Best Matching 25）算法，一种经典的信息检索排序算法，基于词频/文档长度对搜索文本和查询进行相关性打分,由 Rust 的 `bm25` crate 实现 codex:11-14 。

---

## 详细过程

### 1. 参数与 Spec

`create_tool_search_tool` 构造 `ToolSpec::ToolSearch`，定义了 `query`（字符串,必填）和 `limit`（数字,可选,默认值取自 `TOOL_SEARCH_DEFAULT_LIMIT`）两个参数，并生成描述文本 codex:16-32 。这个描述会告诉模型该工具用 BM25 检索被延迟(deferred)的工具元数据，并列出当前可用的工具"来源"（如已连接的 MCP 服务器/Apps) codex:93-95 。测试用例验证了实际发给模型的 JSON schema 与这个 spec 一致 codex:183-199 。

### 2. 模型决定调用的依据

代码层面并不存在"判断是否需要工具"的显式逻辑——是否调用 `tool_search` 完全由模型根据 spec 描述文本自主决定,该描述明确说明:"某些工具可能没有预先提供给你,你应该用 `tool_search` 查找所需工具" codex:93-95 。系统只负责把哪些工具"隐藏"（deferred），从而制造出模型需要搜索才能获得的场景:`finalize_tool_router` 中，若存在 deferred 工具，会移除潜在冲突的直接工具并注册 `tool_search` 执行器 codex:369-404 。

### 3. 请求解析：ToolSearchCall

模型返回 `ResponseItem::ToolSearchCall`（`execution == "client"`）时，`ToolRouter::build_tool_call` 将其解析成 `ToolCall`，参数被反序列化为 `SearchToolCallParams`（即 `query`/`limit`），`tool_name` 固定为 `tool_search` codex:262-280 。

### 4. 调用与检索逻辑：BM25

`ToolSearchHandler::handle_call` 校验 `query` 非空、`limit` 大于0后，调用 `self.search(query, limit)` codex:206-226 。

`search_engine.search(query, limit)` 是核心检索，使用 `bm25` crate 的 `SearchEngine<usize>`（文档 id 为索引） codex:233-246 。搜索引擎在 `ToolSearchHandler::new` 构建时初始化：把每个 `search_infos` 中工具的 `search_text` 作为一篇文档，用 `SearchEngineBuilder::<usize>::with_documents(Language::English, documents).build()` 建立索引 codex:151-158 。

BM25（Best Matching 25）是一种传统的基于词频-逆文档频率（TF-IDF变体）的全文检索排序算法，`bm25` crate 提供了标准实现，对每个候选文档与查询词的匹配程度打分并排序，返回 top-N 结果。这里 `Document::new(idx, search_text)` 把索引 `idx` 与工具的检索文本关联，检索结果通过 `result.document.id` 找回对应的 `search_infos` 条目 codex:151-156 。

### 5. 索引内容：search_text 是什么

每个工具的 `search_text` 由 `default_tool_search_text` 生成，会把工具名（含下划线转空格版本）、描述、参数 schema 中的属性名/描述等拼接成一段文本，供 BM25 索引 codex:111-153 。因此匹配方式本质是"关键词/语义片段"的全文检索，而不是向量语义搜索。

### 6. 匹配结果的合并与返回

检索到的候选 `ToolSearchEntry` 通过 `search_output_tools` 转成 `LoadableToolSpec`，并用 `coalesce_loadable_tool_specs` 把同一命名空间(如 MCP server)下的多个工具合并成一个 `Namespace` 结构返回 codex:248-255 。测试 `mixed_search_results_coalesce_mcp_namespaces` 展示了这种合并行为——两个来自 `mcp__calendar` 的工具被合并进同一个 namespace codex:357-461 。

### 7. 数据来源：谁参与检索

`ToolSearchHandlerCache::get_or_build` 遍历 `ToolRegistry` 中标记为 `Deferred`（延迟暴露）的工具，收集其 `search_info()`（动态工具）或 `immutable_spec()`（不变的内建/MCP工具）作为检索源，并做缓存复用（相同来源时复用同一 handler，避免重复建索引） codex:52-105 。

### 8. 端到端测试验证

`tool_search_returns_deferred_dynamic_tool_and_routes_follow_up_call` 完整演示了流程：模型先发出 `tool_search` 调用（带 `query`/`limit`），系统返回匹配的 `codex_app` 命名空间工具，模型随后据此发出真正的 `function_call` codex:1066-1112 。

## Notes

- BM25 匹配是纯文本/词频检索，不依赖向量嵌入或语义相似度模型；因此搜索质量取决于 `search_text` 构造是否充分覆盖工具名、描述、参数字段等关键词 codex:111-153 。
- "是否需要搜索"完全依赖模型对 prompt 描述的理解与判断，代码不做强制路由；唯一的代码侧控制是决定哪些工具被标记为 `Deferred`（从而对模型不可见,必须搜索才能发现）。
- Apps/Connectors 场景下还有专门的 `search_tool/tool_description.md` 模板，用于渲染面向 Apps 的 tool_search 描述文案 codex:1-7 ，这与主流程中 `create_tool_search_tool` 生成的描述是互补的（可能用于不同场景的模板渲染，具体拼接逻辑未在本次上下文中出现，需进一步查看代码确认关联方式）。

                    ResponsesApiNamespaceTool::Custom(tool) => {
                        push_search_part(&mut parts, tool.name.clone());
                        push_search_part(&mut parts, tool.description.clone());
                        push_search_part(&mut parts, tool.format.syntax.clone());
                    }
                }
            }
        }
        ToolSpec::ToolSearch { description, .. } => {
            push_search_part(&mut parts, description.clone());
        }
        ToolSpec::WebSearch { .. } => {
            push_search_part(&mut parts, "web search".to_string());
        }
        ToolSpec::Freeform(tool) => {
            push_search_part(&mut parts, tool.name.clone());
            push_search_part(&mut parts, tool.description.clone());
            push_search_part(&mut parts, tool.format.syntax.clone());
        }
    }

    parts.join(" ")
}

fn append_function_search_text(tool: &ResponsesApiTool, parts: &mut Vec<String>) {
    push_search_part(parts, tool.name.clone());
    push_search_part(parts, tool.name.replace('_', " "));
    push_search_part(parts, tool.description.clone());
    append_schema_search_text(&tool.parameters, parts);
}

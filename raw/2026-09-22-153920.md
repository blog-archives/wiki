# DeepWiki Q&A with Code Context for Repository: openai/codex
## Q1
请查找任务目标、有效约束、计划、已完成步骤、待办事项、阻塞原因和产出位置的存储结构。哪些是独立的结构化字段，哪些只能从聊天历史中推断？这些状态由谁更新，在什么事件后更新，又如何进入下一轮模型请求？
### Answer
## 直接回答

在这份代码库中，能看到**两个独立的机制**在处理你提到的这些状态，它们的“结构化程度”完全不同：

| 概念 | 是否有独立结构化字段 | 存储位置 | 更新者 / 触发事件 | 如何进入下一轮模型请求 |
|---|---|---|---|---|
| **目标 (Objective)** | ✅ 是，`objective` 列 | `thread_goals` 表 (GOALS_DB) | `GoalStore::insert_thread_goal` / `update_thread_goal`，由 `create_goal`/`update_goal` 工具调用触发 | 通过 steering item 注入 |
| **约束/预算 (Budget)** | ✅ 是，`token_budget`, `tokens_used`, `time_used_seconds` 列 | 同上 | 每轮 turn 结束时累加 token 使用量 | 当超限时状态转 `BudgetLimited`，注入 `budget_limit_steering_item` |
| **状态/阻塞原因 (Status/Blocked)** | ✅ 是，`status` 列（如 `active`/`paused`/`blocked`/`complete`/`budget_limited`） | 同上 | `update_thread_goal` 的 SQL CASE 逻辑自动转换，或显式调用 `update_goal` | 状态变化触发对应 steering item（如 `continuation_steering_item`, `objective_updated_steering_item`） |
| **计划 (Plan)、已完成步骤、待办事项 (Todo)** | ❌ 没有独立的持久化结构化表；只是模型工具调用参数 (`PlanItemArg{step, status}`, `TodoItem{text, completed}`) | 无独立数据库，仅通过 `turn/plan/updated` 通知在当轮内传递并在 UI 渲染 | 模型自己调用 `update_plan` 工具，由 harness 系统提示词要求维护 | 不会被系统结构化"回注"到下一轮请求；只能从**聊天/工具调用历史**中被模型自己记住或重新读取 |
| **产出位置 (Output location)** | ⚠️ 未在当前索引到的代码片段中找到独立字段 | 不确定 | 不确定 | 不确定 |

## 详细说明

### 1. 目标 / 约束 / 状态 —— 有真正的结构化存储（`ext/goal` + `codex-state`）

Goal 的持久化字段在 `thread_goals` 表中通过 `insert_thread_goal` 明确定义：`objective`、`status`、`token_budget`、`tokens_used`、`time_used_seconds`、`created_at_ms`、`updated_at_ms` 都是独立列，不是从聊天记录里推断出来的： codex:213-256 

更新逻辑在 `update_thread_goal` 中，根据传入的 `GoalUpdate{objective, status, token_budget, expected_goal_id}` 构造不同的 SQL 更新语句，其中还包含**自动阻塞/预算超限判定**（例如当 `tokens_used >= token_budget` 时自动把状态置为 `BudgetLimited`）： codex:271-351 

这个更新由 `ext/goal` 的运行时（`GoalRuntimeHandle`）在 turn 生命周期事件后调用，比如状态被 turn 结束事件触发变更后： codex:338-367 

调用之后，代码会把最新的 goal 转换成 protocol 层结构并通过 `event_emitter.thread_goal_updated` 广播出去 codex:365-367 ；根据 wiki 背景，若目标处于活跃状态，运行时还会向模型上下文注入 `continuation_steering_item` 或 `objective_updated_steering_item`，预算超限时注入 `budget_limit_steering_item`，这就是这些状态"进入下一轮模型请求"的路径。

### 2. 计划 (Plan) / 待办事项 (Todo) —— 没有独立数据库结构，仅存在于工具调用参数和 turn 内通知中

与 Goal 不同，Plan/Todo 完全依赖模型自己主动调用 `update_plan` 工具来维护。App-server 协议里 `turn/plan/updated` 通知定义了 `plan` 条目的形状 `{step, status}`，状态只有 `pending`/`inProgress`/`completed`： codex:1876-1876 

TUI 侧接收到这个通知后调用 `chat.on_plan_update(update)` 直接渲染成历史 cell，测试用例展示了这个流程，但没有任何持久化写入数据库的调用： codex:1780-1811 

另外还有一套（可能用于 exec 模式或其它场景的）`TodoItem`/`TodoListItem` 结构，仅是简单的 `{text, completed}` 序列化载荷，同样没有配套的数据库表： codex:310-320 

而"必须维护计划"这个行为规范本身，是写在系统提示词里、要求模型自行调用 `update_plan` 工具、自行标记 `in_progress`/`completed`： codex:38-46 

这意味着：Plan/Todo 的"已完成步骤"、"待办事项"这些状态，**不是从某个独立表中读取的，而是模型自己在对话/工具调用历史中维护的心智状态**——系统只是把它渲染出来，并不会像 Goal 那样自动结构化地"回注"进下一轮 prompt。

### 3. 阻塞原因 (Blocked)

阻塞原因仅在 Goal 系统中有明确定义，是 `ThreadGoalStatus::Blocked` 这个枚举值，出现在 SQL CASE 判断中（当状态为 `Paused`/`Blocked` 且遇到某些 state 变化时保持不变）： codex:290-296 

Plan/Todo 系统里没有看到专门的"阻塞原因"字段。

### 4. 产出位置 (Output location)

在目前提供的代码片段中，我没有找到明确对应"产出位置"这一概念的独立字段或存储结构。由于索引大小限制，某些文件内容可能没有被完全收录；如果你需要确认这一项，建议开启一个 Devin session 来查看完整代码库，尤其是 `codex-rs/state` 和 `codex-rs/ext/goal` 目录下是否有相关字段。

## Q2
当任务中断、进程重启或上下文被压缩后，项目如何恢复目标与进度？请沿保存和恢复路径说明：恢复了哪些字段，如何知道工具是否已经执行、结果是否已保存，以及哪些动作可能被重复执行。是否有相关测试？
### Answer
# 直接回答

这个问题涉及两个独立机制：**Goal 状态恢复**（`ext/goal` 的 `restore_after_resume`）和**工具调用去重/恢复**（`core` 的 tool-call recovery metadata，如 `code_mode.rs` 测试所示）。目标恢复读取的是 `thread_goals` 表里的结构化字段，工具执行去重靠 rollout 中记录的 `executed_tool_calls`/`tool_calls_complete` 元数据来判断哪些调用已完成、避免重复执行。

---

## 1. Goal 恢复路径

线程恢复时（`on_thread_resume` 生命周期钩子）调用 `runtime.restore_after_resume()`： codex:160-173 

该函数从 `thread_goals` 表读取（通过 `GoalStore::get_thread_goal`）之前持久化的 `objective`、`status`、`token_budget`、`tokens_used`、`time_used_seconds`、`created_at_ms`、`updated_at_ms` 等字段： codex:41-66 

测试 `thread_resume_rehydrates_active_goal_idle_accounting` 验证了这条路径：先用 `replace_thread_goal` 落库一个 active goal，然后 `harness.resume_thread()` 触发恢复，检查恢复后的 `tokens_used`/`time_used_seconds`（包括空闲期间累加的 wall-clock 时间）与状态是否正确： codex:1318-1368 

此外 `replace_thread_goal_snapshot` 展示了完整快照式恢复/写入的实现（同时写 `thread_goals` 和 `thread_goal_continuation_deferrals` 表，保证事务一致性）： codex:68-123 

App-server 层也提供了显式的 `thread/goal/get`/`thread/goal/set` 接口，恢复后可查询当前 goal 而不改变它： codex:927-930 ，`thread_resume.rs` 测试也验证了跨恢复的 goal 状态一致性(`get_thread_goal` 校验 `goal_id`不变)： codex:3059-3076 。

**结论**：Goal 恢复是**完全结构化**的——所有字段直接从 SQLite 行读出，不依赖对话历史推断。

## 2. 工具调用是否已执行 / 结果是否已保存 —— 去重机制

在 `core` 侧（与 Goal 系统完全不同的另一套机制），恢复/压缩后是否重复执行工具调用，依赖于 rollout 元数据中的 `executed_tool_calls` 和 `tool_calls_complete` 字段。测试用例展示了会话中断恢复后的检查逻辑： codex:3696-3713 

从这段测试可以看出：
- `metadata["executed_tool_calls"]` 记录了哪些工具调用已经真正执行过（带参数），用来避免重复执行；
- `metadata["tool_calls_complete"]` 是布尔标记，表示该批工具调用是否全部完成；
- 对于**未在中断前完成**的调用（如 `call-wait-background`、`call-wait-active`），恢复后再次查询会返回 "not found"，说明它们没有被静默重放，而是需要模型显式重新处理；
- `call-recovery` 的结果 `"preserved"` 说明已完成的工具输出会被持久化保留，恢复后可直接复用，不会重新执行。

另一个恢复场景测试 `recover_turn_if_idle` 展示了运行时中断后如何在新进程上"恢复未完成的 turn"，而不是从头重跑： codex:176-197 

## 3. 上下文压缩（Compaction）后的恢复

Compaction（历史压缩）不是简单丢弃历史，而是把摘要写入 rollout 的 `RolloutItem::Compacted` 条目，恢复时重放该摘要。测试 `start_new_context_window_persists_checkpoint_state` 验证了压缩后 checkpoint（包含 `replacement_history`、`compaction_response_id`、`latest_token_usage_record`）被正确持久化并可从 rollout 读回： codex:3465-3540 

压缩后跨真实会话边界恢复的测试（`retained_answers_cross_real_session_boundaries`）进一步验证：压缩 checkpoint 中的 `retained_context.verified_answers()` 在恢复/重放后依然保持一致： codex:1120-1187 

`deferred_tool_world_state_survives_resume_without_duplicate_updates` 测试专门验证了"避免重复更新"——恢复后 tool 的 world-state 部分不会被重复注入到请求中（两次请求的 `tools_state` 完全一致）： codex:1023-1093 

## 4. 哪些动作可能被重复执行？

根据测试推断：
- **未标记为 `tool_calls_complete` 的调用**在恢复后找不到结果（返回 "not found"），意味着模型需要重新发起（而不是系统自动重放），本质上避免了自动重复执行，但也意味着该调用的副作用（如果已在后台真实执行了一部分）可能与新一轮请求产生的调用重叠——这是需要模型/系统协同注意的边界情况 codex:3705-3708 。
- 已完成、有 `executed_tool_calls` 记录的调用**不会重复执行**，其结果会被保留复用。
- Goal 的 `insert_thread_goal` 本身通过 `WHERE thread_goals.status = 'complete'` 条件防止重复插入覆盖未完成的目标，是一种显式的"防重复"保护： codex:245-245 。

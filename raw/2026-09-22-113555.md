## Q1
工具调用错误的分层处理
### Answer
# 工具调用错误的分层处理

在 `charmbracelet/crush` 中,工具调用错误的处理分为多个层次:输入清洗层、执行结果层、运行时异常清理层,以及外部 Hooks 层。

---

## 1. 输入清洗层(sanitizeToolInput)

在 `OnToolCall` 回调中,先对工具输入做校验/清洗。如果输入 JSON 不合法,会被标记 `sanitizedToolCalls[tc.ToolCallID] = true`，随后在 `OnToolResult` 中把结果强制替换为错误提示: crush:951-973 

这样即使模型给出了格式错误的参数,也会被统一转成一个明确的错误信息返回给模型继续对话,而不是让底层执行崩溃。

## 2. 正常执行结果层(OnToolResult)

正常工具执行完成后,结果通过 `a.convertToToolResult` 转换并作为 `message.Tool` 角色的消息持久化: crush:968-983 

## 3. 运行中断/异常清理层

当整个 `Run` 因为 provider 错误、超时或用户取消而中止时(`err != nil` 分支),代码会遍历尚未完成或未匹配到结果的工具调用,为它们补写一条错误的 `ToolResult`,避免对话历史中出现"悬空"的工具调用: crush:1100-1157 

其中区分了取消错误与其它错误,内容不同: crush:1138-1146 

## 4. 历史消息重放层(toolResultsForCalls)

在为下一轮请求准备历史消息时(`preparePrompt`),如果某个工具调用在历史里始终没有对应结果(如会话中途中断),会注入一个合成的错误结果,保证 LLM API 要求的"工具调用必须紧跟结果"的约束不被破坏: crush:1662-1687 

## 5. 外部 Hooks 层(PreToolUse)

这是独立于 Agent 主循环的一层,通过用户自定义脚本在工具执行前拦截、修改或阻止调用。退出码约定了不同的错误处理方式: crush:700-710 

多个 hook 命中同一事件时的聚合规则(如 `deny`/`allow`/`null` 优先级)进一步分层处理决策结果: crush:712-733 

---

## 小结

| 层次 | 位置 | 作用 |
|---|---|---|
| 输入清洗 | `OnToolCall`/`sanitizeToolInput` | 拦截非法 JSON 输入 |
| 正常结果 | `OnToolResult` | 持久化工具执行结果 |
| 异常清理 | `Run` 错误分支 | 为未完成调用补写错误结果 |
| 历史重放 | `toolResultsForCalls` | 保证工具调用-结果配对完整性 |
| Hooks | `docs/hooks/README.md` | 用户自定义前置拦截/阻断 |

## Notes
- 前四层均在 `internal/agent/agent.go` 的 `sessionAgent.Run` / `preparePrompt` 中实现,属于同一执行路径的不同阶段。
- Hooks 层(`docs/hooks/README.md`)是独立的外部脚本机制,配置定义在 `internal/config.HookConfig`,与 Agent 主循环通过 PreToolUse 事件耦合,但索引中未直接看到调用点代码,如需确认具体调用代码建议启动 Devin 会话查看完整实现。

func toolResultsForCalls(m message.Message, toolResultsByCall map[string][]fantasy.MessagePart) fantasy.Message {
	content := make([]fantasy.MessagePart, 0, len(m.ToolCalls()))
	for _, tc := range m.ToolCalls() {
		parts := toolResultsByCall[tc.ID]
		delete(toolResultsByCall, tc.ID)
		if len(parts) > 0 {
			content = append(content, parts...)
			continue
		}
		slog.Warn(
			"Injecting synthetic tool result for orphaned tool call",
			"tool_call_id", tc.ID,
			"tool_name", tc.Name,
		)
		content = append(content, fantasy.ToolResultPart{
			ToolCallID: tc.ID,
			Output: fantasy.ToolResultOutputContentError{
				Error: errors.New("tool call was interrupted and did not produce a result, you may retry this call if the result is still needed"),
			},
		})
	}
	return fantasy.Message{
		Role:    fantasy.MessageRoleTool,
		Content: content,
	}
}

## Q2
是否有关于不同错误重试策略，比如超时限流等内部执行有限次数多指数退避重试，调用参数错误等返回给模型重试，其他错误等中断退出等错误处理策略
### Answer
# 错误重试策略分层

在 `charmbracelet/crush` 中,确实存在你描述的三类错误处理路径,分别对应不同的错误类型。

---

## 概览

| 错误类型 | 处理策略 | 位置 |
|---|---|---|
| Provider 限流/超时/瞬时错误 | 内部有限次数重试(退避机制由 `fantasy` 库驱动） | `OnRetry` 回调 |
| 401 未授权 | 刷新凭证后重试（专门的重试路径，非退避） | `retryAfterUnauthorized` |
| 工具调用参数非法（JSON 解析失败） | 不重试请求本身，而是把错误结果回传给模型，让模型在对话中自行重试 | `sanitizeToolInput` + `OnToolResult` |
| 其他致命错误（如 Copilot 未启用、传输错误等） | 中断本轮对话，写入 `FinishReasonError` 并退出 | `Run` 的错误分支 |

---

## 1. Provider 限流/超时类 —— 内部有限次数重试

`sessionAgent.Run` 向 `fantasy` Agent 注册了 `OnRetry` 回调,每次 provider 请求失败重试时都会触发它,记录退避延迟并重置已流式传输的内容,避免重试结果和上次的部分内容拼接： crush:932-942 

这里的重试次数上限和指数退避的具体算法（比如 429/超时应重试多少次、delay 如何计算）是由 `fantasy.ProviderError` 驱动、并在 `fantasy` 库内部实现的，`crush` 只是被动接收回调进行日志记录和状态清理，`providerRetryLogFields` 的单测证明了它主要用于把 `StatusCode`（如 429）、`Title`、`Message` 结构化到日志字段中： crush:1324-1352 

由于 `fantasy` 是外部依赖库（`charm.land/fantasy`），具体的重试次数上限、退避算法在索引到的 `crush` 代码中不可见，如果你需要确认具体参数，建议直接查看 `fantasy` 库源码或启动 Devin 会话深入追踪。

## 2. 401 未授权 —— 独立的凭证刷新重试路径

这不是退避重试,而是一次性的"刷新凭证后重试"逻辑,通过 `makeAuthRefreshCallback` 注册为 fantasy 的 `OnAuthRefresh`： crush:1540-1552 

具体分支包括 OAuth token 刷新、AWS SSO 重新认证（会阻塞等待用户交互完成）、API Key 模板刷新： crush:1463-1495 

若 refresh token 已被吊销，会触发交互式重新认证并阻塞等待，而非立刻放弃： crush:1507-1532 

## 3. 工具调用参数非法 —— 返回给模型自行重试（非请求级重试）

当 `OnToolCall` 检测到工具输入不是合法 JSON 时，不会让底层执行崩溃、也不会重试整个 provider 请求，而是标记该调用，随后在 `OnToolResult` 阶段把结果强制替换成明确的错误提示，返回给模型，让模型在下一轮自主决定是否重新调用： crush:951-983 

## 4. 其他致命错误 —— 中断退出

`Run` 的错误分支根据错误类型分类处理，包括请求超时、Hyper 401、Copilot 模型未启用、通用 `ProviderError`/`fantasy.Error`/传输错误，最终都调用 `currentAssistant.AddFinish(message.FinishReasonError, ...)` 结束本轮而不再重试： crush:1157-1191 

紧接着，为了保证消息历史一致性，未完成的工具调用会被补写错误结果（前一轮回答中提到的"运行中断/异常清理层"）： crush:1100-1157 

---

## Notes
- `fantasy` 库（`charm.land/fantasy`）负责实际的 provider 级重试判定与延迟计算，`crush` 仅通过 `OnRetry` 回调感知重试事件，具体退避算法/最大重试次数在当前索引范围内不可见。
- 401 重试与限流/超时重试是两条独立路径：前者走 `OnAuthRefresh` → `retryAfterUnauthorized`，后者走 `OnRetry`。
- 如果你想确认 `fantasy` 库内部具体的重试次数上限或退避公式，建议启动 Devin 会话，因为这可能涉及 vendor 目录或 go.sum 引用的外部依赖源码，当前索引未完全覆盖。

// retryAfterUnauthorized attempts to refresh credentials after an auth error
// and returns nil if the request should be retried. For OAuth providers whose
// refresh token is revoked, and for Bedrock providers whose AWS SSO session
// has expired, it triggers interactive re-authentication and blocks until the
// user completes it (or the context is cancelled).
func (c *coordinator) retryAfterUnauthorized(ctx context.Context, providerCfg config.ProviderConfig) error {
	switch {
	case providerCfg.OAuthToken != nil:
		slog.Debug("Received 401. Refreshing token and retrying", "provider", providerCfg.ID)
		if err := c.refreshOAuth2Token(ctx, providerCfg); err != nil {
			// If the refresh token was revoked, trigger interactive
			// re-auth and wait for the user to complete it.
			var exchangeErr *oauth.TokenExchangeError
			if c.notify != nil && errors.As(err, &exchangeErr) && exchangeErr.IsRefreshTokenRevoked() {
				slog.Info("Refresh token revoked, waiting for re-authentication", "provider", providerCfg.ID)

## Q3
反过来对于模型调用产生的错误，是否有什么重试或处理策略
### Answer
# 模型输出本身导致的"错误" —— 处理策略

区别于 provider/网络层错误，这里指模型生成内容本身有问题（参数格式错误、拒绝回答、超长、重复调用等），Crush 针对这些情况采用的是"识别 + 标记 + 继续对话"策略，而不是网络层重试。

---

## 1. 工具调用参数不是合法 JSON —— 清洗并让模型重试

`OnToolCall` 中调用 `sanitizeToolInput` 检测参数是否为合法 JSON，若不是则标记 `sanitizedToolCalls`，随后 `OnToolResult` 把结果强制替换为明确的错误提示返回给模型： crush:951-983 

这不是内部重试，而是把错误暴露给模型，让模型在对话中自行决定是否重新调用（本质上是"模型级重试"）。

## 2. 内容过滤 / 拒答（Content Filter / Refusal）

`OnStepFinish` 中会检查 `stepResult.FinishReason`，若命中 `fantasy.FinishReasonContentFilter`（如 Anthropic 的 `stop_reason=refusal`、OpenAI 的 `content_filter`），记录一个专门的 `FinishReasonContentFilter`，并记日志，交由 UI 展示 REFUSED 提示： crush:988-1007 

这里没有自动重试逻辑，仅做标记透传给 UI。

## 3. 达到最大输出长度（Max Tokens）

同一个 `OnStepFinish` 里，`fantasy.FinishReasonLength` 被映射为 `message.FinishReasonMaxTokens`： crush:988-994 

也不会自动重试，仅记录该轮结束原因。

## 4. 工具调用循环检测（Loop Detection）

`StopWhen` 中注册了一个停止条件 `hasRepeatedToolCalls`，用于检测模型是否陷入重复调用同一工具的死循环，一旦命中即主动结束当前轮，而不是任其无限重试： crush:1040-1064 

## 5. 悬空工具调用（模型请求工具但没走完流程）

当运行被中断（取消/错误）时，未完成的工具调用会被强制标记为完成并补写 `Input: "{}"`，随后为它们补写错误的 `ToolResult`： crush:1110-1157 

同样地，在准备下一轮历史消息时（`preparePrompt`），任何历史遗留下来的"孤儿"工具调用会被注入合成的错误结果，让模型可以感知到之前的调用失败、并可自行重试： crush:1662-1687 

单测 `TestPreparePrompt_OrphanedToolUse` 验证了这一行为：会为孤儿调用生成 `fantasy.ToolResultOutputContentError` 类型的合成错误结果 crush:800-822 。

---

## 小结

| 模型侧"错误"类型 | 处理策略 | 是否自动重试 |
|---|---|---|
| 工具参数非合法 JSON | 替换为错误提示，回传模型 | 否，交由模型决定是否重调 |
| 内容过滤/拒答 | 标记 `FinishReasonContentFilter`，UI 展示 | 否 |
| 达到最大 token | 标记 `FinishReasonMaxTokens` | 否 |
| 重复调用同一工具（循环） | `hasRepeatedToolCalls` 主动终止轮次 | 否（主动打断） |
| 悬空/孤儿工具调用 | 补写合成错误结果，保持对话结构合法 | 否，模型可自行决定重试 |

## Q1
工具调用错误的分层处理
### Answer
## 回答

根据现有索引内容,Claude Code 中"工具调用错误的分层处理"主要体现在 `EventCalls.tool` 的事件链路和 `ToolUse`/`ToolResult` 类型的错误状态字段上,而不是一个单独的"分层处理"系统。

---

### 工具调用的事件链路

`EventCalls.tool` 定义了工具调用相关的三个可插拔事件:`call`(实际调用)、`check`(权限检查)、`describe`(工具描述) claude-code:3818-3822 。每个事件都会经过插件链(hook chain),各层插件可以通过 `next(e)` 将事件传递给下一层,也可以拦截/改写结果——这正是"分层"体现的地方。

### 错误状态在 `ToolUse` / `ToolResult` 中的表示

调用完成后,该次调用在事务记录(transcript)中的表现由 `ToolUse` 类型描述,包含三个关键的运行状态标志:

- `isRunning`:调用仍在进行中 claude-code:7791-7794 
- `isErrored`:调用以错误结束(包括在弹窗处被拒绝的情况也算一种) claude-code:7795-7798 
- `isInterrupted`:调用被中止打断,可能是用户按 Esc,也可能是插件调用了 `$.turn.abort` 在运行中把它切断,或在其运行前就丢弃了它 claude-code:7799-7805 

对应的调用结果由 `ToolResult` 承载,其中 `output` 存放工具自身的结果对象(比如 Bash 工具的 `{ stdout, stderr, interrupted, ... }`),`isErrored` 标志决定界面是绘制错误文本还是绘制 `output` claude-code:7835-7858 。可以看到,"出错"与"被中断"是两种不同的语义分层:前者代表工具执行失败(包括权限拒绝),后者代表外部中止导致未完成。

### 与权限/策略层的关联(sec-default mod)

在内置安全默认插件 `mods/sec-default` 中,可以看到策略层如何介入工具列表/调用的处理链,例如 `managedToolsRestored` 函数在组织策略(managed settings)和用户层级(user tier)之间合并工具列表,策略读取失败或任一层结果缺失时会"fail closed"(即回退到更严格的一侧),体现出策略校验失败时向上层传播错误(拒绝)而不是静默放行 claude-code:17-33 。这可以看作是"工具调用"在权限检查这一层的错误(拒绝)处理逻辑的一个具体例子,虽然它针对的是 `tool.list`(工具枚举)而非 `tool.call` 本身,但沿用了同样"多层叠加、任一层失败即收紧"的模式。

在现有索引中,确实能找到与你描述的"分层错误重试策略"相符的具体实现,但主要来自 `security-guidance` 插件的 `_call_claude` 函数,而非核心 CLI 引擎本身。

---

### `_call_claude` 中的分层重试策略

`plugins/security-guidance/hooks/llm.py` 中的 `_call_claude` 函数实现了你描述的三种典型错误处理策略 claude-code:386-400 :

1. **限流/瞬时错误 → 有限次数指数退避重试**
   `429`(限流)和可选的 `5xx`(503/502/529 等瞬时错误)会触发最多 3 次重试,退避时间随尝试次数递增(429 是 `(attempt+1)*5` 秒,5xx 是 `(attempt+1)*2` 秒) claude-code:469-473 。网络层错误(`URLError`/`TimeoutError`)同样走固定次数(3 次)、递增退避(`(attempt+1)*3` 秒)的重试逻辑 claude-code:479-487 。

2. **认证参数错误 → 就地纠正重试**
   如果用 `x-api-key` 请求收到 `401`,且存在备用的 `ANTHROPIC_AUTH_TOKEN`,代码会切换认证方式后 `continue` 重试,而不是直接失败 claude-code:462-468 ——这属于"参数/认证错误的即时纠正重试",不同于把错误原样返回给模型重试。

3. **不可重试错误 → 直接中断返回**
   对于非限流、非可重试的 5xx,或重试次数耗尽后,代码记录状态码到 `_last_call_claude_http_error` 并 `return None`,把处理权交还给调用方,不再自行重试 claude-code:474-478 。

此外,函数还专门支持 `retry_5xx=False` 模式:让 5xx 立即返回 `None`,以便上层的"模型链"(fallback chain)可以快速切换到下一个模型,而不必先付出约 6 秒的退避成本;但 429 无论如何都会重试,因为这是针对具体 API key 的限流,换模型也无法绕过 claude-code:396-399 。

### 第三方(3P)Provider 的降级路径

当检测到 Bedrock/Vertex/Foundry 等第三方 provider 时,`_call_claude` 会完全绕过上面的 HTTP 重试逻辑,转而通过 `_call_claude_via_sdk` 走 Agent SDK 子进程调用,该子进程有独立的 60 秒超时(区别于上面的按次重试),超时或调用失败都直接返回 `None` 而不重试 claude-code:360-383 claude-code:404-412 。这体现了"重试策略因错误来源分层":HTTP 直连路径按错误类型精细重试,SDK 委托路径则简单地"超时/失败即放弃"。

---

### 核心引擎侧的模型调用错误策略(仅有 CHANGELOG 描述,无实现代码)

1. **不可预期的不可重试错误 → fallback 模型重试一次**
   当 API 拒绝请求且属于"不可预期的非可重试错误"时,Claude Code 会在配置的 fallback 模型上重试一次该 turn;但认证、限流、请求体过大、传输层错误这几类会被视为"确定性失败",直接上抛给用户/上层,而不会做 fallback 重试 claude-code:2907-2907 。这正对应了你说的"其他错误直接中断"这一策略分支。

2. **`fallbackModel` 设置 → 主模型过载/不可用时的多级 fallback**
   `fallbackModel` 设置支持配置最多三个按顺序尝试的 fallback 模型,在主模型过载或不可用时依次切换 claude-code:2903-2903 。这是"限流/过载类错误 → 换模型重试"策略的具体配置项。

3. **工具调用格式错误(模型输出畸形) → 丢弃错误输出后重试**
   当模型生成的工具调用格式有问题时,系统会把畸形的输出从重试上下文中丢弃,然后重试,这一行为覆盖 Bedrock、Vertex 和 Foundry 等第三方 provider claude-code:1152-1152 。这属于"模型自身输出错误 → 清理后重新调用"的策略,与"调用参数错误反馈给模型重试"的思路一致。

4. **流式响应中断 → 自动续接而非视为失败**
   当响应被计算机休眠、连接断开或服务器错误从流中截断时,子agent不会因此终止,而是自动续接,而不是报告一个不完整的响应 claude-code:1023-1023 。这是"传输层临时故障 → 自动恢复继续"的策略,不同于直接失败中断。

5. **无响应头 → 延长等待而非提前判定失败**
   当 API 未返回任何响应头时,重试逻辑现在会等待到 `API_TIMEOUT_MS`(默认 10 分钟)而不是提前 3 分钟就判定失败,并且提示信息说明该如何调整 claude-code:835-835 。这体现了"超时类错误 → 延长等待窗口"的调优策略。

6. **`/goal` 等长任务的模型调用失败 → 指数退避重试或暂停并说明原因**
   针对 API 错误、网络掉线或 token 限制导致的静默卡死,`/goal` 现在会带指数退避重试,或者暂停并说明原因(包括等到用量限制重置) claude-code:553-553 。这是目前索引里描述最接近你说的"有限次数+指数退避"策略的一条记录。

7. **自托管 runner 场景的 401 → 持续重试并主动刷新凭证**
   自托管 runner 会话在 401 后会持续重试,而不是等到下一次计划刷新才恢复,并且在收到 401 后主动获取新 token claude-code:235-235 。这属于"认证错误 → 主动纠正后重试"的策略,类似上一轮 `security-guidance` 插件里 401 fallback 到 `ANTHROPIC_AUTH_TOKEN` 的做法。

8. **中断的 turn 恢复 → 有时间窗口限制,防止重试过期的失败**
   `CLAUDE_CODE_RESUME_INTERRUPTED_TURN` 之前会重新运行 6 小时甚至更早之前失败的 turn;现在修复为按 `CLAUDE_CODE_RESUME_INTERRUPTED_TURN_MAX_AGE_MS` 限制重试的时间窗口 claude-code:556-556 。这说明系统对"API 错误导致的中断"有专门的重试/恢复机制,但也设有时效边界防止对过期错误做无意义重试。

# 工具调用错误的分层处理

Codex 的工具调用系统对错误采取了多层次的处理架构，从最底层的执行错误分类，到中间层的调度/钩子处理，再到最外层的取消/超时兜底，层层递进。

---

## 第一层：执行结果 → 错误事件的转换 (`ToolEvents::finish`)

最底层是执行结果的分类，`ToolEvents::finish` 根据 `Result<ExecToolCallOutput, ToolError>` 将不同的错误类型映射为不同的 `ToolEventStage` 和 `FunctionCallError`：

- 成功但退出码非 0 → `RespondToModel` codex:393-397 
- 沙箱超时（`SandboxErr::Timeout`）→ 单独的 `ToolEventFailure::Output` codex:400-407 
- 沙箱拒绝（`SandboxErr::Denied`）→ 对 `apply_patch` 有特殊处理：如果已经提交了部分补丁前缀，走 `Success` 分支保留 diff codex:408-423 
- 其它 Codex 内部错误 → 通用 `execution error: {err:?}` 消息 codex:424-429 
- 用户拒绝审批 (`ToolError::Rejected`) → 归一化提示语（"exec command rejected by user" / "patch rejected by user"） codex:431-456 

---

## 第二层：`ToolRegistry::dispatch_any_with_terminal_outcome` 中的钩子拦截

在 `ToolRegistry` 层面，错误处理围绕 hook 生命周期（Pre/PostToolUse）分层：

1. **工具不存在** → 生成 `unsupported_tool_call_message`，记录到 `dispatch_trace.record_failed`，返回 `FunctionCallError::RespondToModel` codex:516-536 
2. **payload 类型不匹配** → `FunctionCallError::Fatal` codex:549-565 
3. **PreToolUse hook 阻断** → `PreToolUseHookResult::Blocked` 转换为 `RespondToModel`，同时通过 `notify_tool_finish_if_unclaimed` 标记生命周期为 `Blocked` codex:577-591 
4. **Hook 输入重写失败** → 记录 `ToolCallOutcome::Failed { handler_executed: false }` codex:598-613 
5. **PostToolUse hook 阻断**（工具已执行完成后）→ 独立于执行结果之外的拒绝路径，`lifecycle_outcome` 标记为 `handler_executed: true`，随后如果 `outcome.should_block` 为真，仍会把已经成功的结果转换为错误 codex:707-731 

这体现了"handler 是否已经执行"（`handler_executed`）作为区分错误发生阶段的关键标志。

---

## 第三层：并行调度层的取消/超时兜底 (`ToolCallRuntime`)

在 `parallel.rs` 中，`ToolCallRuntime::dispatch` 处理任务被取消/中止的情形，是错误处理的最外层兜底：

- 若任务已完成或已达到终态（`terminal_outcome_reached`），直接等待结果 codex:182-186 
- 否则真正中止任务：`dispatch_handle.abort()`，然后构造 `aborted_response`，并调用 `notify_tool_aborted` 通知会话 codex:187-206 
- `tool_task_join_error` 把 tokio 任务 join 失败也统一包装为 `FunctionCallError::Fatal` codex:215-217 
- `failure_response` 根据 `ToolPayload` 类型（`ToolSearch` / `Custom` / 默认 Function）分别构造不同结构的错误响应，确保模型侧收到符合协议的输出格式 codex:219-244 

---

## 第四层：MCP 外部工具调用的独立错误路径

对于 MCP（Model Context Protocol）外部工具，错误处理在 `handle_mcp_tool_call` 中单独展开：

- **参数解析失败** → 直接返回 `CallToolResult::from_error_text` codex:141-150 
- **工具不可用**（`prepared_call` 为空）→ 通过 `notify_mcp_tool_call_skip` 通知并返回跳过结果 codex:159-176 
- **元数据构建失败** → 同样走 `notify_mcp_tool_call_skip` codex:184-202 

`McpHandler::handle_call` 是这条路径在工具系统里的入口，它负责把结果包装成 `McpToolOutput` 并交回给 `ToolRegistry` 统一处理 codex:228-248 。

---

## 第五层：可观测性 - 错误的追踪记录

## Q2
是否有关于不同错误重试策略，比如超时限流等内部执行有限次数多指数退避重试，调用参数错误等返回给模型重试，其他错误等中断退出等错误处理策略
### Answer
## 直接回答

在你之前问的"工具调用错误分层"体系（`ToolEvents::finish` / `ToolRegistry::dispatch_any_with_terminal_outcome` / `ToolCallRuntime`）里，**并没有统一的"按错误类型分级重试"策略**——那一层的逻辑是一次性分类 + 返回（`RespondToModel` / `Fatal` / 中止），没有内部自动重试或指数退避。真正的**指数退避重试**逻辑存在于两个不同的、更底层的子系统里：

1. MCP 客户端传输层的 `run_service_operation_with_transient_retries`（针对可重试的网络错误） codex:1354-1408 
2. `exec-server` 连接恢复层的 `is_retryable_recovery_error` + `registry_recovery_retry_delay`（针对连接/注册中心错误） codex:835-896 

这两者与工具调用的错误分层处理（`FunctionCallError` 分类）是**不同的系统**，请不要混为一谈。

---

## 详细说明

### 1. MCP 客户端的重试（超时/限流类错误）

`RmcpClient::run_service_operation` 是 MCP 工具调用（如 `tools/list`, `tools/call`）的统一入口，遇到会话过期（404）会先尝试重新初始化再重试一次 codex:1316-1352 。

真正的**有限次数 + 固定/递增延迟重试**在 `run_service_operation_with_transient_retries` 中：它遍历 `STREAMABLE_HTTP_RETRY_DELAYS_MS` 数组作为重试延迟表，只有当 `is_retryable_tools_list_error` 判定错误可重试（当前限定为 `tools/list` 的可重试传输错误）时才继续重试，否则直接返回错误；重试次数耗尽后按最后一次结果返回 codex:1354-1408 。

单次尝试的超时控制在 `run_service_operation_once` 中，通过 `active_time_timeout` 包装，超时则映射为 `ClientOperationError::Timeout` codex:1410-1433 。

这条重试链**只覆盖 MCP 传输层网络故障**（连接被拒、超时等），不涉及"参数错误让模型重试"或"其他错误中断退出"这类语义分层。

### 2. `exec-server` 的连接恢复重试（指数退避）

`registry_recovery_retry_delay` 是标准的**指数退避**实现：`multiplier = 1 << min(attempt, 4)`，`base_delay` 随尝试次数倍增直到 `REGISTRY_RECOVERY_MAX_RETRY_INTERVAL` 上限，并加入基于 hash 的随机抖动 codex:885-896 。

是否值得重试由 `is_retryable_recovery_error` 判定：连接中断、`ProvisioningFailed`、WebSocket 连接/初始化超时、注册中心可重试错误（连接失败/超时/5xx/429）、以及特定的"会话已被占用"错误码都属于可重试范围 codex:835-874 。

这是**执行环境（沙箱/容器）连接层**的恢复机制，不是"工具调用参数错误 vs 内部错误"的分级重试。

### 3. 工具调用错误分层里"没有"重试的证据

回顾核心分层代码：`ToolEvents::finish` 直接把执行结果一次性映射为 `Ok`/`Err(FunctionCallError)`，没有循环或延迟逻辑 codex:379-460 ；`ToolRegistry::dispatch_any_with_terminal_outcome` 中每个错误分支都是"记录 trace + 直接 return Err"，同样是一次性处理，没有重试循环 codex:495-565 ；`ToolCallRuntime` 在取消场景下也只是构造 `aborted_response` 后返回，不会重新调度任务 codex:187-206 。

## Notes

- `FunctionCallError` 本身只有语义分类（`RespondToModel` vs `Fatal`），决定错误消息是"喂给模型让它自己决定要不要重试"还是"直接中断本轮"，但这属于错误消息的**呈现策略**，不是自动重试机制。

## Q3
反过来对于模型调用产生的错误，是否有什么重试或处理策略
### Answer
## 直接回答

有的。与工具调用的一次性错误分类不同，**模型 API 调用有专门的多层重试系统**：底层由 `codex-client` 的 `RetryPolicy`（针对普通 HTTP 请求，覆盖 429/5xx/传输错误）负责重试 codex:11-36 ；流式请求（Responses API 长连接）由 `codex-rs/core/src/responses_retry.rs` 中的 `handle_retryable_response_stream_error` 专门处理，按错误类型分为"不可重试立即退出"（如上下文超限、用量超限）、"有限次数 + 退避重试"、"连接失败无限重试"、"重试耗尽后降级传输协议"四类策略。

---

## 详细说明

### 1. 错误分类的起点：`map_api_error`

模型 API 返回的原始传输错误（HTTP 状态码、SSE 内容）先经过 `map_api_error` 统一映射为 `CodexErr`：例如 429 会区分出 `UsageLimitReached`（含 plan 类型、恢复时间、rate limit 快照）vs 普通 `RetryLimit`；503 且带 `server_is_overloaded`/`slow_down` code 映射为 `ServerOverloaded`；`ApiError::Retryable`/`RateLimitExceeded` 会携带服务器建议的 `delay` 并通过 `with_retry_delay` 附加到 `CodexErr` 上 codex:21-39 codex:131-169 。

`CodexErr` 结构本身携带一个可选的 `retry_delay`,并提供 `retry_delay()` / `with_retry_delay()` 存取方法，供上层重试逻辑读取服务器建议的等待时间 codex:414-421 。`CodexErrorDetails` 枚举定义了所有语义分类，比如 `Stream`（流断开，session 循环视为瞬时错误自动重试）、`RateLimitExceeded`、`ContextWindowExceeded`、`ServerOverloaded`、`RetryLimit` 等 codex:83-167 。

### 2. 传输层（unary 请求）重试：`RetryConfig` / `RetryPolicy`

针对普通 HTTP 请求（非流式），Provider 级别配置了 `RetryConfig`，可分别开关 429、5xx、传输错误的重试，并设置最大重试次数与基础延迟；它会转换成 `codex-client` 使用的 `RetryPolicy` codex:11-36 。测试用例证实了这一行为，例如临时认证失败会自动重试 codex:491-514 ，而认证构建错误（非瞬时）则不会重试 codex:516-547 。这与 `codex-rs/core/tests/suite/retry_after.rs` 中的 `http_retry_backoff_exhausts_attempts` 用例一致，验证了固定次数指数退避的行为 codex:296-346 。

### 3. 流式请求重试：`handle_retryable_response_stream_error`

真正的核心逻辑在 `codex-rs/core/src/responses_retry.rs`。它被 `run_sampling_loop`（`codex-rs/core/src/session/turn.rs`）在每次采样请求失败时调用，构成一个 `loop`：

```
try_run_sampling_request → 失败 → 按 err.details() 分类处理 → 重试或返回
```

具体分支：

- **不可重试，立即退出**：`ContextWindowExceeded`（上下文超限）会记录 `total_tokens_full` 后直接返回错误 codex:1479-1483 ；`UsageLimitReached`（额度耗尽）会先更新 rate limit 状态，同样直接返回，不做自动重试（因为重试没有意义，必须等待额度恢复） codex:1484-1490 。
- **其它错误先判断 `err.is_retryable()`**：不可重试则直接返回 codex:1499-1501 ；可重试则调用 `handle_retryable_response_stream_error`，成功后进入下一轮循环并调用 `turn_context.turn_timing_state.record_sampling_retry()` codex:1503-1513 。

在 `handle_retryable_response_stream_error` 内部，进一步分三种策略：

1. **无限重试（仅连接失败 + Feature 开关）**：当 `Feature::UnboundedConnectionRetries` 开启、错误是 `ConnectionFailed`、且不是内部会话/Bedrock 时，走独立的"连接重试计数器"（不消耗常规重试预算），延迟从 5 秒起指数翻倍，上限 60 秒 codex:17-18 codex:58-83 。测试 `connection_failures_increment_retry_telemetry_without_consuming_retry_budget` 验证了这个行为（5s → 10s 指数退避） codex:1324-1394 。
2. **重试次数耗尽后降级传输协议**：当常规重试次数达到 `max_retries` 且能切换到 fallback transport（WS→HTTP），则发出 `Warning` 事件并重置重试计数，让请求继续用新传输方式重试 codex:85-100 。
3. **常规有限次数 + 退避重试**：重试次数 `< max_retries` 时，延迟优先取服务器建议值（`err.retry_delay()`），否则本地退避 `backoff(retry_count)`；同时向 UI 发送 `notify_stream_error` 提示重连状态，并通过 `codex_client::record_retry!` 记录遥测 codex:102-126 。多个测试验证了服务器建议延迟优先于本地退避，例如 rate-limit 消息里的建议延迟 codex:1070-1121 ，以及 websocket 连接数超限时的本地退避重连 codex:1396-1458 。
4. **重试次数耗尽且无法降级，直接返回 `Err(err)`** codex:128-128 。这在测试 `websocket_overload_with_nested_retry_after_is_terminal` 中体现：即使错误里嵌套了 `Retry-After`，`ServerOverloaded` 仍是终态，不会继续重试或降级传输 codex:1606-1687 。

### 4. 终局：中断退出 & 呈现给用户

当所有重试路径都耗尽或错误不可重试时，`run_sampling_loop` 直接把 `CodexErr` 向上抛出；测试 `continue_after_stream_error` 说明一次流失败会中断本轮，但下一轮用户输入仍可正常发起新请求（并非直接杀死整个 session） codex:20-53 。`CodexErr::to_codex_protocol_error` 把内部错误类别映射成对外协议里的 `CodexErrorInfo`（比如 `ContextWindowExceeded`、`RateLimitExceeded`、`ServerOverloaded`、`ResponseTooManyFailedAttempts` 等），供 UI/客户端呈现具体错误原因 codex:430-465 。

## Q1
对于模型请求发送错误时，是否有重试策略
### Answer
## 答案

是的，eino 提供了完整的模型请求重试策略，通过 `ChatModelAgentConfig.ModelRetryConfig`（即 `TypedModelRetryConfig[M]`）配置<cite repo="cloudwego/eino" path="adk/chatmodel.go" start="403-407" end="403-407" />。它支持最大重试次数、可自定义的重试判断逻辑，以及重试前的等待策略。

---

## 详细说明

### 配置入口

在创建 `ChatModelAgent` 时，可通过 `ModelRetryConfig` 字段开启重试；若为 `nil` 则不重试<cite repo="cloudwego/eino" path="adk/chatmodel.go" start="403-407" end="403-407" />。此外还有配套的 `ModelFailoverConfig`，在重试耗尽后可切换到备用模型<cite repo="cloudwego/eino" path="adk/chatmodel.go" start="409-414" end="409-414" />。

### 核心配置结构 `TypedModelRetryConfig`

该结构体定义在 `adk/retry_chatmodel.go`，主要字段包括：

- `MaxRetries`：最大重试次数，0 表示不重试<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="222-226" end="222-226" />
- `ShouldRetry`：新版回调，接收 `TypedRetryContext`（包含输出消息、错误、重试次数等），返回 `TypedRetryDecision`，可以决定是否重试、改写错误、修改输入消息、追加模型选项、自定义等待时长等<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="228-239" end="228-239" />
- `IsRetryAble`：旧版（已 Deprecated）判断错误是否可重试的回调，向后兼容<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="241-244" end="241-244" />
- `BackoffFunc`：计算下次重试前等待时长，若不设置则使用内置指数退避+抖动算法（基础 100ms，最大 10s）<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="246-252" end="252-252" /><cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="262-281" end="262-281" />

### 执行逻辑

真正的重试逻辑由 `typedRetryModelWrapper` 实现，它包裹底层模型 `model.BaseModel[M]`<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="319-330" end="319-330" />：

- `Generate` 方法：如果设置了 `ShouldRetry` 则走新逻辑 `generateWithShouldRetry`，否则走旧逻辑 `generateLegacy`（基于 `IsRetryAble`+`BackoffFunc` 循环重试直到 `MaxRetries`）<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="332-337" end="332-337" /><cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="339-377" end="339-377" />
- `Stream` 方法同理，分为 `streamWithShouldRetry` 与 `streamLegacy`<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="678-685" end="678-685" /><cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="687-759" end="687-759" />

两种情况下都会跳过一些特殊错误的重试，例如中断信息（`compose.ExtractInterruptInfo`）和 `ErrStreamCanceled`，这些错误直接返回不会重试<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="356-362" end="356-362" />。

若所有重试次数用尽仍然失败，会返回 `RetryExhaustedError`，其中包含最后一次错误和总重试次数<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="376-376" end="376-376" />。

### 重试通知事件

在重试过程中，会向事件流发送 `WillRetryError`，用于实时观测重试行为，其中还可携带用户自定义的 `RejectReason`<cite repo="cloudwego/eino" path="adk/retry_chatmodel.go" start="96-100" end="96-100" />。

### 与 Failover 的配合

重试耗尽后，若同时配置了 `ModelFailoverConfig`，agent 会切换到备用模型继续尝试，测试用例 `TestRetryThenFailover` 中的 `Generate_RetryExhaustedTriggersFailover` 场景验证了这一行为<cite repo="cloudwego/eino" path="adk/wrappers_retry_failover_test.go" start="49-97" end="49-97" />。

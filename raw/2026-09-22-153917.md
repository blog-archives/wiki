# DeepWiki Q&A with Code Context for Repository: openai/codex
## Q1
请从用户提交一条消息开始，追踪到模型调用、工具执行、工具结果回传，再到最终回答的完整路径。指出入口函数、Agent 循环、模型调用位置、工具分发位置和停止条件。先选默认或最简单的一条路径，不展开全部实现分支。
### Answer
## 答案概述

最简路径：用户消息作为 `Submission`（含 `Op::UserTurn`）进入 Session 的输入队列，由 `run_turn` 驱动的循环发起模型采样请求 `run_sampling_request`，流式接收 `ResponseEvent`；若响应包含工具调用，则通过 `ToolRouter`/`registry` 分发执行，工具结果写回历史后继续下一轮采样；当模型输出无工具调用的最终消息（或历史规范中"无更多输出"）时循环结束，发出 `EventMsg::TurnComplete`。

---

## 详细路径

### 1. 入口：Submission 与 Op

用户输入被包装为 `Submission`，携带 `Op::UserTurn`，通过 SQ（Submission Queue）进入 Codex 核心，这是协议文档中定义的顶层入口概念 <cite repo="openai/codex" path="codex-rs/docs/protocol_v1.md" start="16-32" /> <cite repo="openai/codex" path="codex-rs/docs/protocol_v1.md" start="68-72" />。

### 2. Agent 循环：`run_turn`

`run_turn` 是一个 `Task`（由若干 `Turn` 组成）的主体，函数体内先做首次上下文捕获（`capture_step_context_with_required_mcp_servers`），随后进入 `loop`，每次迭代：捕获/复用 `step_context`，构造 `sampling_request_input`，调用 `run_sampling_request` codex:333-441 。这个循环即是 Agent 主循环，一轮对应一次模型请求+工具执行的组合，输出作为下一轮输入，符合协议文档中 `Turn` 的定义 <cite repo="openai/codex" path="codex-rs/docs/protocol_v1.md" start="34-41" />。

### 3. 模型调用位置

`run_sampling_request` 内部通过 `client_session`（`ModelClientSession`）发起流式请求，随后在 `outcome` 循环里通过 `stream.next()` 逐个接收 `ResponseEvent`，直到收到 `response.completed` 或流关闭/出错 codex:2335-2372 。这对应架构文档中 Turn 执行流程图里 `Client->>Turn: ResponseEvent` 的部分。

### 4. 工具分发位置

当响应中出现工具调用项时，Session/`ToolRouter` 将其分发给具体工具处理器执行。核心分发逻辑位于 `codex-rs/core/src/tools/registry.rs` 中的 `handle_any_tool`，它调用 `tool.handle(invocation.clone())` 执行具体工具，并生成 `AnyToolResult` codex:772-797 。执行完成后，结果经过 PostToolUse 钩子检查、成功/失败判定，最终通过 `dispatch_trace.record_completed`/`record_failed` 记录并返回 `Ok(result)` 或 `Err(err)` codex:698-756 。

MCP 类工具（例如 `mcp_resource`）走的是同样模式：先 `emit_tool_call_begin`，执行 `operation`，再 `emit_tool_call_end` 把结果回传到会话事件流 codex:280-324 。

### 5. 工具结果回传

工具执行结果（`AnyToolResult`/`ToolOutput`）被写回到会话历史（conversation items），供下一次 `run_sampling_request` 的 `sampling_request_input` 使用；`run_turn` 循环中通过 `sess.clone_history().await.for_prompt(...)` 把已记录的工具输出重新纳入下一轮模型输入 codex:416-424 。这形成了"模型调用 → 工具分发 → 结果回传 → 再次模型调用"的闭环，正是循环体内 `next_step_context`/`step_context` 反复构造的原因。

### 6. 停止条件

循环退出（即最终回答产生）依据协议文档定义的几种终止条件：
- 模型完成任务且没有更多输出可供下一轮 Turn（无工具调用、无待处理输入）
- 用户新一轮输入打断当前 Task 并开启新 Task
- UI 发送 `Op::Interrupt`
- 致命错误（如模型连接超出重试次数）
- 阻塞等待用户批准（执行命令或应用补丁）

async fn handle_any_tool(
    tool: &dyn CoreToolRuntime,
    invocation: ToolInvocation,
) -> Result<AnyToolResult, FunctionCallError> {

    let payload = invocation.payload.clone();

    if output.contains_external_context()
        && invocation.turn.config.memories.disable_on_external_context
    {

            "tool_output",
        )
        .await;
    }
    let post_tool_use_payload =
        CoreToolRuntime::post_tool_use_payload(tool, &invocation, output.as_ref());
    Ok(AnyToolResult {
        call_id,
        payload,
        result: output,
        post_tool_use_payload,
    })

## Q2
在刚才的执行路径上，最终发送给模型的请求在哪里组装？请列出其中的系统提示、工具定义、历史消息、当前用户输入、检索结果、记忆和任务状态分别来自哪里、以什么形式进入请求，以及排列顺序。哪些内容每轮重建，哪些内容持续累积？
### Answer
## 答案概述

最终发送给模型的请求由两步组装：先在 `build_prompt` 中构造与传输无关的 `Prompt` 结构 codex:1381-1399 ，再在 `ModelClient::build_responses_request`（`codex-rs/core/src/client.rs`）中把 `Prompt` 转换成实际的 `ResponsesApiRequest` 线上格式 codex:935-1032 。

---

## 详细拆解

### 1. `Prompt` 的组装（`build_prompt`）

```rust
Prompt {
    input,                                    // 历史消息 + 当前用户输入
    tools: step_context.tool_router.model_visible_specs(),  // 工具定义
    parallel_tool_calls: true,
    base_instructions,                        // 系统提示
    output_schema: turn_context.final_output_json_schema.clone(),
    ...
}
``` codex:1381-1399 

各字段来源：

| 字段 | 来源 | 形式 |
|---|---|---|
| `input` | `sess.clone_history().await.for_prompt(...)`，即会话历史经归一化后的 `Vec<ResponseItem>` | `ResponseItem` 列表（含历史消息、用户输入、工具调用/结果） |
| `tools` | `step_context.tool_router.model_visible_specs()`，每步（step）重新构建的工具集合 | `Arc<[ToolSpec]>` |
| `base_instructions` | `sess.get_base_instructions()`（系统提示/base instructions） | 纯文本 `BaseInstructions` |
| `output_schema` | `turn_context.final_output_json_schema` | 可选 JSON schema |

`input` 的具体拼装发生在 `run_turn` 循环里：`sess.clone_history().await.for_prompt(&step_context.settings.model_info.input_modalities)` codex:416-424 。这一步把**持续累积的对话历史**（用户消息、assistant 回复、工具调用与结果）转换为模型可读的 `ResponseItem` 序列——这就是"历史消息 + 当前用户输入 + 工具结果回传"共同进入请求的地方。用户当前输入在进入循环前已通过 `record_conversation_items` 写入历史，因此在这一步会作为历史的最后一条被自然包含进去。

“检索结果”和“记忆”若存在（例如 memories 系统、connector 检索），也是先被写入会话历史（`record_conversation_items`/`record_additional_contexts`）后，再随下一次 `clone_history().for_prompt(...)` 一并纳入 `input`，本质上走的是同一条通道，而不是单独的字段。“任务状态”（sticky routing 的 `x-codex-turn-state`）不进入 `Prompt.input`，而是走 HTTP/WS 请求头，详见下文。

`prompt_debug.rs` 中的调试构造函数演示了同样的组装顺序：捕获 step context → 记录用户输入 → `clone_history().for_prompt(...)` → `build_prompt(...)` codex:84-111 ，可以印证这条主线路径。

| 内容 | 来源 | 进入请求的形式 | 位置 |

### 4. 每轮重建 vs 持续累积

- **每轮重建**：`tools`（`step_context.tool_router` 在每个 step 都重新捕获，见 `run_turn` 循环中 `capture_step_context_with_required_mcp_servers` 的调用） codex:366-403 ；`base_instructions`/`instructions`（每次请求都从当前配置读取，不做增量）；`responses_lite` 模式下的 `AdditionalTools`/指令前缀项也是每次重建，只是用确定性哈希保持身份一致，方便重试/续接时对齐 codex:938-967 。
- **持续累积**：会话历史（`sess.clone_history()` 背后的存储），包括历史消息、用户输入、工具调用与结果、以及写入历史的记忆/检索上下文，都是跨轮次持续追加的，每轮只是重新序列化（`for_prompt`）成 `input`，而不是重新生成内容 codex:416-424 。
- **turn-scoped 而非跨轮累积**：sticky routing token（`x-codex-turn-state`）是 `ModelClientSession` 内的单轮状态，仅在同一 turn 内的连续请求间复用，不进入下一次用户消息的新 turn。

## Q3
这个项目如何确定可用上下文窗口、估算输入 token，并预留输出空间？系统提示、工具定义、历史消息、检索结果和记忆之间是否存在明确预算或优先级？预算检查发生在工具结果加入之前还是之后？超过预算时实际执行什么降级策略？请区分显式分配、隐式占用和未做管理的部分。
### Answer
## 答案概述

可用上下文窗口由 `ModelInfo::resolved_context_window`/`usable_context_window` 结合 `effective_context_window_percent` 显式计算，并作为硬上限 codex:498-521 ；输入 token 估算靠 `sess.get_total_token_usage()`（API 报告值）与本地 `estimate_item_token_count` 启发式两条路径 codex:654-690 ；预算检查发生在**模型响应完成之后**（即工具调用结果已写入历史之后）的下一轮准备阶段，而非工具结果加入之前；超预算时的降级策略是触发自动压缩（auto-compact）或历史裁剪（`trim_function_call_history_to_fit_context_window`）。系统提示、工具定义与历史消息之间没有独立的“预算配额”划分——只有历史消息类别（尤其工具输出）享有显式的 token 预算/裁剪逻辑，系统提示和工具定义是隐式占用、未被主动裁剪的部分。

---

## 详细分析

### 1. 上下文窗口与预留空间的确定

`ModelInfo` 定义了 `resolved_context_window`（取 `context_window` 或 `max_context_window`）与 `usable_context_window`（乘以 `effective_context_window_percent` 后取整除 100，实际预留了 headroom） codex:498-508 。这个百分比即是显式为输出/安全边界预留空间的机制。

自动压缩阈值 `auto_compact_token_limit` 另外取 `resolved_context_window * 9/10` 与配置值的较小者，作为比“硬上限”更早触发的软阈值 codex:510-521 。

### 2. 输入 token 的估算

`context_window_token_status_with_config` 是核心预算检查函数：
- `active_context_tokens` 来自 `sess.get_total_token_usage()`（API 上一次响应报告的累计用量）
- 按配置的 `AutoCompactTokenLimitScope`（`Total` 或 `BodyAfterPrefix`）计算 `auto_compact_scope_tokens`
- `full_context_window_limit` = `resolved_context_window * effective_context_window_percent / 100`
- 判断 `token_limit_reached`（软阈值+fallback buffer）与 `full_context_window_limit_reached`（硬上限） codex:52-120 

本地（未发起请求前）的 token 数也可用 `ContextManager` 的启发式估算，例如 `get_non_last_reasoning_items_tokens` 通过 `estimate_item_token_count` 对每个历史条目做近似计数 codex:666-690 。`recompute_token_usage` 也会在没有 API 用量数据时用 `history.estimate_token_count_with_base_instructions` 兜底估算总 token 数并写回 `TokenUsageInfo` codex:4437-4474 。

### 3. 系统提示/工具定义/历史/检索/记忆之间是否有明确预算或优先级？

**没有跨类别的硬性配额划分**。从代码看：
- token 预算检查（`context_window_token_status_with_config`）只针对**总量**（`active_context_tokens`），不区分系统提示、工具定义、历史消息各自占多少份额 codex:56-94 。
- 唯一有"预算"概念的显式配置是 `TokenBudgetConfig`（`reminder_threshold_tokens`、`auto_compact_fallback_buffer_tokens`），但这也是作用于**整体上下文窗口**的提醒/兜底阈值，而非按内容类型分配 codex:78-118 。
- 唯一有类别区分裁剪优先级的是**远程压缩时的历史裁剪** `trim_function_call_history_to_fit_context_window`：它专门针对"Codex 生成的"条目——工具调用输出（`FunctionCallOutput`/`CustomToolCallOutput`/`ToolSearchOutput`）——从历史**最旧**部分开始截断/替换，而不会触及系统提示（`base_instructions`）本身（`base_tokens` 只是被计入总量，但不被裁剪） codex:403-459 。这说明历史中的工具输出比其它历史条目有更低的保留优先级。

### 4. 预算检查发生在工具结果加入之前还是之后？

发生在**之后**。在主循环 `run_turn` 中，`run_sampling_request` 完成（包括其内部的工具调用与结果回传都已写入历史）之后，才计算 `token_status`：

```rust
let (has_pending_input, token_status) = async {
    ...
    let token_status = super::context_window::context_window_token_status(...).await;
    ...
}
``` codex:458-469 

随后基于 `token_status.token_limit_reached` 决定是否 `should_roll_over`（触发压缩） codex:505-514 。也就是说，预算检查是**每步（step）结束后、下一次采样请求发起前**的把关点，工具调用结果早已计入历史（并因此计入下次估算的 token 数），而不是在工具结果生成时或写入前拦截。

对于远程压缩路径，`trim_function_call_history_to_fit_context_window` 则是在**发起压缩请求前**，对已有历史做裁剪以适配上下文窗口 codex:34-39 ，同样是"结果已写入历史之后"的后处理，而非拦截。

### 5. 超预算时的降级策略

主要有两条路径：

1. **Auto-compact（自动压缩）**：当 `should_roll_over`（`token_limit_reached` 或显式请求新窗口）为真时，调用 `run_auto_compact`，用 `InitialContextInjection::BeforeLastUserMessage` 把总结插入历史，随后 `continue` 循环重新采样 codex:505-544 。压缩本身分本地/远程两种实现（见上一轮讨论的 wiki），远程压缩会先执行历史裁剪 `trim_function_call_history_to_fit_context_window` 再调用压缩端点 codex:23-98 。
2. **Token budget 提醒/回退 (`maybe_record`)**：当 `base_window_tokens_remaining` 低于 `reminder_threshold_tokens` 时，向历史注入一条提醒消息；如果 `allow_auto_compact_fallback` 且余量归零，则注入 `auto_compact_fallback_prompt`（例如提示模型"保存重要状态"） codex:159-214 。这是给模型的"软提示"，不是强制截断。

超出硬上限（`full_context_window_limit_reached`）与超出软阈值（`token_limit_reached`）都会走向同一个 `should_roll_over` 分支，触发压缩 codex:505-514 ，测试用例中也验证了"fallback buffer 耗尽后滚动到新 context window"的行为 codex:1324-1422 。

### 6. 显式分配 / 隐式占用 / 未管理部分总结

| 类别 | 归类 | 依据 |
|---|---|---|
| 上下文窗口整体大小（`usable_context_window`）与自动压缩阈值 | **显式分配** | `ModelInfo::usable_context_window`/`auto_compact_token_limit` 显式按百分比/配置计算 codex:503-521  |

async fn context_window_token_status_with_config(
    sess: &Session,
    config: &Config,
    model_info: &ModelInfo,
) -> ContextWindowTokenStatus {
    let active_context_tokens = sess.get_total_token_usage().await;

    // Count either the full active context or only the tokens added after the initial prefix.
    let (auto_compact_scope_tokens, auto_compact_scope_limit, auto_compact_window_prefill_tokens) =
        match config.model_auto_compact_token_limit_scope {
            AutoCompactTokenLimitScope::Total => (
                active_context_tokens,
                model_info.auto_compact_token_limit(),
                None,
            ),
            AutoCompactTokenLimitScope::BodyAfterPrefix => {
                let window = sess.auto_compact_window_snapshot().await;
                let baseline = window.prefill_input_tokens.unwrap_or(active_context_tokens);

                let scope_limit = config
                    .model_auto_compact_token_limit
                    .or_else(|| model_info.auto_compact_token_limit());
                (
                    active_context_tokens.saturating_sub(baseline),
                    scope_limit,
                    window.prefill_input_tokens,
                )
            }
        };

    // The model's full context window is a hard cap, independent of the auto-compaction scope.
    let full_context_window_limit = model_info.resolved_context_window().map(|context_window| {
        context_window.saturating_mul(model_info.effective_context_window_percent) / 100
    });

    // Report remaining tokens against the base (unbuffered) window, capped by the full context.
    let base_window_tokens_remaining = [
        tokens_remaining(auto_compact_scope_limit, auto_compact_scope_tokens),
        tokens_remaining(full_context_window_limit, active_context_tokens),
    ]
    .into_iter()
    .flatten()
    .min();

    // Only reserve the fallback buffer when there is a fallback prompt to use it.
    let auto_compact_fallback_buffer_tokens = config
        .token_budget
        .as_ref()
        .map_or(0, crate::config::TokenBudgetConfig::fallback_buffer_tokens);
    let buffered_auto_compact_limit = auto_compact_scope_limit
        .map(|limit| limit.saturating_add(auto_compact_fallback_buffer_tokens));

    // Force compaction once the buffered window or the model's full context window is reached.
    let full_context_window_limit_reached =
        full_context_window_limit.is_some_and(|limit| active_context_tokens >= limit);
    let token_limit_reached = buffered_auto_compact_limit
        .is_some_and(|limit| auto_compact_scope_tokens >= limit)
        || full_context_window_limit_reached;

    ContextWindowTokenStatus {
        active_context_tokens,
        auto_compact_scope_tokens,
        auto_compact_scope_limit,
        full_context_window_limit,
        base_window_tokens_remaining,
        auto_compact_window_prefill_tokens,
        full_context_window_limit_reached,
        token_limit_reached,
    }

pub(super) fn resolve_token_budget(
    configured_token_budget: Option<&TokenBudgetConfig>,
    use_model_defaults: bool,
    model_info: &ModelInfo,
) -> Option<TokenBudgetConfig> {
    if !use_model_defaults {
        return configured_token_budget.cloned();
    }

    let Some(model_defaults) = model_info
        .model_messages
        .as_ref()
        .and_then(|messages| messages.token_budget.as_ref())
    else {
        return configured_token_budget.cloned();
    };

    let token_budget = TokenBudgetConfig {
        use_history_notes_extension: configured_token_budget

        reminder_threshold_tokens: Some(model_defaults.reminder_threshold_tokens),
        reminder_message_template: model_defaults.reminder_message_template.clone(),
        guidance_message: Some(model_defaults.guidance_message.clone()),
        auto_compact_fallback_prompt: Some(model_defaults.auto_compact_fallback_prompt.clone()),
        auto_compact_fallback_buffer_tokens: Some(
            model_defaults.auto_compact_fallback_buffer_tokens,
        ),
    };

        tracing::warn!(
            model = %model_info.slug,
            %error,
            "ignoring invalid model-owned token-budget defaults"

        return configured_token_budget.cloned();

pub(super) async fn maybe_record(
    sess: &Session,
    turn_context: &TurnContext,
    base_window_tokens_remaining: Option<i64>,
    allow_auto_compact_fallback: bool,
) {
    if !turn_context.config.features.enabled(Feature::TokenBudget) {
        return;
    }
    let Some(base_window_tokens_remaining) = base_window_tokens_remaining else {
        return;
    };

    let Some(config) = turn_context.config.token_budget.as_ref() else {
        return;
    };

    if config
        .reminder_threshold_tokens
        .is_some_and(|threshold| base_window_tokens_remaining <= threshold)
    {
        let reminder_due = {
            let mut state = sess.state.lock().await;
            state.claim_token_budget_reminder()
        };
        if reminder_due {
            let response_item =
                ContextualUserFragment::into(crate::context::TokenBudgetReminder::new(
                    &config.reminder_message_template,
                    base_window_tokens_remaining,
                ));
            sess.record_conversation_items(turn_context, std::slice::from_ref(&response_item))
                .await;
        }
    }

    if !allow_auto_compact_fallback || base_window_tokens_remaining != 0 {
        return;
    }
    let Some(prompt) = config.auto_compact_fallback_prompt.as_deref() else {
        return;
    };

    let fallback_due = {
        let mut state = sess.state.lock().await;
        state.claim_auto_compact_fallback()
    };
    if !fallback_due {
        return;
    }

    let response_item =
        ContextualUserFragment::into(crate::context::AutoCompactFallbackPrompt::new(prompt));
    sess.record_conversation_items(turn_context, std::slice::from_ref(&response_item))
        .await;
}

pub(crate) fn trim_function_call_history_to_fit_context_window(
    history: &mut ContextManager,
    turn_context: &TurnContext,
    base_instructions: &BaseInstructions,
) -> (usize, i64) {
    let Some(context_window) = turn_context.model_context_window() else {
        return (0, 0);
    };
    // Keep the unclamped total so replacing an item cannot lose an overflow hidden by i64
    // saturation in the normal history estimator.
    let base_tokens =
        i128::try_from(approx_token_count(&base_instructions.text)).unwrap_or(i128::MAX);
    let original_items = history.annotated_items();
    let mut estimated_tokens = history_item_groups(original_items.iter().map(|item| &item.item))
        .map(|group| group.estimated_token_count())
        .fold(base_tokens, i128::saturating_add);
    let initial_estimated_tokens = i64::try_from(estimated_tokens).unwrap_or(i64::MAX);
    let mut rewritten_items = Vec::new();
    let mut consumed_items: usize = 0;

    for group in history_item_groups(original_items.iter().map(|item| &item.item))
        .collect::<Vec<_>>()
        .into_iter()
        .rev()
    {
        if i64::try_from(estimated_tokens).unwrap_or(i64::MAX) <= context_window {
            break;
        }
        let group_item_count = 1 + usize::from(group.attached_notice.is_some());
        let source_index = original_items
            .len()
            .saturating_sub(consumed_items.saturating_add(group_item_count));
        let Some(rewritten_item) = original_items
            .get(source_index)
            .and_then(rewritten_output_for_context_window)
        else {
            break;
        };
        estimated_tokens = estimated_tokens
            .saturating_sub(group.estimated_token_count())
            .saturating_add(i128::from(estimate_item_token_count(&rewritten_item.item)));
        consumed_items += group_item_count;
        rewritten_items.push(rewritten_item);
    }

    let rewritten_outputs = rewritten_items.len();
    if rewritten_outputs > 0 {
        let retained_len = original_items.len() - consumed_items;
        let mut items = original_items[..retained_len].to_vec();
        items.extend(rewritten_items.into_iter().rev());
        history.replace_annotated(items);
    }

    let final_estimated_tokens = i64::try_from(estimated_tokens).unwrap_or(i64::MAX);
    let estimated_deleted_tokens = initial_estimated_tokens.saturating_sub(final_estimated_tokens);
    (rewritten_outputs, estimated_deleted_tokens)
}

## Q4
项目是否实现滑动窗口、历史摘要、工具结果截断和按需加载？分别在哪里触发，处理什么信息，依据消息条数、token 数还是其他条件？请追踪一次处理前后的上下文变化，说明原始内容是否仍可重新读取。
### Answer
## 直接回答

这四种机制在代码里都能找到对应实现，但强度和"是否可恢复"各不相同：

| 机制 | 是否实现 | 触发依据 | 原始内容可恢复? |
|---|---|---|---|
| 滑动窗口（context window rollover） | ✅ `start_new_context_window` | token 数（`token_limit_reached`/显式 `new_context` 工具调用） | 内存中的旧历史被整体替换，不可从当前 `ContextManager` 直接读回，但压缩前的原始条目理论上仍留在 rollout 持久化日志中 |
| 历史摘要（compaction） | ✅ `compact.rs`/`compact_remote.rs` | token 数（`auto_compact_token_limit`/`token_limit_reached`） | 摘要替换了大部分历史，仅保留有限的最近用户消息；原始条目不在新的内存历史里，但 rollout 日志里的 `RolloutItem::Compacted` 记录了 replacement 关系，可用于重放 |
| 工具结果截断 | ✅ 两处：写入时按 `TruncationPolicy`；压缩前按 `trim_function_call_history_to_fit_context_window` | token 数/字节数（`TruncationPolicy::Tokens`），压缩场景下依据剩余上下文窗口大小 | 写入时截断是永久性的（原始未截断内容不会保留在历史里）；压缩前截断只作用于**克隆**出来的历史副本，不影响真实会话历史 |
| 按需加载 | ⚠️ 未找到明确证据 | — | — |

---

## 详细说明

### 1. 滑动窗口：`start_new_context_window`

当 `token_limit_reached`（软阈值超限）或显式请求新上下文（`take_new_context_window_request`）时，`run_turn` 循环触发 `should_roll_over`，调用 `run_auto_compact`，其中一种效果是整体替换历史为一批全新的初始上下文条目 codex:4207-4258 。这不是传统意义上"逐步滑出旧消息"的滑动窗口，而是**整窗替换**：`build_initial_context_with_world_state` 重新生成环境/指令等基础条目，再加上可选保留的客户端 developer 消息，通过 `replace_compacted_history` 一次性替换掉 `ContextManager` 里的全部条目 codex:4230-4256 。触发条件是 token 数，而非消息条数。

判断是否触发 rollover 的逻辑在 `run_turn` 中：`should_roll_over = needs_follow_up && (sess.take_new_context_window_request().await || token_limit_reached)` codex:505-514 。

### 2. 历史摘要（Compaction）

**本地压缩**（`compact.rs`）：当上下文超限时，向历史注入 `SUMMARIZATION_PROMPT`，让模型生成摘要文本，再用 `build_compacted_history` 重建历史——只保留摘要 + 最近的、总量不超过 `COMPACT_USER_MESSAGE_MAX_TOKENS`（20,000 token）的用户消息 codex:670-715 。摘要构造完成后调用 `sess.replace_compacted_history(...)` 落地新历史 codex:387-400 。

**远程压缩**：类似,但摘要由远程压缩端点返回 `ResponseItem::Compaction`，随后同样走 `insert_initial_context_before_last_real_user_or_summary` + `replace_compacted_history` codex:266-313 。

触发条件是 token 数（`token_limit_reached`），不是消息条数。压缩后，原始完整历史不再存在于内存中的 `ContextManager`；但根据 `history.rs` 顶部的模块注释——"Compaction replaces only the model window... checkpoint replay and source-call rollback share their live lifecycle" codex:1-5 ——以及 rollout 重放逻辑里对 `RolloutItem::Compacted` 的处理（区分是否带 `replacement_history`，并在缺失时从头重建） codex:378-409 ，可以确认原始内容的血缘关系保存在持久化的 rollout 日志中，能够被重放/回滚恢复，但**当前活跃的内存历史（用于下一次模型请求）看不到原文**。

### 3. 工具结果截断

有两处独立的截断逻辑：

**(a) 记录时截断（永久性）**：`ContextManager` 在 `record_items`/`record_annotated_items` 时应用 `TruncationPolicy`（如 `TruncationPolicy::Tokens`），依据的是单条工具输出自身的 token/字节数，而非整体上下文占用 codex:50-54 。这类截断发生在工具结果**刚写入历史时**，一旦截断，未截断的原始内容不会留在会话历史里——这是一种不可逆的"每条目"降级。

pub(crate) fn trim_function_call_history_to_fit_context_window(
    history: &mut ContextManager,
    turn_context: &TurnContext,
    base_instructions: &BaseInstructions,
) -> (usize, i64) {
    let Some(context_window) = turn_context.model_context_window() else {
        return (0, 0);
    };
    // Keep the unclamped total so replacing an item cannot lose an overflow hidden by i64
    // saturation in the normal history estimator.
    let base_tokens =
        i128::try_from(approx_token_count(&base_instructions.text)).unwrap_or(i128::MAX);
    let original_items = history.annotated_items();
    let mut estimated_tokens = history_item_groups(original_items.iter().map(|item| &item.item))
        .map(|group| group.estimated_token_count())
        .fold(base_tokens, i128::saturating_add);
    let initial_estimated_tokens = i64::try_from(estimated_tokens).unwrap_or(i64::MAX);
    let mut rewritten_items = Vec::new();
    let mut consumed_items: usize = 0;

    for group in history_item_groups(original_items.iter().map(|item| &item.item))
        .collect::<Vec<_>>()
        .into_iter()
        .rev()
    {
        if i64::try_from(estimated_tokens).unwrap_or(i64::MAX) <= context_window {
            break;
        }
        let group_item_count = 1 + usize::from(group.attached_notice.is_some());
        let source_index = original_items
            .len()
            .saturating_sub(consumed_items.saturating_add(group_item_count));
        let Some(rewritten_item) = original_items
            .get(source_index)
            .and_then(rewritten_output_for_context_window)
        else {
            break;
        };
        estimated_tokens = estimated_tokens
            .saturating_sub(group.estimated_token_count())
            .saturating_add(i128::from(estimate_item_token_count(&rewritten_item.item)));
        consumed_items += group_item_count;
        rewritten_items.push(rewritten_item);
    }

    let rewritten_outputs = rewritten_items.len();
    if rewritten_outputs > 0 {
        let retained_len = original_items.len() - consumed_items;
        let mut items = original_items[..retained_len].to_vec();
        items.extend(rewritten_items.into_iter().rev());
        history.replace_annotated(items);
    }

    let final_estimated_tokens = i64::try_from(estimated_tokens).unwrap_or(i64::MAX);
    let estimated_deleted_tokens = initial_estimated_tokens.saturating_sub(final_estimated_tokens);
    (rewritten_outputs, estimated_deleted_tokens)
}

## 直接回答

在检索到的代码范围内，只有两类状态是**独立的结构化字段**：**任务目标（goal）**通过 app-server 的 `thread/goal/*` RPC 持久化 codex:204-208 ；**计划/已完成/待办**通过 `plan` item（`PlanItem`，`{step, status}` 数组）结构化存储，由模型调用 `update_plan` 工具驱动，并通过 `turn/plan/updated` 事件广播 codex:1876-1876 codex:1894-1894 。而**有效约束、阻塞原因、产出位置**在已检索的代码中**没有找到专门的独立字段**，它们更可能是从聊天历史/条目状态中隐式推断出来的（例如 AGENTS.md 内容、`commandExecution`/`fileChange` 条目的 `status`/`path`）。

---

## 详细说明

### 1. 任务目标（Goal）——独立结构化字段

app-server 提供专门的 RPC 管理"目标"：
- `thread/goal/set` — 为线程创建/更新一个持久化的 goal，返回当前 goal 并广播 `thread/goal/updated`
- `thread/goal/get` — 读取当前持久化 goal
- `thread/goal/clear` — 清除 goal，广播 `thread/goal/cleared` codex:204-208 

这说明 goal 是**由客户端/用户通过显式 RPC 调用更新**的（而不是模型自主更新），并且"每个 materialized thread 只有一个 goal"。它作为持久化状态存在（很可能落在 SQLite 类似结构），但在已检索片段中我没有找到它如何具体被序列化进 `Prompt.input` 的代码路径——这点需要进一步查看 `thread_goal`/`state_db` 相关实现才能确认它如何进入下一轮模型请求。

### 2. 计划、已完成步骤、待办事项——独立结构化字段（`PlanItem`）

`turn/plan/updated` 事件的 payload 是 `{ turnId, explanation?, plan }`，其中 `plan` 是一组 `{ step, status }`，`status` 取值 `pending`/`inProgress`/`completed` codex:1876-1876 。对应的 `plan` item 类型为 `{id, text}`，支持流式增量 `item/plan/delta` codex:1894-1894 。

这套结构由系统提示中明确规定的 `update_plan` 工具驱动：模型被要求维护"精确一个 in_progress 步骤"，标记完成、变更计划时都要调用 `update_plan`（见 GPT-5.1/5.2 提示词） codex:36-46 codex:63-73 。核心引用 `codex_protocol::items::PlanItem` 出现在 `turn.rs` 的引入列表中 codex:88-88 ，说明它作为一种 `TurnItem` 参与 turn 的条目生命周期（`item/started` → `item/completed`）。

**更新者与触发事件**：模型通过函数调用（`update_plan` 工具调用）主动更新，这本身就是一次工具执行（对应我们此前讨论的"工具分发"路径 codex:772-797 ）。工具调用及其输出会作为普通 `FunctionCall`/`FunctionCallOutput` 写入会话历史（`ResponseItem`），因此计划状态是**通过常规的历史累积机制**自然进入下一轮模型请求的 `input`（即此前讨论的 `sess.clone_history().await.for_prompt(...)` 路径 codex:416-424 ），而不需要额外的注入逻辑。

### 3. 有效约束、阻塞原因、产出位置——未找到独立字段

在已检索的上下文中：
- **约束（constraints）**：没有发现专门的"约束"字段结构。已知与"约束"语义接近的是 AGENTS.md 规则（系统提示中明确说明其作用域和优先级规则），以及 turn 的 `sandboxPolicy`/`permissions` 设置——但这些是配置/系统提示层面的内容，不是任务级"约束"独立存储结构。
- **阻塞原因（blocking reason）**：`commandExecution`、`fileChange` 等 item 有 `status` 字段（`inProgress`/`completed`/`failed`/`declined`），可以反映"被拒绝/失败"，但没有看到统一的"阻塞原因"字段；这更像是从各条目的 `status`/`error` 中推断的。
- **产出位置（output location）**：`fileChange` item 携带 `changes[].path` codex:1898-1898 ，这是离散的、按次操作记录的路径信息，而不是一个统一的"产出位置"字段。

这几类状态更符合"只能从聊天历史/条目集合中推断"的类别，而非专门的结构化持久字段。

## Q6
请分别找出当前模型上下文、会话历史持久化、任务状态和跨会话记忆的实现。如果项目声称支持长期记忆，请追踪一条信息如何被写入、在未来另一个任务中被检索，并实际进入模型请求。只有存储没有读取使用的部分，请单独标明。
### Answer
## 直接回答

四类状态分别对应不同子系统：**当前模型上下文**由 `ContextManager`（内存态历史 + `for_prompt` 序列化）承担；**会话历史持久化**由 Rollout 机制（JSONL 落盘 + `RolloutItem` 重放）承担；**任务状态**是 goal（`thread/goal/*` RPC）与 plan（`PlanItem`/`update_plan` 工具）两个结构化字段，其余靠历史推断；**跨会话记忆**由独立的 `codex-rs/ext/memories`（读路径，作为 `ContextContributor` 向 prompt 注入）与 `codex-rs/memories/write`（写路径，后台 Phase 1/2 流水线生成 `MEMORY.md`/`memory_summary.md`）共同实现——这是一条"写入 → 未来任务检索 → 进入模型请求"的完整闭环，而非只存不读。

---

## 详细说明

### 1. 当前模型上下文（Current Model Context）

`ContextManager`（`codex-rs/core/src/context_manager/history.rs`）是内存中的活跃历史容器，其模块注释明确说明"Compaction replaces only the model window"，即它就是"当前模型上下文"的载体 codex:1-5 。该结构持有 `items: Arc<Vec<ResponseItemEnvelope>>`、`retained_context`、`token_info` 等字段 codex:60-90 。每轮通过 `sess.clone_history().await.for_prompt(...)` 序列化为 `Vec<ResponseItem>` 进入请求（前几轮已详细讨论过） codex:416-424 。

### 2. 会话历史持久化（Rollout）

持久化落在 Rollout 层：`codex-rs/rollout/src/model_context.rs` 定义了从持久化 JSONL 反向扫描重建"最新模型上下文"的逻辑（`ModelContextScanProgress`，直到看到 `CompactedItem`+`replacement_history` 或兼容的 `TurnContextItem`） codex:9-30 。测试用例证实了这条路径：`load_latest_model_context` 从磁盘读取历史，再通过 `resume_thread_with_history`/`InitialHistory::Resumed` 恢复到内存 `ContextManager` codex:150-182 ，甚至支持压缩后的 rollout 文件（`.jsonl.zst`）恢复 codex:159-194 。这就是"会话历史持久化"的实现与验证。

### 3. 任务状态（Goal / Plan）

同前几轮讨论：goal 通过 app-server 的 `thread/goal/set|get|clear` 持久化 codex:204-208 ；plan 通过 `PlanItem`/`update_plan` 工具驱动，随普通历史机制进入下一轮请求 codex:88-88 。这两者是本次检索范围内仅有的独立结构化任务状态字段。

### 4. 跨会话记忆（Cross-Session Memory）：写入 → 检索 → 进入请求 的完整闭环

这是本项目**明确声称支持长期记忆**的子系统，分为写路径和读路径两个独立 crate：

#### (a) 写入：Phase 1 + Phase 2 流水线

`codex-rs/memories/README.md` 说明：当根会话启动、非临时会话、记忆功能开启、非子代理会话、且 state DB 可用时，后台异步触发两阶段流水线 codex:29-38 ：
- **Phase 1（Rollout Extraction）**：从 state DB 按启动认领规则挑选闲置足够久的历史 rollout，过滤出记忆相关的 `ResponseItem`，发送给模型并行提炼出 `raw_memory` + `rollout_summary` codex:40-60 。
- **Phase 2（Consolidation）**：一个"Memory Writing Agent"读取 `raw_memories.md`、既有 `MEMORY.md`、`rollout_summaries/*.md`，将新证据合并进持久化的 `MEMORY.md`（操作手册条目）与 `memory_summary.md`（始终加载进系统提示的稠密索引，首行必须是 `v1`） codex:20-27 。这一步明确写道"Always loaded into the system prompt" codex:20-24 ，这正是"写入的信息如何最终进入模型请求"的关键证据。

驱动这一流程的运行时上下文构造在 `codex-rs/memories/write/src/runtime.rs` 中，例如 `stage_one_request_context` 为 Phase 1 组装模型调用所需的 `model_info`、`reasoning_effort` 等 codex:209-239 。

#### (b) 检索/注入：读路径

`codex-rs/memories/read/src/lib.rs` 是读路径的入口 crate,明确定位 `memory_root`（`CODEX_HOME/memories`）目录,并声明自己"owns memory injection, memory citation parsing, and telemetry classification...does not depend on the memory write pipeline" codex:1-14 。

实际把记忆内容"塞进"模型请求的是 `codex-rs/ext/memories` 扩展：`MemoriesExtension` 实现了 `ContextContributor`（同时也是 `ConfigContributor`/`ToolContributor`/`ThreadLifecycleContributor`），并通过 `build_memory_tool_developer_instructions` 构造 developer-message 形式的 prompt fragment codex:1-26 。作为 `ContextContributor`,它的职责就是往每轮的 `Prompt` 里注入内容——这与我们此前讨论的“系统提示/历史消息进入 `Prompt.input`”是同一条通路,只是发起方是记忆扩展而非 `Session` 自身。

除了被动注入的 `memory_summary.md` 摘要,模型还能**主动检索**更详细的记忆:`codex-rs/ext/memories/src/tools/` 下有 `search.rs`、`read.rs`、`list.rs` 三个工具模块,以及用于写入的 `ad_hoc_note.rs`(临时笔记工具)。这些工具走的正是前几轮讨论过的标准工具分发路径(`registry.rs` 的 `handle_any_tool`),其输出作为 `FunctionCallOutput` 写入历史,并随下一次 `for_prompt` 进入模型请求——也就是说,记忆的"主动检索"结果最终汇入的仍是 `ContextManager` 这条主干通道,而不是另开一条独立管道。

`record_completed_response_item_with_finalized_facts` 里可以看到读路径与历史记录的耦合点:处理完成的响应条目时,会尝试检测/记录"memory citation"(`record_stage1_output_usage_for_memory_citation`/`record_stage1_output_usage_and_detect_memory_citation`),并在检测到引用时调用 `sess.record_memory_citation_for_turn` codex:92-130 。这证明系统确实在追踪"模型是否真的使用了被注入/检索到的记忆内容"，是"写入→检索→在下一轮任务中被使用"这条闭环里的使用侧遥测证据。

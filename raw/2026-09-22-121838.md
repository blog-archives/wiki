# DeepWiki Q&A with Code Context for Repository: openai/codex
## Q1
模型调用超时的处理方式
### Answer
## 回答

在 codex 代码库中，"模型调用超时"涉及几个不同的子系统，处理方式各不相同：

---

### 1. 模型列表/元数据获取超时（Models Manager）

当从远程 `/models` 端点获取模型列表超时（默认约 5 秒）时，`ModelsManager.get_default_model` 会直接超时并回退到内置的默认模型（`bundled_default_model_slug()`），而不会阻塞调用方： codex:1263-1311 

测试断言超时发生在约 4.5s~5.8s 之间，并且最终返回内置默认模型 slug，而不是抛出错误。

---

### 2. Code Mode 中 JS 执行 `wait` 超时

在 Code Mode（JS REPL 执行系统）中，如果宿主端在等待一个 yield 出去的 cell 恢复时超时，会把超时信息作为工具调用结果返回给模型（而不是让整个 turn 失败），并允许下一次 `exec` 重新连接： codex:2247-2340 

测试中可以看到超时输出会包含 `"code-mode host timed out waiting for wait response"` 文本，随后模型可以再次发起 `exec` 来重连 codex:2333-2360 。

---

### 3. 模型请求失败（含超时相关错误码）时的重试/降级

`should_retry_with_current_model` 判断某些 `CodexErr`（如 `ServerOverloaded`、`InternalServerError`、`RetryLimit` 等）是否属于"模型特定错误，值得用同一模型重试"，并配合 `record_model_fallback` 记录遥测和日志，说明系统在压缩/请求失败时会尝试用当前模型重试或降级： codex:8-20 codex:22-63 

同时 TUI 也会向用户展示提示，例如当响应耗时较长时弹出"是否切换到更快模型"的提示框： codex:1-14 

---

### 4. Guardian 子代理（Auto-Review）超时

如果是指自动审批 Guardian 子代理调用超时（`GUARDIAN_REVIEW_TIMEOUT`，见 Resume/Review Commands 相关系统），会生成专门的超时提示信息，区分"超时"和"策略拒绝"两种情形，并可能包含模型自定义的 `timeout_instructions`： codex:1729-1753 

## Notes

- 以上四个子系统（Models Manager 的远程拉取超时、Code Mode 的 wait 超时、模型请求错误重试/降级、Guardian 审查超时)是代码库中与"模型调用超时"相关但彼此独立的机制,具体你指的是哪一种,可以进一步说明以便我给出更精准的定位。

            | CodexErrorDetails::UsageLimitReached(_)

## Q2
就是指模型请求失败的一系列处理方式
### Answer
## 回答

你问的是模型请求失败时的一系列处理方式，这主要体现在错误分类（`CodexErrorDetails`）、传输层到业务错误的映射（`api_bridge.rs`）、以及重试/降级逻辑（`compact_model_fallback.rs` 和 `client.rs` 中的重试机制）。

---

### 1. 错误分类：`CodexErrorDetails`

所有模型调用失败都会被归类为 `CodexErrorDetails` 枚举的某个变体,包括超时(`RequestTimeout`)、流断开(`Stream`)、限流(`RateLimitExceeded`)、上下文超限(`ContextWindowExceeded`)、服务过载(`ServerOverloaded`)、内部错误(`InternalServerError`)、重试耗尽(`RetryLimit`)等： codex:93-158 

这个错误随后会被转换为客户端可见的 `CodexErrorInfo`，用于 TUI/前端展示： codex:431-464 

---

### 2. 传输层错误 → 业务错误映射（`codex-api`）

`codex-api` 的 `api_bridge.rs` 负责把 HTTP 状态码、SSE 报错和底层传输错误（`TransportError`）翻译成 `CodexErr`：

- `TransportError::Timeout` → `CodexErr::RequestTimeout`
- `TransportError::RetryLimit` → `CodexErr::RetryLimit`
- HTTP 429 + `usage_limit_reached` → `CodexErr::UsageLimitReached`
- HTTP 500 → `CodexErr::InternalServerError`
- 其他非预期状态码 → `CodexErr::UnexpectedStatus` codex:131-197 

---

### 3. 重试/降级策略

`should_retry_with_current_model` 判断某类错误（`InvalidRequest`、`UnexpectedStatus`、`ContextWindowExceeded`、`UsageLimitReached`、`ServerOverloaded`、`InternalServerError`、`RetryLimit`）是否值得用同一模型重试，主要用于压缩流程的模型降级重试： codex:8-20 

失败或成功都会记录遥测和日志： codex:22-63 

---

### 4. 实际重试行为（HTTP vs 流式 vs WebSocket）

集成测试 `retry_after.rs` 展示了不同层级、不同错误类型下的具体重试策略：

- **HTTP 层过载(503)**：按本地退避重试（`request_max_retries` 次数），忽略上游 `Retry-After` 头，超出次数后才终止并抛出 `ServerOverloaded` 错误： codex:348-417 

- **流式(SSE)限流**：按 `stream_max_retries` 重试，若响应体中带有精确的重试延时消息（如"Please try again in 1s"），会采用该延时而不是本地默认退避： codex:1070-1121 

- **流式过载是终态,不重试**：一旦在 SSE 流中出现 `server_is_overloaded`，无论是否带 `Retry-After` 头，都被视为终态错误，直接结束 turn，不会重试： codex:1179-1250 

- **WebSocket 过载同样是终态**，且不会像连接失败那样降级回退到 HTTP 传输（`fallback_warning_events` 断言为 0）： codex:1606-1687 

---

## Notes

- 之前提到的 Models Manager 拉取超时、Code Mode `wait` 超时、Guardian 审查超时属于各自独立的子系统,与这里讨论的"模型请求失败重试/降级"机制不是同一套代码路径,不再赘述。
- `retry_after.rs` 里带 `TODO(anp) respect Retry-After` 注释的用例表明,目前 Codex 在部分场景下尚未完全遵循上游服务器返回的 `Retry-After` 头部,而是采用固定的本地退避策略,这是当前已知的一个设计取舍/待办项 codex:244-247 。

## Q3
错误分类具体有哪些内容
### Answer
## 答案

错误分类的核心是 `CodexErrorDetails` 枚举，定义在 `codex-rs/protocol/src/error.rs`。它列出了所有模型请求可能失败的语义类别：

---

### `CodexErrorDetails` 完整变体列表

| 变体 | 含义 |
|---|---|
| `TurnAborted` | turn 被中止 |
| `SessionBudgetExceeded` | 共享 rollout token 预算耗尽 |
| `Stream(String)` | SSE 流在完成前断开(可重试) |
| `RateLimitExceeded(String)` | 流内收到的可重试限流 |
| `ContextWindowExceeded` | 上下文窗口耗尽 |
| `ThreadNotFound(ThreadId)` | 找不到指定 thread |
| `AgentLimitReached` | agent thread 数量达到上限 |
| `SessionConfiguredNotFirstEvent` | session-configured 事件不是流中第一个事件 |
| `Timeout` | 子进程执行超时(10s) |
| `RequestTimeout` | 请求本身超时 |
| `Spawn` | 子进程 spawn 失败 |
| `Interrupted` | 用户 Ctrl-C 中断 |
| `UnexpectedStatus(UnexpectedResponseError)` | 未预期的 HTTP 状态码 |
| `InvalidRequest(String)` | 无效请求 |
| `ToolCollision(String)` | 多个工具重名 |
| `InvalidImageRequest()` | 图片投毒/无效图片 |
| `UsageLimitReached(UsageLimitReachedError)` | 使用额度达到上限 |
| `ServerOverloaded` | 模型服务过载 |
| `CyberPolicy { message }` | 触发网络安全策略 |
| `MisalignmentPolicyViolation { message, misalignment }` | 触发对齐策略违规 |
| `ResponseStreamFailed(ResponseStreamFailed)` | 响应流失败 |
| `ConnectionFailed(ConnectionFailedError)` | 连接失败 |
| `QuotaExceeded` | 配额超限 |
| `UsageNotIncluded` | 当前套餐不包含此用量,需升级 |
| `InternalServerError` | 服务端内部错误(高需求导致) |
| `RetryLimit(RetryLimitReachedError)` | 重试次数耗尽 |
| `InternalAgentDied` | agent loop 意外死亡 |
| `Sandbox(SandboxErr)` | 沙箱错误 |
| `LandlockSandboxExecutableNotProvided` | 缺少 landlock sandbox 可执行文件 |
| `UnsupportedOperation(String)` | 不支持的操作 |
| `RefreshTokenFailed(RefreshTokenFailedError)` | token 刷新失败 |
| `Fatal(String)` | 致命错误 |
| `Io` / `Json` / `TokioJoin` / `EnvVar` 等 | 外部错误类型的自动转换(IO、JSON 解析、tokio join、环境变量) | codex:82-190 

---

### 每个变体是否可重试：`is_retryable`

`CodexErr::is_retryable` 方法把上述变体分成两组:

- **不可重试**(直接终止 turn): `TurnAborted`、`SessionBudgetExceeded`、`Interrupted`、`EnvVar`、`Fatal`、`UsageNotIncluded`、`QuotaExceeded`、`InvalidImageRequest`、`InvalidRequest`、`ToolCollision`、`RefreshTokenFailed`、`UnsupportedOperation`、`Sandbox`、`LandlockSandboxExecutableNotProvided`、`RetryLimit`、`ContextWindowExceeded`、`ThreadNotFound`、`AgentLimitReached`、`Spawn`、`SessionConfiguredNotFirstEvent`、`UsageLimitReached`、`ServerOverloaded`、`CyberPolicy`、`MisalignmentPolicyViolation`
- **可重试**(传输/瞬时性错误): `Stream`、`RateLimitExceeded`、`Timeout`、`RequestTimeout`、`UnexpectedStatus`、`ResponseStreamFailed`、`ConnectionFailed`、`InternalServerError`、`InternalAgentDied`、`Io`、`Json`、`TokioJoin` codex:371-412 

注意这里有些细微差异:例如 `ServerOverloaded`、`RetryLimit`、`UsageLimitReached`、`ContextWindowExceeded` 在 `is_retryable` 中被标记为**不可重试**,但在之前讨论的 `should_retry_with_current_model` 中却被认为"值得用同一模型重试" codex:8-20 ——这两者语义不同:`is_retryable` 是关于"是否值得对同一次请求做底层传输重试",而 `should_retry_with_current_model` 是关于"压缩失败后是否值得用当前模型重新尝试整个压缩流程"。

---

### 转换为客户端可见错误:`to_codex_protocol_error`

`CodexErr::to_codex_protocol_error` 把内部详细错误映射为对外暴露的 `CodexErrorInfo`(驼峰式,供 TUI/app-server 协议使用):

- `ContextWindowExceeded` → `ContextWindowExceeded`
- `SessionBudgetExceeded` → `SessionBudgetExceeded`
- `RateLimitExceeded` → `RateLimitExceeded`
- `UsageLimitReached` / `QuotaExceeded` / `UsageNotIncluded` → 统一归为 `UsageLimitExceeded`
- `ServerOverloaded` → `ServerOverloaded`
- `CyberPolicy` → `CyberPolicy`
- `MisalignmentPolicyViolation` → `MisalignmentPolicyViolation`
- `RetryLimit` → `ResponseTooManyFailedAttempts { http_status_code }`
- `ConnectionFailed` → `HttpConnectionFailed { http_status_code }`
- `ResponseStreamFailed` → `ResponseStreamConnectionFailed { http_status_code }`
- `RefreshTokenFailed` → `Unauthorized`
- `SessionConfiguredNotFirstEvent` / `InternalServerError` / `InternalAgentDied` → 统一归为 `InternalServerError`
- `UnsupportedOperation` / `ThreadNotFound` / `AgentLimitReached` → 统一归为 `BadRequest`
- `Sandbox` → `SandboxError`
- 其他所有未列出的变体 → `Other` codex:431-464 

这个 `CodexErrorInfo` 枚举本身在 app-server protocol schema 中定义,以驼峰命名对外暴露给 IDE 客户端,例如 `contextWindowExceeded`、`serverOverloaded`、`internalServerError` 等 codex:135-178 。

---

### 上游产生这些错误的位置

在 `codex-api` 的 `api_bridge.rs` 中,`map_api_error` 和 HTTP/传输层错误映射逻辑负责把底层 HTTP 状态码、SSE 报错体、`TransportError` 转换为具体的 `CodexErrorDetails` 变体,例如 429+`usage_limit_reached` → `UsageLimitReached`,500 → `InternalServerError`,`TransportError::Timeout` → `RequestTimeout` 等 codex:21-65 codex:131-197 。

## Notes

- 目前看到的 `is_retryable` 与 `should_retry_with_current_model` 是两套独立判定逻辑,服务于不同场景(底层传输重试 vs. 压缩流程模型降级重试),不要混淆。
- `CodexErrorInfo` 是对外协议层的精简/归并版本,不是 `CodexErrorDetails` 的一一映射,很多内部细分错误在对外展示时会被合并为 `Other` 或更宽泛的类别。

## Q4
什么样的错误是可以重试的
### Answer
## 答案

可重试的错误由 `CodexErr::is_retryable` 方法定义,判断依据是 `CodexErrorDetails` 的具体变体： codex:397-408 

**可重试的错误类型：**

| 变体 | 含义 |
|---|---|
| `Stream(String)` | SSE 流在完成前断开 |
| `RateLimitExceeded(String)` | 流内可重试限流 |
| `Timeout` | 子进程超时(10s) |
| `RequestTimeout` | 请求本身超时 |
| `UnexpectedStatus(_)` | 未预期的 HTTP 状态码 |
| `ResponseStreamFailed(_)` | 响应流失败 |
| `ConnectionFailed(_)` | 连接失败 |
| `InternalServerError` | 服务端内部错误(高需求) |
| `InternalAgentDied` | agent loop 意外死亡 |
| `Io(_)` / `Json(_)` / `TokioJoin(_)` | IO、JSON 解析、tokio join 等外部错误 |

---

## 详细说明

### 判定逻辑

`is_retryable` 把所有 `CodexErrorDetails` 变体分成两组,凡不在下面"不可重试"列表中、且属于传输/流式/内部瞬时性质的错误都返回 `true`： codex:371-412 

**不可重试的错误**(直接终止 turn,不做底层传输重试)：`TurnAborted`、`SessionBudgetExceeded`、`Interrupted`、`EnvVar`、`Fatal`、`UsageNotIncluded`、`QuotaExceeded`、`InvalidImageRequest`、`InvalidRequest`、`ToolCollision`、`RefreshTokenFailed`、`UnsupportedOperation`、`Sandbox`、`LandlockSandboxExecutableNotProvided`、`RetryLimit`、`ContextWindowExceeded`、`ThreadNotFound`、`AgentLimitReached`、`Spawn`、`SessionConfiguredNotFirstEvent`、`UsageLimitReached`、`ServerOverloaded`、`CyberPolicy`、`MisalignmentPolicyViolation`。

### 上游产生这些可重试错误的位置

在 `codex-api` 的 `api_bridge.rs` 中,传输层错误被映射为这些可重试的 `CodexErr` 变体，例如 `TransportError::Timeout` → `CodexErr::RequestTimeout`，`TransportError::Connection` → `CodexErr::ConnectionFailed`： codex:185-194 

而 HTTP 500 会被映射为 `CodexErr::InternalServerError`： codex:131-132 

### 单元测试验证

`error_tests.rs` 中的 `retryability_preserves_error_details_distinctions` 测试直接验证了各类错误的可重试性,值得注意的是它展示了两个容易混淆的例子：`ServerOverloaded` 不可重试，但语义相近的 `RateLimitExceeded` 可重试；`RetryLimit`（重试次数已耗尽）不可重试，但泛化的 `UnexpectedStatus`（同样是 429 状态码）却可重试，`InternalServerError` 也可重试： codex:35-77 

### 重试延时（`retry_delay`）

部分可重试错误（如 `Stream`、`RateLimitExceeded`）在构造时可以携带服务器建议的重试延时，通过 `with_retry_delay` 附加，供上层重试逻辑使用具体延时而非默认退避： codex:26-39 ，测试 `map_api_error_preserves_retry_delay` 验证了这一行为： codex:13-51 

## Notes

- 需要注意 `is_retryable`（是否值得对同一次请求做底层传输重试）与之前提到的 `should_retry_with_current_model`（压缩失败后是否值得用当前模型重试整个压缩流程）是两套独立判定逻辑,语义不同，不要混淆——例如 `ServerOverloaded`、`ContextWindowExceeded`、`UsageLimitReached`、`RetryLimit` 在 `is_retryable` 中为不可重试,但在 `should_retry_with_current_model` 中被认为值得换个思路重试。
- `is_retryable` 目前未直接体现"重试次数上限"或"具体退避策略"，这部分逻辑在更上层的重试循环（未在当前索引片段中完整展示）中实现。

## Q5
重试和降级的具体条件是什么
### Answer
## 答案

Codex 的"重试"和"降级"分为两套独立机制，分别作用于不同层级：**流式请求重试**（`handle_retryable_response_stream_error`）和**压缩流程的模型降级重试**（`should_retry_with_current_model`）。

---

### 1. 请求级重试：`handle_retryable_response_stream_error`

只有当 `err.is_retryable()` 为 `true` 时才会进入这个重试循环(在 `run_turn` 主循环中先判断,不可重试则直接终止 turn)： codex:1495-1513 

具体重试条件按优先级依次是：

1. **无限连接重试**：若开启 `Feature::UnboundedConnectionRetries` 特性,且是采样(Sampling)请求,且错误是 `ConnectionFailed`,且非内部会话来源,且 provider 不是 Amazon Bedrock,则无限次按指数退避重试(初始延时 `INITIAL_CONNECTION_RETRY_DELAY`,每次翻倍,上限 `MAX_CONNECTION_RETRY_DELAY`)： codex:58-83 

2. **WebSocket → HTTPS 传输降级**：若重试次数已达到 `max_retries`(由 `provider.info().stream_max_retries()` 配置)且 `client_session.try_switch_fallback_transport` 成功,则从 WebSocket 降级到 HTTPS,并重置重试计数： codex:85-100 

3. **常规按次数重试**：若重试次数 `< max_retries`,则按 `err.retry_delay()`(服务器建议的延时,如限流消息里的"retry in Ns")或本地 `backoff(retry_count)` 退避后重试： codex:102-126 

4. 若以上条件都不满足(重试次数耗尽且无法降级传输),则把错误原样返回,终止 turn: codex:128-128 

可重试的错误种类(`is_retryable() == true`)：`Stream`、`RateLimitExceeded`、`Timeout`、`RequestTimeout`、`UnexpectedStatus`、`ResponseStreamFailed`、`ConnectionFailed`、`InternalServerError`、`InternalAgentDied`、`Io`、`Json`、`TokioJoin`： codex:397-408 

---

### 2. 模型降级重试：`should_retry_with_current_model`

这是压缩(compaction)流程专用的判定,当用"上一个模型"做压缩失败时,判断是否值得改用"当前模型"重试。触发条件是错误详情属于以下之一：`InvalidRequest`、`UnexpectedStatus`、`ContextWindowExceeded`、`UsageLimitReached`、`ServerOverloaded`、`InternalServerError`、`RetryLimit`： codex:8-20 

无论成功还是失败,都会通过 `record_model_fallback` 记录遥测(`codex.compaction.model_fallback` counter,带 `reason`/`implementation`/`outcome` 标签)和日志： codex:22-63 

---

### 3. 具体错误类型在实际重试测试中的行为差异

| 场景 | 是否重试 | 依据 |
|---|---|---|
| HTTP 503 过载,无 `Retry-After` | 按本地退避重试(`request_max_retries`次),耗尽后终止 | codex:244-247  |
| SSE 流内 `server_is_overloaded` | **终态,不重试**(无论是否带 `Retry-After`) | codex:1252-1322  |
| SSE 流内限流,消息含具体延时(如"try again in 1s") | 按服务器建议延时重试(`stream_max_retries`次) | codex:1123-1176  |
| WebSocket 过载 | **终态,不重试,也不降级回 HTTP** | codex:1606-1687  |
| 压缩流程(Compact V2)本身失败 | 按本地退避重试,忽略上游 `Retry-After` | codex:419-489  |

## Notes

- `is_retryable`(单次请求的传输层重试资格)、`handle_retryable_response_stream_error` 里的具体循环条件(连接无限重试/传输降级/按次退避)、以及 `should_retry_with_current_model`(压缩流程的模型降级)是三层不同粒度的判定,彼此独立但共同构成"重试与降级"的整体机制。
- `retry_after.rs` 中多处标注 `TODO(anp) respect Retry-After`,说明目前部分场景(HTTP 503、压缩流程)尚未完全遵循上游 `Retry-After` 头,而是采用固定本地退避,这是已知的设计取舍。

## Q6
就算是重试，具体的做法有哪些
### Answer
## 答案

具体的重试"做法"（即真正执行的操作）都在 `handle_retryable_response_stream_error` 函数中，共有三种具体手段：

1. **原地 sleep 后重发请求**（最常见）
2. **无限指数退避重连**（仅限连接失败场景）
3. **切换传输协议（WebSocket → HTTPS）后重置计数继续重试**

---

## 详细做法

### 1. 常规按次重试：sleep + 重新进入循环

`try_run_sampling_request` 外层是一个 `loop`，出错后调用重试处理函数，只要返回 `Ok(())` 就重新走一遍 `loop` 顶部逻辑（重新构建 prompt、重新发起请求）： codex:1439-1513 

具体做法是：重试计数 `+1`，计算延时（优先用服务器建议的 `err.retry_delay()`，否则用本地 `backoff(retry_count)` 指数退避算法），打印日志，通过 `sess.notify_stream_error` 把"Reconnecting... N/M"消息推给前端 UI（避免用户以为卡死），记录遥测（`codex_client::record_retry!`），然后 `tokio::time::sleep(delay).await`，返回 `Ok(())`： codex:102-126 

值得注意的细节：为减少噪音，release 构建下会隐藏第一次 WebSocket 重试的提示消息（只有第 2 次及以后才展示），debug 构建则始终展示，这一行为在测试中被验证： codex:184-203 

### 2. 无限连接重试：指数退避,无次数上限

当满足特定条件（`Feature::UnboundedConnectionRetries` 开启 + 是采样请求 + 错误类型是 `ConnectionFailed` + 非内部会话 + provider 不是 Amazon Bedrock）时，走一条独立于 `max_retries` 计数的无限重试路径：延时从 `INITIAL_CONNECTION_RETRY_DELAY`(5秒) 开始，每次重试后翻倍，上限 `MAX_CONNECTION_RETRY_DELAY`(60秒)，通知用户"Reconnecting... waiting for network"，然后 sleep 并返回 `Ok(())` 继续循环： codex:17-18 codex:58-83 

集成测试验证了这一行为——网络连接失败的重试独立计数，不消耗常规的 stream 重试预算，延时按 5s → 10s 逐级增长： codex:1324-1394 

### 3. 传输降级：WebSocket → HTTPS

当常规重试次数已达到 `max_retries` 上限时，会先尝试调用 `client_session.try_switch_fallback_transport`，如果切换成功（说明当前用的是 WebSocket 且允许降级），则发出 `EventMsg::Warning`("Falling back from WebSockets to HTTPS transport")，把重试计数器清零，返回 `Ok(())` 用新传输方式继续走常规重试路径： codex:85-100 

但要注意：这个降级只对"重试次数耗尽"的普通错误生效；如果错误本身是**终态**错误（如 `ServerOverloaded`），根本不会进入这个重试函数，因此也不会触发降级——测试明确验证了 WebSocket 过载不会降级回 HTTP（`fallback_warning_events` 断言为 0）： codex:1689-1768 

### 4. 重试耗尽后：直接放弃

以上三种手段都不满足条件时（常规重试次数用尽，且传输降级也不可行/已经用过），函数返回 `Err(err)`，把错误原样抛给调用者，`try_run_sampling_request` 的 loop 因此终止,整个 turn 以该错误结束： codex:128-128 

---

## 汇总表

| 做法 | 触发条件 | 具体操作 | 计数影响 |
|---|---|---|---|
| 无限连接重试 | Feature 开启 + Sampling + `ConnectionFailed` + 非内部会话 + 非 Bedrock | sleep(指数退避 5s→60s) 后重试 | 不消耗 `retries` 计数,单独计数 `connection_retries` |
| 传输降级 | `retries >= max_retries` 且可切换 fallback transport | WS→HTTPS,发警告事件,`retries`清零 | 重置为 0 |
| 常规按次重试 | `retries < max_retries` | sleep(`retry_delay()`或`backoff()`) 后重试,通知UI | `retries += 1` |
| 放弃/终止 | 以上都不满足 | 直接 `Err(err)` 返回,turn 失败 | — |

## Notes

- 这四种做法都发生在同一个函数 `handle_retryable_response_stream_error` 内，按上表顺序依次判断（if-else if 链式结构），彼此互斥。
- 之前讨论的"是否可重试"(`is_retryable()`) 是进入这整个流程的前置门槛：只有 `is_retryable() == true` 的错误才会调用这个函数，否则直接终止 codex:1499-1501 。
- 压缩流程的 `should_retry_with_current_model`（模型降级）是完全独立的另一套机制，不涉及本回答中描述的这几种"请求级重试"手段。

/// Headerless websocket overloads must neither reconnect nor fall back to HTTP.
#[tokio::test(flavor = "current_thread")]
async fn websocket_overload_without_retry_after_is_terminal() -> Result<()> {
    skip_if_no_network!(Ok(()));

    let mut telemetry = RetryTelemetryCapture::install();
    let server = responses::start_websocket_server(vec![vec![
        vec![
            responses::ev_response_created("prewarm"),
            responses::ev_completed("prewarm"),
        ],
        vec![json!({
            "type": "error",
            "status": 503,
            "error": {
                "code": "server_is_overloaded",
                "message": "This model is disabled."
            }
        })],
    ]])
    .await;
    let test = test_codex()
        .with_config(|config| {
            config.model_provider.request_max_retries = Some(2);
            config.model_provider.stream_max_retries = Some(2);
        })
        .build_with_websocket_server(&server)
        .await?;

    submit_user_input(&test, "reject the websocket overload").await?;

    let mut error_events = 0;
    let mut stream_error_events = 0;
    let mut fallback_warning_events = 0;
    loop {
        match wait_for_event(&test.codex, |_| true).await {
            EventMsg::Error(error) => {
                error_events += 1;
                assert_eq!(
                    error.codex_error_info,
                    Some(CodexErrorInfo::ServerOverloaded)
                );
                assert_eq!(
                    error.message,
                    "Selected model is at capacity. Please try a different model."
                );
            }
            EventMsg::StreamError(_) => stream_error_events += 1,
            EventMsg::Warning(warning)
                if warning.message.contains("Falling back from WebSockets") =>
            {
                fallback_warning_events += 1;
            }
            EventMsg::TurnComplete(event) => {
                assert_eq!(
                    event.error.and_then(|error| error.codex_error_info),
                    Some(CodexErrorInfo::ServerOverloaded)
                );
                break;
            }
            _ => {}
        }
    }

    assert_eq!(error_events, 1);
    assert_eq!(stream_error_events, 0);
    assert_eq!(
        fallback_warning_events, 0,
        "websocket must not fall back to HTTP"
    );
    let request_count: usize = server.connections().iter().map(Vec::len).sum();
    assert_eq!(request_count, 2, "expected only prewarm and terminal error");
    assert_eq!(
        telemetry.events.try_recv(),
        Err(mpsc::error::TryRecvError::Empty)
    );
    server.shutdown().await;

    Ok(())
}

# DeepWiki Q&A with Code Context for Repository: openai/codex
## Q1
工具调用后产生的结果比较大时，处理方式是什么
### Answer
## 概述

当工具调用产生的结果过大时，Codex 会根据不同的工具类型采用不同的截断（truncation）策略，核心思想是使用 `TruncationPolicy` 对输出进行按字节数、Token 数等限制，避免超大结果占满模型上下文或撑爆存储。

---

## 各类工具的处理方式

### 1. MCP 工具调用结果

MCP 工具结果分两条路径处理：

- **发给模型前的清洗**：`sanitize_mcp_tool_result_for_model` 会根据模型支持的输入模态（文本/图片/音频）替换不支持的内容块 codex:896-933 。
- **写入事件/rollout 存储前的截断**：`truncate_mcp_tool_result_for_event` 会先序列化整个结果，若超过 `MCP_TOOL_CALL_EVENT_RESULT_MAX_BYTES`，就把结果压缩为一段带截断标记的文本预览，并清空 `structured_content` 和 `meta` codex:935-977 。对应的测试验证了大结果和大错误消息都会被截断到预算范围内 codex:1067-1112 。这一行为也在 app-server 集成测试中得到验证，超大 MCP 结果最终作为带 “truncated” 标记的纯文本内容返回 codex:1071-1080 。

### 2. Exec/Shell 命令输出

`format_exec_output_for_model` 负责把 shell 执行输出格式化为发送给模型的文本，其中会调用 `truncate_text` 按 `TruncationPolicy` 截断超大内容，并附加行数、退出码、耗时等元数据 codex:92-119 。测试用例证实：当 `exec_command` 产生 10 万行输出时，最终返回给模型的文本会被截断到约一万字符左右，并带有 “…N chars truncated…” 或 “…N tokens truncated…” 标记 codex:136-211 codex:275-293 。

### 3. Code Mode（JS REPL）结果

Code Mode 中，`truncate_code_mode_result` 会根据结果内容类型选择不同截断路径：若全部是文本项，用 `formatted_truncate_text_content_items_with_policy`；否则用更通用的 `truncate_function_output_items_with_policy`（同时处理音频 token 估算） codex:326-342 。

此外，Code Mode 中工具调用的**响应字节预算**是特殊的：直接调用（`ToolCallSource::Direct`）受宿主截断策略限制，而 Code Mode 调用因为接收的是"typed results"（无需按文本截断），所以只受工具自身限制 codex:142-158 。

在 code-mode-host 的集成测试中可以看到，当嵌套工具返回超大结果（`big_result`）时，该调用会被拒绝（在 JS 侧捕获异常），但不会导致整个 REPL 会话崩溃，后续调用仍可正常执行 codex:618-697 。

### 4. Dynamic Tools (TUI)

在 `codex-rs/tui/src/dynamic_tools.rs` 中，`success_response` 采用了更激进的**迭代式裁剪**策略：先按字节数检查，超限则逐步：
1. 从最新 `turn` 的 `items` 中移除较早项；
2. 若 `threads` 数组超过 1 个，pop 掉；
3. 移除 `polls` 中的部分冗余字段（如 `latestAssistantMessage`、`cursor` 等）；
4. 若仍超限，将 `max_chars` 减半后调用 `truncate_response` 强制截断，并在结果中标记 `"truncated": true`；
5. 若所有裁剪手段用尽仍超限，返回错误 "Dynamic tool response exceeded the maximum context budget" codex:302-368 。

### 5. 底层文本截断策略

以上多处使用的核心工具是 `TruncationPolicy`（按字节数 `Bytes(n)` 或 按 Token 数 `Tokens(n)`），配合 `truncate_text` / `truncate_function_output_items_with_policy` 等函数完成统一截断逻辑，这一策略在 `context_tests.rs` 中也有专门针对 MCP 结构化结果截断的单元测试验证 codex:130-178 。

## Notes

- 不同工具系统（MCP、exec、Code Mode、TUI dynamic tools）各自实现了独立但思路相似的截断逻辑，没有一个统一的全局截断入口。
- `prompting-guide.md` 中提及的 "Programmatic Tool Calling" 章节讨论的是模型侧如何用代码减少中间结果规模，属于提示工程建议，与代码层面的截断实现是互补但不同的机制 codex:134-162 ，仅供参考背景，非直接回答本问题的核心代码。

```rust
fn sanitize_mcp_tool_result_for_model(
    input_modalities: &[InputModality],
    result: Result<CallToolResult, String>,
) -> Result<CallToolResult, String> {
    let supports_image_input = input_modalities.contains(&InputModality::Image);
    let supports_audio_input = input_modalities.contains(&InputModality::Audio);
    if supports_image_input && supports_audio_input {
        return result;
    }

    result.map(|call_tool_result| CallToolResult {
        content: call_tool_result
            .content
            .iter()
            .map(|block| {
                if let Some(content_type) = block.get("type").and_then(serde_json::Value::as_str) {
                    if content_type == "image" && !supports_image_input {
                        return serde_json::json!({
                            "type": "text",
                            "text": "<image content omitted because you do not support image input>",
                        });
                    }
                    if content_type == "audio" && !supports_audio_input {
                        return serde_json::json!({
                            "type": "text",
                            "text": "<audio content omitted because you do not support audio input>",
                        });
                    }
                }

                block.clone()
            })
            .collect::<Vec<_>>(),
        structured_content: call_tool_result.structured_content,
        is_error: call_tool_result.is_error,
        meta: call_tool_result.meta,
    })
}
```

```rust
fn truncate_mcp_tool_result_for_event(
    result: &Result<CallToolResult, String>,
) -> Result<CallToolResult, String> {
    match result {
        Ok(call_tool_result) => {
            // The app-server rebuilds `ThreadItem::McpToolCall` from this item,
            // so avoid persisting multi-megabyte results in rollout storage.
            let Ok(serialized) = serde_json::to_string(call_tool_result) else {
                return Ok(call_tool_result.clone());
            };
            if serialized.len() <= MCP_TOOL_CALL_EVENT_RESULT_MAX_BYTES {
                return Ok(call_tool_result.clone());
            }

            // A huge MCP result can put bytes in `content`, `structuredContent`,
            // or `_meta`. Collapse the event copy to a text preview of the whole
            // serialized result so the UI still has useful context without
            // preserving a multi-megabyte structured payload.
            //
            // This budget applies to the preview text, not the final event JSON.
            // The preview is itself serialized into a JSON string, so quotes and
            // backslashes can be escaped again and the stored event may end up
            // somewhat larger than this byte budget.
            let truncated = truncate_text(
                &serialized,
                TruncationPolicy::Bytes(MCP_TOOL_CALL_EVENT_RESULT_MAX_BYTES),
            );
            Ok(CallToolResult {
                content: vec![serde_json::json!({
                    "type": "text",
                    "text": truncated,
                })],
                structured_content: None,
                is_error: call_tool_result.is_error,
                meta: None,
            })
        }
        Err(message) => Err(truncate_text(
            message,
            TruncationPolicy::Bytes(MCP_TOOL_CALL_EVENT_RESULT_MAX_BYTES),
        )),
    }
}
```

```rust
/// Format the combined exec output for sending back to the model.
/// Includes exit code and duration metadata; truncates large bodies safely.
pub fn format_exec_output_for_model(
    exec_output: &ExecToolCallOutput,
    truncation_policy: TruncationPolicy,
) -> String {
    // round to 1 decimal place
    let duration_seconds = ((exec_output.duration.as_secs_f32()) * 10.0).round() / 10.0;

    let content = build_content_with_timeout(exec_output);

    let total_lines = content.lines().count();

    let formatted_output = truncate_text(&content, truncation_policy);

    let mut sections = Vec::new();

    sections.push(format!("Exit code: {}", exec_output.exit_code));
    sections.push(format!("Wall time: {duration_seconds} seconds"));
    if total_lines != formatted_output.lines().count() {
        sections.push(format!("Total output lines: {total_lines}"));
    }

    sections.push("Output:".to_string());
    sections.push(formatted_output);

    sections.join("\n")
}
```

```rust
impl ToolCall<'_> {
    /// Returns the response-content budget, bounded by the tool's own size limit.
    ///
    /// Direct calls use the host's effective text-output allowance. Code Mode receives
    /// typed results without that truncation, so only the tool's limit applies.
    /// Callers must include serialization overhead when fitting a response to this budget.
    pub fn response_byte_budget(&self, max_response_bytes: usize) -> usize {
        match &self.source {
            ToolCallSource::Direct => {
                max_response_bytes.min((self.truncation_policy * 1.2).byte_budget())
            }
            ToolCallSource::CodeMode {
                cell_id: _,
                runtime_tool_call_id: _,
            } => max_response_bytes,
        }
    }
}
```

```rust
fn success_response(mut value: Value) -> Result<DynamicToolCallResponse, String> {
    let mut max_chars = MAX_RESPONSE_BYTES / 2;
    loop {
        let text = serde_json::to_string(&value).map_err(|error| error.to_string())?;
        if text.len() <= MAX_RESPONSE_BYTES {
            return Ok(DynamicToolCallResponse {
                content_items: vec![DynamicToolCallOutputContentItem::InputText { text }],
                success: true,
            });
        }
        if max_chars == 0 {
            if let Some(items) = value
                .get_mut("turns")
                .and_then(Value::as_array_mut)
                .and_then(|turns| {
                    turns.iter_mut().rev().find_map(|turn| {
                        turn.get_mut("items")
                            .and_then(Value::as_array_mut)
                            .filter(|items| !items.is_empty())
                    })
                })
            {
                items.remove(0);
                continue;
            }
            if let Some(threads) = value
                .get_mut("threads")
                .and_then(Value::as_array_mut)
                .filter(|threads| threads.len() > 1)
            {
                threads.pop();
                continue;
            }
            if value
                .get_mut("polls")
                .and_then(Value::as_array_mut)
                .is_some_and(|polls| {
                    polls.iter_mut().rev().any(|poll| {
                        poll.as_object_mut().is_some_and(|fields| {
                            [
                                "latestAssistantMessage",
                                "latestToolMarker",
                                "latestTurn",
                                "latestAssistantMessageId",
                                "latestToolMarkerId",
                                "revision",
                                "schemaVersion",
                                "changed",
                                "cursor",
                            ]
                            .into_iter()
                            .any(|name| fields.remove(name).is_some())
                        })
                    })
                })
            {
                continue;
            }
            return Err("Dynamic tool response exceeded the maximum context budget".to_string());
        }
        max_chars /= 2;
        truncate_response(&mut value, max_chars);
        if let Value::Object(fields) = &mut value {
            fields.insert("truncated".to_string(), Value::Bool(true));
        }
    }
}
```

```markdown
## Programmatic Tool Calling

Programmatic Tool Calling is useful when code can reduce large, structured intermediate results before they return to model context.

Use it for:

- filtering, joining, sorting, ranking, deduplication, and aggregation;
- batching across many similar records;
- repeated deterministic validation;
- large structured results that can be reduced to a compact schema.

Prefer direct tool calls when:

- one call is sufficient;
- intermediate outputs are already small;
- each result may change the next decision;
- an action requires approval;
- the final answer must preserve citations or native artifacts;
- the workflow requires semantic judgment between calls.

Do not rely on generic instructions such as “use Programmatic Tool Calling efficiently.” State the bounded stage, eligible tools, output schema, retry limit, stop condition, and handoff back to direct model judgment.

    Use Programmatic Tool Calling only for the bounded record-reduction stage.
```

## Q2
被截断的数据怎么获取
### Answer
## 直接回答

根据目前检索到的代码，Codex 里被截断的数据**在大多数情况下不会被完整保留以供后续取回**——截断发生的位置和保存的内容视具体工具类型而不同：

---

## 各场景详情

### 1. MCP 工具结果：截断后的原始数据被丢弃

`truncate_mcp_tool_result_for_event` 只保留一个文本预览，并显式清空 `structured_content` 和 `meta`，原始的完整 `CallToolResult` 在这一步之后不会再被存储 codex:935-977 。这是专门针对写入事件/rollout 存储时的处理（注释提到 app-server 会从这个事件重建 `ThreadItem::McpToolCall`），所以一旦落盘就只剩截断后的预览文本，没有代码路径能再取回完整原始结果 codex:940-943 。

同理，`sanitize_mcp_tool_result_for_model` 是发给模型前的另一层处理，把不支持的模态（图片/音频）替换成占位文本，被替换的原始内容块同样直接丢弃，不保留 codex:906-933 。

### 2. Exec/Shell 输出：原始字节仍在内存对象中，但未暴露取回接口

`ExecCommandToolOutput` 结构体保留了 `raw_output: Vec<u8>`（完整未截断的原始字节），截断只发生在渲染为文本时 codex:346-360 。具体来说：

- `response_text()` 调用 `truncated_output_with_policy` 对 `raw_output` 做截断，用于生成返回给模型的文本，但 `raw_output` 本身不会被修改或丢弃 codex:516-541 。
- `code_mode_result()` 同样是基于 `raw_output` 按 `max_output_tokens` 生成截断后的字符串给 Code Mode 使用 codex:414-444 。

但从检索到的代码看，**没有额外的工具调用接口能让模型显式请求"给我完整的 raw_output"**——`raw_output` 字段只存在于该结构体的生命周期内（该轮工具调用返回后），并未被持久化或提供二次查询的 API。

### 3. Unified Exec 的分块/轮询机制：不是"取回截断数据"，而是"持续读取新输出"

`unified_exec::process_manager` 支持通过 `chunk_id` 和进程 ID 做后续的 `write_stdin` / 轮询读取，从正在运行的进程里持续拉取**新产生**的输出 codex:789-811 。这是一种“流式追加读取”，并非重新获取已经因为超出 token/byte 预算而被裁掉的那部分历史输出。

### 4. Code Mode 嵌套工具调用：截断只记录元信息，不保留原始内容

在 `ExecutedToolCallRecorder` 相关测试中可以看到，当嵌套工具调用参数超过 `MAX_EXECUTED_TOOL_CALL_ARGUMENT_BYTES` 时，会调用 `ExecutedToolCall::truncated(name, original_bytes, max_bytes)`，只记录原始字节数和上限，而不保留截断掉的具体内容本身 codex:305-316 。

## Q3
这些处理方式是工具自行处理的，还是有中间件或者入口统一处理
### Answer
## 直接回答

两者都有，但更准确地说：**没有单一的强制中间件拦截所有工具输出**，而是通过一个共享的 `ToolOutput` trait 契约 + 共享的截断工具函数（`TruncationPolicy`/`truncate_text`），让各个工具类型在各自的实现里"自行调用"截断逻辑。

---

## 详细说明

### 共享契约层：`ToolOutput` trait

所有工具的输出都要实现 `codex_tools::ToolOutput` trait，其中定义了 `log_output`、`to_response_item`、`code_mode_result` 等方法 codex:10-63 。这个 trait 本身**并不强制截断**——它只是提供接口形状，具体是否截断、如何截断由每个实现自行决定。例如 `JsonToolOutput` 和 `CallToolResult` 的 `to_response_item`/`code_mode_result` 实现里就没有做字节/token 截断，只是纯转换 codex:140-210 。

### 各工具类型：自行调用共享的截断工具函数

- **MCP**：`McpToolOutput`（在 `codex-rs/core/src/tools/context.rs`）的 `to_response_item` 调用自己的 `response_payload()`（内部走 `truncation_policy`），是该类型自己实现的逻辑 codex:130-139 。此外在 `mcp_tool_call.rs` 中，`truncate_mcp_tool_result_for_event` 是在事件发出前**专门插入的一个函数调用点**，被上游 MCP 调用流程显式调用（而不是自动触发） codex:583-592 ，这里更像是"在特定管道位置手动埋点"而非全局中间件。
- **Exec/Unified Exec**：`ExecCommandToolOutput::response_text()` 自己调用 `truncated_output_with_policy` 完成截断 codex:516-541 。
- **Code Mode**：`truncate_code_mode_result` 是 code_mode 模块内部定义的辅助函数，在处理嵌套工具调用结果时按需调用 codex:326-342 。
- **TUI Dynamic Tools**：`success_response` 是 TUI 层单独实现的裁剪逻辑，和 core 的 `TruncationPolicy` 完全独立 codex:302-368 （这是 tui crate 内部逻辑，与上面 core crate 的 MCP/Exec 截断是不同的代码路径，仅思路类似）。

### 唯一略带"统一入口"性质的地方：`ToolCall::response_byte_budget`

`codex-rs/tools/src/tool_call.rs` 中的 `response_byte_budget` 方法，根据调用来源（`ToolCallSource::Direct` vs `CodeMode`）统一计算出一个字节预算上限 codex:142-158 。这是所有工具调用都会经过的 `ToolCall` 结构体的方法，算是最接近"统一入口"的设计，但它只是**提供预算数值**，具体截断动作（调用 `truncate_text` 等）仍需各工具输出实现自己完成。

    /// typed results without that truncation, so only the tool's limit applies.
    /// Callers must include serialization overhead when fitting a response to this budget.
    pub fn response_byte_budget(&self, max_response_bytes: usize) -> usize {

                cell_id: _,
                runtime_tool_call_id: _,
            } => max_response_bytes,

## Q1
工具调用后产生的结果比较大时，处理方式是什么
### Answer
## 答案

当工具调用产生的结果过大时，`crush` 根据不同工具采用了几种处理策略：截断、落盘为临时文件、限制返回大小。

---

### 1. 网络类工具：落盘为临时文件

`web_fetch` 和 `agentic_fetch` 在抓取网页内容超过 `LargeContentThreshold`（约 50KB）时，不会直接把内容塞进上下文，而是用 `os.CreateTemp` 写入临时文件，并提示子代理改用 `view`/`grep` 工具查看该文件： crush:46-75 

`agentic_fetch` 的实现逻辑相同，在 URL 模式下判断 `len(content) > tools.LargeContentThreshold`，超限则写入 `tmpDir` 下的临时 `.md` 文件，并把文件路径而非原始内容塞进给子代理的 prompt： crush:110-139 

### 2. `fetch` 工具：硬性截断

普通的 `fetch` 工具设置了 `MaxFetchSize`（100KB）上限，通过 `io.LimitReader` 限制读取的字节数，超出限制的内容会被截断而非落盘：

（参考 wiki 摘要）`MaxFetchSize` 定义于 `internal/agent/tools/fetch.go:22`，截断逻辑在 `internal/agent/tools/fetch.go:182-185`。

### 3. `view` 文件读取工具：分级限制 + 报错

`view` 工具对返回内容大小也有严格限制：
- 若请求的整个文件很大，但只截取一小段（`Offset`/`Limit`）在 `MaxViewSize` 之内，仍可正常返回： crush:111-134 
- 若截取的那部分内容本身超过 `MaxViewSize`，则直接返回错误 `"Content section is too large"`，而不是截断输出： crush:136-155 
- 底层 `readTextFile` 会返回 `contentTooLargeError`，用于上层判断并给出对应提示： crush:175-196 

### 4. UI 展示层：diff 结果的折叠截断

在聊天界面渲染 `multiedit` 的 diff 结果时，如果 diff 行数超过一定阈值（`collapsedMaxLines`），且未处于展开状态，会截断显示并提示还有多少行被省略： crush:1016-1054 

### 5. 大媒体（图片等）工具结果：转换为占位文本 + 附加为用户消息

对于工具返回的媒体类结果（如截图），如果当前模型 provider 不支持原生媒体附件（非 Anthropic/Bedrock 系），`workaroundProviderMediaLimitations` 会把媒体内容从工具结果里剥离，替换为文本占位符，再把原始媒体作为独立的用户消息（`FilePart`）重新组织，避免污染 `tool` 角色消息导致会话中断： crush:2201-2285

## Notes

- 以上几种机制服务于不同层级：网络抓取类（`web_fetch`/`agentic_fetch`）用「落盘 + 让 agent 自行 `view`/`grep`」的方式规避一次性塞入超大上下文；`fetch`/`view` 则是直接的硬性大小上限与截断/报错；UI 层的截断只影响展示，不影响底层数据；`agent.go` 中的媒体处理是应对多模态工具结果在不支持媒体的模型下的兼容性问题，属于另一类“大结果”（多模态负载）处理。

## Q2
对于截断等操作，是对应的工具调用完之后自己处理的，还是有相应的中间件或者入口统一处理
### Answer
## 答案

是由**各个工具自己在其 handler 函数内部处理**的，`crush` 并没有一个统一的中间件或入口来对所有工具结果做截断/落盘。每个工具在返回 `fantasy.ToolResponse` 之前，各自判断内容大小并做相应处理。

---

### 证据

**`web_fetch`**：其判断逻辑（`hasLargeContent := len(content) > LargeContentThreshold`）直接写在 `NewWebFetchTool` 返回的闭包（工具的执行函数）里，是该工具专属的处理： crush:41-75 

**`agentic_fetch`**：同样，大小判断和落盘逻辑写在 `agenticFetchTool` 方法内部，属于这个工具自身的实现细节，和 `web_fetch` 没有共享同一份代码，只是重复了类似的模式： crush:69-139 

**`view`**：其大小限制通过底层函数 `readTextFile` 实现，返回 `contentTooLargeError`，这个错误类型和判断逻辑是 `view` 工具专属的（在 `internal/agent/tools/view.go`，测试文件里可以看到调用方式），不是全局中间件： crush:175-196 

**`agent.go` 里的 `workaroundProviderMediaLimitations`** 是唯一一处相对"统一"的处理点——但它并不是针对"结果过大"，而是针对多模态数据（图片等）在不同 provider 之间的兼容性问题。它在 `sessionAgent.Run` 生成消息历史的阶段被调用，作用范围是所有工具的 `ToolResult`，而不是某个特定工具，可以视为一种跨工具的统一后处理： crush:2180-2211 

---

## 详细说明

1. **没有统一的"大小限制中间件"**：`fantasy.AgentTool` 框架（`fantasy.NewParallelAgentTool` 等）只是提供了工具注册和调用的通用接口，本身不包含结果大小检查逻辑。每个工具的常量（如 `LargeContentThreshold`、`MaxViewSize`、`MaxLineLength`）都是各自模块单独定义、单独判断的。

2. **唯一接近"统一入口"的地方是 `workaroundProviderMediaLimitations`**，它在 `sessionAgent` 构造发给模型的消息历史时，对所有工具的结果做统一遍历处理——但这处理的是多模态兼容性问题（图片转换为占位符文本+独立用户消息），而不是"结果过大截断"这个语义。

3. UI 层（`internal/ui/chat/tools.go` 的 `toolOutputMultiEditDiffContent`）也是各工具渲染函数（针对 `multiedit` 专属）里单独处理截断展示的，不是通用中间件。

- 如果你想找一个真正统一的"结果大小检查"入口，目前代码库中没有看到这样的抽象层；各工具各自为战，模式相似但实现独立。

// workaroundProviderMediaLimitations converts media content in tool results to
// user messages for providers that don't natively support images in tool results.
//
// Problem: OpenAI, Google, OpenRouter, and other OpenAI-compatible providers
// don't support sending images/media in tool result messages - they only accept
// text in tool results. However, they DO support images in user messages.
//
// If we send media in tool results to these providers, the API returns an error.
//
// Solution: For these providers, we:
//  1. Replace the media in the tool result with a text placeholder
//  2. Inject a user message immediately after with the image as a file attachment
//  3. This maintains the tool execution flow while working around API limitations
//
// Anthropic and Bedrock support images natively in tool results, so we skip
// this workaround for them.
//
// Example transformation:
//
//	BEFORE: [tool result: image data]
//	AFTER:  [tool result: "Image loaded - see attached"], [user: image attachment]

## 工具调用大结果处理：统一中间件管道 vs 工具专属策略
本图追踪 Claude Code 中工具调用结果的处理路径：引擎侧的统一 tool.call/PostToolUse 事件管道（可供任意 hook 环绕拦截），插件如何利用这条管道做统一处理，以及 CHANGELOG 记录的、按工具类型（Bash/Task/MCP）定制的大结果截断/存盘策略。核心存盘/截断实现代码不在当前索引范围内（推测在闭源 core 引擎里）。快速跳转：统一入口见 [1a][1b]，中间件环绕用法见 [2b][2c]，按工具定制的策略证据见 [4a][4b][4c]。
### 1. 引擎如何为每次工具调用统一触发事件管道
类型系统层面证明：所有工具调用（无论 Bash、Read、MCP 还是自定义插件工具）都统一经过 tool.call → next 链 → core → PostToolUse 这条单一入口，而不是每个工具各自处理事件分发。
### 1a. 统一的 tool.call 事件 (`claude-code.d.ts:3222`)
引擎准备运行任意工具前统一触发该事件，next(e) 依次跑完下方所有 hook，再运行 core（权限提示+工具本体）
```text
'tool.call': ToolCallInput;
```
### 1b. tool.call 的统一返回类型 (`claude-code.d.ts:3654`)
`{ result, context? }` 或 `{ deny }` 或 core 自身的 `{ ref, result }`——所有工具的结果都套同一个壳
```text
'tool.call': ToolCallResult;
```
### 1c. 调用结束后的统一 PostToolUse 事件 (`claude-code.d.ts:6316`)
tool_response 即工具的完整结果；任意工具执行完毕后都会走这个统一 hook 入口，可在此处对结果做后处理（如判断是否需要落盘）
```text
type PostToolUseHookInput = BaseHookInput & { hook_event_name: 'PostToolUse'; tool_name: string; tool_input: unknown; tool_response: unknown; ... }
```
### 1d. 并行工具调用批次结束后的统一事件 (`claude-code.d.ts:6290`)
一批并行工具调用全部完成后触发一次，同样是集中式的下游处理点，而非各工具各自触发
```text
type PostToolBatchHookInput = BaseHookInput & { hook_event_name: 'PostToolBatch'; tool_calls: PostToolBatchToolCall[]; }
```
### 1e. UI 层读取的统一 output 字段 (`claude-code.d.ts:7814`)
无论具体工具类型，UI（transcript 行）都从同一个 output 字段读取结果用于展示——再次体现了统一存取点而非各工具自建通道

## Q1

是否有什么暂停当前 agent loop，然后仍然可以从暂停的地方继续恢复进行的机制

### Answer

## 答案

是的，Codex 中存在这样的机制,主要通过两层实现：**中断当前任务 (`Op::Interrupt`)** 和 **基于持久化历史恢复线程 (resume from rollout)**。

---

## 详细说明

### 1. 暂停：`Op::Interrupt`

当前正在运行的任务（`Task`/`Turn`）可以通过 `Op::Interrupt` 中断，UI 层可主动发起 codex:31-41 。在 `AgentControl` 中，`interrupt_agent` 方法会向目标线程发送 `Op::Interrupt` codex:355-371 。TUI 中的 `stop_agents_overview_thread` 也是通过查找活跃 turn 后调用 `turn_interrupt` 完成暂停 codex:705-756 。

被中断的 turn 状态不会丢失：每次 `Turn` 完成（或被中断保存进度）后，模型的 `response_id` 会被记录在 `Session` 状态中，并通过 `EventMsg::TurnComplete` 返回给 UI，用于日后从这个断点继续对话 codex:45-45 。

### 2. 恢复：从 rollout 恢复线程

Codex 会把会话事件持久化为 rollout（JSONL）文件。恢复时，`ThreadManager::resume_thread_from_rollout` 读取该 rollout 文件重建 `InitialHistory`，再调用 `resume_thread_with_history` 重新 spawn 一个 `Session`： codex:1046-1063 codex:1098-1133

在多代理（multi-agent）场景中，`AgentControl` 提供了 `resume_agent_from_rollout` / `resume_single_agent_from_rollout`，用于恢复某个被关闭或暂停的子代理线程，恢复时会重新加载存储的历史记录、代理路径/角色等元数据，再重新建立会话 codex:1202-1283 。工具层的 `resume_agent` 处理器就是通过调用此接口来"唤醒"之前关闭的代理 codex:191-212 。

App Server 层同样实现了幂等的 resume 语义：如果线程仍在运行且配置未变，直接复用现有线程；否则关闭旧的空闲线程缓存并从存储中重新加载历史 codex:4220-4268 。

### 3. 分叉 (Fork) 作为另一种"续接"方式

除了原地恢复，Codex 还支持 `InitialHistory::Forked`，即从某个历史断点分叉出新线程，同样是恢复到之前状态后继续 codex:4456-4471 。

### 4. 端到端测试佐证

`control_tests.rs` 中的测试用例证明了完整暂停→关闭→恢复流程：先 `shutdown_all_threads_bounded` 关闭线程，再用新的 `ThreadManager` 调用 `resume_agent_from_rollout`，确认恢复后的线程状态不是 `NotFound` codex:1063-1084 ，即使是嵌套的父子代理树也能正确恢复 codex:4658-4683 。

    async fn extend_deadlines_while_paused(
        pause_state: &mut Option<watch::Receiver<bool>>,
        deadline: &mut Instant,
        post_exit_deadline: &mut Option<Instant>,
    ) {
        let Some(receiver) = pause_state.as_mut() else {
            return;
        };
        if !*receiver.borrow() {
            return;
        }

        let paused_at = Instant::now();
        while *receiver.borrow() {
            if receiver.changed().await.is_err() {
                break;
            }
        }

        let paused_for = paused_at.elapsed();
        *deadline += paused_for;
        if let Some(post_exit_deadline) = post_exit_deadline.as_mut() {
            *post_exit_deadline += paused_for;
        }
    }

## 暂停并恢复 Agent Loop 的机制

梳理 Codex 中三种不同粒度的"暂停-恢复"能力：用户中断（新turn）、同一turn的无缝挂起/恢复（worker间转移）、以及基于 rollout 的整会话重建。快速跳转：挂起核心逻辑见[2c]，恢复挂起turn见[3c]，rollout整体恢复见[4b]。

## Q3

这个中断的持久化，需要保存哪些内容呢

### Answer

## 答案

这里的"中断的持久化"指的是 `SuspendTurnAndShutdown` 机制的持久化内容,主要包括三部分：**`turn_id`（内存中原样返回，不落盘但由调用方保存）**、**完整的会话历史（rollout 文件）**，以及**指向该 turn 的 `root_turn_id` 引用上下文（写入 rollout 中的某个 context item）**。

---

## 详细说明

### 1. `turn_id`：挂起结果中携带的唯一标识

挂起成功后，`suspend_turn_and_shutdown` 会从被取消的 task 里取出 `turn_context.sub_id` 作为 `turn_id` codex:66-69 ，并最终作为 `SuspendTurnOutcome::Suspended { turn_id }` 返回给调用方 codex:18-28 。这个 `turn_id` 本身并不是额外写入磁盘的新内容，而是从已经在 rollout 中持久化的 turn 上下文里读取出来的——真正的持久化载体是下面第 2 点的 rollout 历史。

### 2. 完整会话历史：通过 flush 落盘

挂起流程的关键步骤是在真正取消执行前先 `flush` 一次历史 codex:40-46 ，这样即便随后取消失败，原 worker 依然完整持有这个 turn，不会出现"两边都不完整持有"的中间状态。取消执行、清理内存等待队列后，还会再次 `flush` 并**关闭 rollout writer** codex:44-46 。关闭 writer 是安全交接的关键：只要 writer 没关，就不能让另一个 worker 去写同一份历史文件，否则会产生并发写冲突。

需要特别强调的是，这次挂起**不会写入 `TurnAborted` 或 `TurnComplete` 终止事件**——这正是它与 `Op::Interrupt` 的本质区别：turn 在协议历史上仍然是"未完成"的状态，而不是"已终止"，因此后续才能被识别为可恢复。

### 3. `root_turn_id` 引用上下文：用于恢复时校验归属

恢复时（`recover_turn_if_idle`），代码会用之前保存的 `turn_id` 去匹配持久化的 `reference_context_item`，从中取出原来的 `root_turn_id` codex:364-374 。这说明持久化内容中还包含了这个 turn 在会话树中的归属信息（`root_turn_id`），确保恢复后的 turn 依然挂在正确的会话树位置上，而不是变成一个孤立的顶层 turn。

### 4. 最佳努力（不持久化）的部分

内存中的等待状态——挂起的用户输入、审批（approval）等待者、elicitation 或 server-request 等待者——**只存在于当前进程内，不会被持久化**，挂起时会被清空/丢弃，属于"best effort"的取舍 codex:391-398 （该注释见 `codex_thread.rs` 中 `suspend_turn_and_shutdown` 的文档说明）。这意味着恢复后不会自动重放挂起前排队的用户输入或悬而未决的审批请求。

---

## 汇总表

| 内容 | 是否持久化 | 位置/机制 |
|---|---|---|
| 完整对话历史（ResponseItem 等） | ✅ 持久化 | rollout 文件，通过 `live_thread.flush()` 落盘 codex:40-46 |
| `turn_id` | ✅（间接，随 rollout 中的 turn context 一起持久化） | `task.turn_context.sub_id` codex:66-69 |
| `root_turn_id`（会话树归属） | ✅ 持久化在 `reference_context_item` 中 | 恢复时按 `turn_id` 过滤取出 codex:364-374 |
| rollout writer 状态 | ✅（关闭动作被持久化的"信号"） | flush + shutdown，避免双写冲突 |
| 挂起时排队的用户输入/审批等待者 | ❌ 不持久化，best effort 丢弃 | 仅内存态 |
| `TurnAborted`/`TurnComplete` 事件 | ❌ 不写入 | 与 `Op::Interrupt` 的核心区别 |

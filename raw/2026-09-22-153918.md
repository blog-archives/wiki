# DeepWiki Q&A with Code Context for Repository: openai/codex
## Q1
请从用户提交一条消息开始，追踪到模型调用、工具执行、工具结果回传，再到最终回答的完整路径。指出入口函数、Agent 循环、模型调用位置、工具分发位置和停止条件。先选默认或最简单的一条路径，不展开全部实现分支。
### Answer
## 简要回答

最简单的默认路径是：`Op::UserTurn` 提交 → `run_turn` 主循环 → `run_sampling_request` 发起模型调用 → 流式响应通过 `handle_output_item_done` 判定是否为工具调用 → 若是工具调用则通过 `ToolRouter` / `ToolCallRuntime` 分发执行 → 工具结果作为 `FunctionCallOutput` 写回历史 → 下一轮采样请求带着工具结果继续 → 当模型只返回纯文本消息（无工具调用）时循环终止，触发 `TurnComplete`。

---

## 详细路径

### 1. 入口函数：`run_turn`
`run_turn` 是单次 Task 内 Turn 循环的核心入口，注释中明确描述了该循环的语义：模型要么返回工具调用，要么返回助手消息；若是工具调用则执行并把结果反馈给下一次采样请求，若是纯消息则记录并结束该 Turn。
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="148-169" end="169" />

### 2. Agent 循环
在 `run_turn` 内部有一个 `loop`，每次迭代：先处理 pending input/hooks，再构建 `step_context`，然后调用 `run_sampling_request` 发起模型请求：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="334-341" end="341" />
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="404-438" end="438" />

### 3. 模型调用位置
在采样请求闭包中，历史记录被转换为 prompt 输入，并调用 `run_sampling_request`（内部使用 `ModelClientSession` 向 Model Provider API 发起流式请求）：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="417-438" end="438" />

### 4. 流式结果处理与工具分发
模型流式返回的每个输出 item 由 `handle_output_item_done` 处理。它先尝试用 `ToolRouter::build_tool_call` 判断该 item 是否是工具调用：

- **是工具调用**：记录该 item 到历史，然后通过 `ctx.tool_runtime.handle_tool_call` 分发执行（这是工具分发的具体位置），并标记 `needs_follow_up = true` 以便循环继续：
<cite repo="openai/codex" path="codex-rs/core/src/stream_events_utils.rs" start="298-329" end="329" />

- **不是工具调用（纯消息/reasoning）**：调用 `finalize_non_tool_response_item` 生成最终 `TurnItem`，通过 `emit_turn_item_started` / `emit_turn_item_completed` 发出事件，并记录到历史，同时把 `last_agent_message` 保存下来，这是"回答完成"的信号来源：
<cite repo="openai/codex" path="codex-rs/core/src/stream_events_utils.rs" start="330-362" end="362" />

- **模型要求直接响应或拒绝工具**：构造 `FunctionCallOutput` 写回历史，同样设置 `needs_follow_up = true` 继续循环：
<cite repo="openai/codex" path="codex-rs/core/src/stream_events_utils.rs" start="363-384" end="384" />

### 5. 工具结果回传
工具执行结果（无论是真实工具调用的输出，还是"respond to model"分支的 `FunctionCallOutput`）都作为 `ResponseItem`/`FunctionCallOutput` 被写回会话历史（`record_conversation_items` / `record_completed_response_item_with_finalized_facts`），下一次循环迭代构建 `sampling_request_input` 时会通过 `sess.clone_history().await.for_prompt(...)` 把这些结果重新纳入 prompt：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="417-423" end="423" />

如果本轮存在待完成的工具调用（`in_flight` 不为空），`run_turn` 会等待它们完成（`drain_in_flight`）后再继续循环：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="2834-2840" end="2840" />

### 6. 停止条件
循环终止/Turn 完成的判定条件体现在两处：
1. 语义上的默认路径——`run_turn` 函数头部注释说明"若模型仅发送助手消息，则记录进历史并认为该 Turn 完成"：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="157-160" end="160" />
2. 代码上，`handle_output_item_done` 在非工具分支不设置 `needs_follow_up`（保持默认 `false`），从而不会触发下一轮采样，Turn 自然结束：
<cite repo="openai/codex" path="codex-rs/core/src/stream_events_utils.rs" start="330-362" end="362" />

此外，取消 token 被触发、hooks 拒绝、致命错误（`FunctionCallError::Fatal`）等也是提前终止路径，但非"默认最简路径"，此处不展开。

### 7. 最终回答上抛给 UI
Turn 内所有事件（包括 `AgentMessageContentDelta`、`ItemCompleted`）通过 `Session::send_event` / `send_event_raw` 发往事件通道，UI 侧通过 `CodexThread::next_event` 消费，最终 `EventMsg::TurnComplete` 标志本轮结束（如 wiki 所述的 Turn Execution Sequence）。这一层跨越了 `session/handlers.rs` 与 `codex_thread.rs`，其具体细节不在本次提供的代码片段中，但 Overview wiki 中的时序图印证了这一收尾流程。

## Q2
在刚才的执行路径上，最终发送给模型的请求在哪里组装？请列出其中的系统提示、工具定义、历史消息、当前用户输入、检索结果、记忆和任务状态分别来自哪里、以什么形式进入请求，以及排列顺序。哪些内容每轮重建，哪些内容持续累积？
### Answer
## 简要回答

最终发给模型的请求在 `build_prompt` 中组装为一个 `Prompt` 结构体：`input`（历史+当前消息）、`tools`（工具定义）、`base_instructions`（系统提示）、`output_schema` 等字段各自来源不同，`build_prompt` 由 `run_sampling_request` 每轮调用一次，随后传给 `try_run_sampling_request` → `client_session.stream(prompt, ...)` 发出请求。

<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="1381-1399" end="1399" />

## 详细说明

### 组装位置：`build_prompt`

`Prompt` 结构体的字段与来源：

| 字段 | 内容 | 来源 |
|---|---|---|
| `input` | 历史消息 + 当前用户输入 + 工具结果 | 传入的 `input: Vec<ResponseItem>` 参数 |
| `tools` | 工具定义 | `step_context.tool_router.model_visible_specs()` |
| `parallel_tool_calls` | 固定为 `true` | 硬编码 |
| `base_instructions` | 系统提示 | 传入参数 `base_instructions` |
| `output_schema`/`output_schema_strict` | 任务/输出格式约束 | `turn_context.final_output_json_schema` + `is_basic_session_source` 判定 |
| `cyber_access_program` | 任务状态相关的权限标志 | `turn_context.cyber_access_program` |

**系统提示（`base_instructions`）**：每轮在 `run_sampling_request` 开始时通过 `sess.get_prompt_base_instructions().await` 取一次，随后在该轮内的所有重试（retry loop）中被 `.clone()` 复用：

<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="1458-1462" end="1462" />

**工具定义（`tools`）**：来自 `step_context.tool_router`，而 `tool_router` 是在 `step_context` 构建时通过 `built_tools`/`build_tool_router` 生成的（结合 MCP 工具、内置工具、插件推荐等）：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="1640-1650" end="1650" />

由于 `step_context` 在每次循环迭代（每个 sampling step）都可能重新 `capture_step_context_with_required_mcp_servers`，工具集是**按 step 重建**的（当输入变化，如新增 MCP 需求时会刷新）：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="367-402" end="402" />

**历史消息 + 当前用户输入（`input`）**：通过 `sess.clone_history().await.for_prompt(...)` 从会话历史克隆出来，这是**持续累积**的部分——每次工具结果、用户消息、assistant 消息都会被 `record_conversation_items` 写回历史，下一次组装 `input` 时会带上之前所有内容：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="417-423" end="423" />

在 `run_sampling_request` 内部的重试/续接循环中，第一次用外部传入的 `initial_input`，之后每次续接都重新 `clone_history()`：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="1444-1450" end="1450" />

此外，`executed_tool_calls.attach_pending_to_prompt` 会把待处理的工具调用结果附加进 `prompt_input`（并做 `bound_executed_tool_calls_for_prompt` 截断），这是历史之外额外拼接进请求的部分：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="1452-1457" end="1457" />

**检索结果 / 记忆**：从当前提供的代码片段中看不到独立的"检索结果"或"记忆"字段直接进入 `Prompt` 结构；如果这些内容存在，很可能是作为 `ResponseItem`（例如系统注入的上下文消息）被 `record_conversation_items` 写入历史后，经由 `clone_history().for_prompt(...)` 混入 `input` 里，而不是作为 `Prompt` 的独立字段。代码中确实有 "context diffs/full reinjection" 的说法，出现在 `run_turn` 顶部注释中：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="175-178" end="178" />

我没有找到具体的"记忆检索"模块代码片段，无法确认其精确形式和入口——如果你需要，我可以进一步定位 `memory`/`retrieval` 相关模块。

**任务状态**：体现在 `output_schema`/`output_schema_strict`/`cyber_access_program` 等字段，这些来自 `turn_context`，`turn_context` 在整个 Turn 生命周期内是稳定的（不是每个 sampling step 重建，而是整个 Turn 复用同一个 `Arc<TurnContext>`）：
<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="1387-1398" end="1398" />

### 排列顺序

`Prompt` 结构体字段声明顺序是 `input` → `tools` → `parallel_tool_calls` → `base_instructions` → `output_schema` → `output_schema_strict` → `cyber_access_program`，但这只是结构体定义顺序，实际序列化为 HTTP 请求体的顺序取决于 `client_session.stream` 内部序列化逻辑，这部分代码未在当前上下文中提供。

<cite repo="openai/codex" path="codex-rs/core/src/session/turn.rs" start="1382-1399" end="1399" />

### 每轮重建 vs 持续累积总结

| 内容 | 重建/累积 |
|---|---|
| `base_instructions`（系统提示） | 每轮（每次 `run_sampling_request`）取一次，但内容本身通常是静态的 |
| `tools`（工具定义） | 随 `step_context` 重建，可能因新增 MCP 需求而在同一 Turn 内变化 |
| `input`（历史+用户输入+工具结果） | **持续累积**：写入 `sess` 的历史存储，每次组装时重新克隆完整历史 |
| `output_schema`/`cyber_access_program`（任务状态） | 来自 `turn_context`，整个 Turn 内保持不变 |

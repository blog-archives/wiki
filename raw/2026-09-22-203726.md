补充关于长期记忆的更新：# 长期记忆的更新、冲突处理与过期机制

## 更新/写入方式:INIT vs INCREMENTAL UPDATE

Phase 2 整合 agent 根据现有产物是否存在来判断模式:如果 `memory_summary.md`/`skills/` 缺失,走 INIT(从零构建);否则走 INCREMENTAL UPDATE(增量整合) [1](#3-0) 。

增量更新的核心机制是读取 `phase2_workspace_diff.md`(git 风格 diff),把新增/修改的 `raw_memories.md`、`rollout_summaries/*.md` 当作"待摄入队列",把已删除的文件当作"待遗忘/清理队列" [2](#3-1) 。具体流程:

1. 对新增/修改的 rollout,在 `raw_memories.md` 中定位对应片段,必要时打开对应 `rollout_summaries/*.md`
2. 把新信号路由进已有 `MEMORY.md` 块,或新建块
3. 对已删除的输入,在 `MEMORY.md` 中检索并手术式删除/重写不再受支持的内容
4. 若某个块混合了已删除和仍存在的证据,保留仍受支持的内容,必要时拆分/重写该块
5. 最后再回头修订 `memory_summary.md`,移除失效的摘要/索引内容 [3](#3-2) 

模板也要求增量模式下最小化改动:如果现有块仍反映当前证据,应保持原有措辞、标签和相对顺序稳定;只在真正需要修复过时/歧义/schema 漂移时才重写 [4](#3-3) 。

## 新老记忆冲突如何处理

模板明确把 `updated_at` 作为一等信号:**更新鲜的已验证证据通常优先**,若新 rollout 实质性改变了某任务族的指导内容,应更新该任务/块,并考虑将其移到文件靠前位置 [5](#3-4) 。若证据冲突且验证情况不明,则显式保留这种不确定性,而不是强行合并 [6](#3-5) 。此外要求区分证据的"认知状态"(epistemic status):已验证的仓库/工具事实可直接陈述;明确的用户偏好若看起来稳定可提升;从反复跟进推断出的偏好可谨慎提升;探索性讨论、助手自身的一次性提议应保持局部化、降级或省略,除非后续证据证明其确实成立 [7](#3-6) 。

## 遗忘/删除机制("forgetting")

当某个 rollout summary 或 extension 资源文件被删除(不再被选中)时,consolidation agent 需要在 `MEMORY.md` 中搜索其文件名、路径、thread id,只删除那些"仅由被删除输入支持"的记忆;若某个块同时含已删除和仍存在的证据,不能整块删除,而是移除失效引用/局部指导,保留共享或仍受支持的内容 [8](#3-7) 。这一"遗忘机制"依赖于 workspace diff 的删除项作为权威信号(`{{ phase2_workspace_diff_file }}` 中的每一处变更都必须被传播并整合) [9](#3-8) 。

Final pass 阶段还会做全局审计:移除主要保存探索性讨论、助手单方面建议或一次性印象的记忆(除非有明确证据证明它们后来被证实稳定有用),并核实所有引用的 rollout 是否仍然存在,清理指向已删除输入或缺失文件的块/任务小节 [10](#3-9) 。

## 是否有过期机制

**有**,过期机制体现在两个层面:

### 1. 输入选择层面的 `max_unused_days`

Phase 2 从 state DB 选取 stage-1 输出时,忽略 `last_usage` 超出配置的 `max_unused_days` 窗口的记忆;对没有 `last_usage` 的记忆(从未被使用过),回退用 `generated_at` 判断,保证新鲜但从未使用的记忆仍可入选 [11](#3-10) 。代码层面对应 `get_phase2_input_selection`,测试用例展示了这一过期排除逻辑:一条 40 天前生成、31 天前最后使用的记忆(超出 30 天窗口)被排除,只有 2 天前使用过的和 50 天前生成但从未使用过的记忆(新鲜未用)被选中 [12](#3-11) 。这意味着:**长期不被引用且已经用过一次的记忆会被"冷落"、逐渐从整合输入中掉出**,从而不会继续被写入/刷新到 `MEMORY.md`。

### 2. 整合产物层面的显式清理

如前所述,当支撑某条记忆的原始输入(rollout summary)被删除,整合 agent 会主动清理 `MEMORY.md` 中失去证据支撑的内容 [8](#3-7) ;`memory_summary.md` 的 `## What's in Memory` 索引也要求删除陈旧、重复或低信号的主题,即便它们曾出现在上一版摘要中 [13](#3-12) 。Final pass 还专门要求移除"未来更可能无用的陈旧或低信号块" [14](#3-13) 。

### 写入完成后的落地

无论是更新还是清理,最终都通过 Phase 2 的产物校验与 git baseline 重置完成落盘:`phase2.rs` 在 agent 完成后调用 `validate_consolidation_artifacts_for_version` 校验产物,校验通过后重置 workspace baseline 并将任务标记为 `succeeded` [15](#3-14) 。

``` ## 答案

记忆是否"被引用/使用"是通过检测模型输出中的**记忆引用(citation)**来判断的:当模型在回复中引用某个 `thread_id` 对应的记忆时,系统会解析这个引用并更新该记忆对应 `stage1_outputs` 行的 `usage_count` 和 `last_usage` 字段。

---

## 详细流程

### 1. 使用发生的时机:处理模型输出 item 时

每当一个模型响应 item 完成,`record_completed_response_item_with_finalized_facts` 都会检测其中是否包含记忆引用 [1](#4-0) 。它有两条路径:

- 如果 `finalized_facts.memory_citation` 已经存在(说明上游已经解析过引用),直接调用 `record_stage1_output_usage_for_memory_citation`
- 否则调用 `record_stage1_output_usage_and_detect_memory_citation`,从原始文本中检测引用 [2](#4-1) 

### 2. 从文本中提取引用

`record_stage1_output_usage_and_detect_memory_citation` 从 assistant 输出文本里剥离出 citation 标记(`strip_citations`),再用 `parse_memory_citation` 解析出结构化的 `MemoryCitation`;如果没有引用则直接返回 `false` [3](#4-2) 。

### 3. 把引用映射为 thread_id 并落库

`record_stage1_output_usage_for_memory_citation` 把 `MemoryCitation` 转换成 `thread_ids`,再通过 `MemoryStore::record_stage1_output_usage` 写入数据库 [4](#4-3) 。

### 4. 数据库落地:`usage_count` / `last_usage`

`record_stage1_output_usage` 是核心更新逻辑:对每个被引用的 `thread_id`,把 `stage1_outputs` 表中该行的 `usage_count` 加一,并把 `last_usage` 设为当前 Unix 时间戳(未命中的 `thread_id` 会被忽略) [5](#4-4) 。

这两个字段正是过期判断的依据 —— 在 Phase 2 输入选择 `get_phase2_input_selection` 中,SQL 明确按 `last_usage`(有则用它,否则回退 `source_updated_at`)是否落在 `max_unused_days` 窗口内来筛选,并按 `usage_count DESC` 排序优先选择更常被引用的记忆 [6](#4-5) ;修剪函数 `prune_stage1_outputs_for_retention` 同样用 `COALESCE(last_usage, source_updated_at)` 判断陈旧度来删除长期未使用的记忆 [7](#4-6) 。

### 关联的额外副作用:标记"污染"

在同一个 `record_completed_response_item_with_finalized_facts` 流程中,如果这次响应 item 涉及外部上下文(比如网页搜索),还会额外调用 `mark_thread_memory_mode_polluted_if_external_context`,把该 thread 的 `memory_mode` 标记为 `polluted`,这是一个独立但相关的机制(与"是否引用"无关,但同样影响该线程是否会被再次纳入记忆流水线) [8](#4-7) 。

单测 `record_stage1_output_usage` 对多个 `thread_id`(包括重复、缺失的)进行更新,验证 `usage_count` 按引用次数累加、`last_usage` 被正确写入 [9](#4-8) 。另一测试 `get_phase2_input_selection_excludes_stale_used_memories_but_keeps_fresh_never_used` 直观展示了"使用/未使用"如何影响 phase2 选择结果:31 天未用的记忆被排除,从未用过但新鲜的记忆仍保留 [10](#4-9) 。

## Notes

- 这套 usage 追踪与之前讨论的"过期机制"(`max_unused_days`)是直接绑定的一体机制:引用触发计数更新 → 计数与时间共同决定该记忆是否继续参与 Phase 2 整合或被 `prune_stage1_outputs_for_retention` 清理。
- `codex-rs/memories/read/src/usage.rs` 中的 `MemoriesUsageKind`/`memories_usage_from_command` 是另一套**遥测/统计**机制,用来分类哪些 shell 命令读取了哪个记忆文件(用于 metrics),它与这里讨论的"引用计数决定过期"逻辑是不同的子系统,请勿混淆 [11](#4-10) 。

    /// Record usage for cited stage-1 outputs.
    ///
    /// Each thread id increments `usage_count` by one and sets `last_usage` to
    /// the current Unix timestamp. Missing rows are ignored.
    pub async fn record_stage1_output_usage(
        &self,
        thread_ids: &[ThreadId],
    ) -> anyhow::Result<usize> {
        if thread_ids.is_empty() {
            return Ok(0);
        }

        let now = Utc::now().timestamp();
        let mut tx = self.pool.begin().await?;
        let mut updated_rows = 0;

        for thread_id in thread_ids {
            updated_rows += sqlx::query(
                r#"
UPDATE stage1_outputs
SET
    usage_count = COALESCE(usage_count, 0) + 1,
    last_usage = ?
WHERE thread_id = ?
                "#,
            )
            .bind(now)
            .bind(thread_id.to_string())
            .execute(&mut *tx)
            .await?
            .rows_affected() as usize;
        }

        tx.commit().await?;
        Ok(updated_rows)
    }

    /// Prunes stale stage-1 outputs while preserving the latest phase-2
    /// baseline and stage-1 job watermarks.
    ///
    /// Query behavior:
    /// - considers only rows with `selected_for_phase2 = 0`
    /// - keeps recency as `COALESCE(last_usage, source_updated_at)`
    /// - removes rows older than `max_unused_days`
    /// - prunes at most `limit` rows ordered from stalest to newest
    pub async fn prune_stage1_outputs_for_retention(
        &self,
        max_unused_days: i64,
        limit: usize,
    ) -> anyhow::Result<usize> {
        if limit == 0 {
            return Ok(0);
        }

        let cutoff = (Utc::now() - Duration::days(max_unused_days.max(0))).timestamp();
        let rows_affected = sqlx::query(
            r#"
DELETE FROM stage1_outputs
WHERE thread_id IN (
    SELECT thread_id
    FROM stage1_outputs
    WHERE selected_for_phase2 = 0
      AND COALESCE(last_usage, source_updated_at) < ?
    ORDER BY
      COALESCE(last_usage, source_updated_at) ASC,
      source_updated_at ASC,
      thread_id ASC
    LIMIT ?
)
            "#,
        )
        .bind(cutoff)
        .bind(limit as i64)
        .execute(self.pool.as_ref())
        .await?
        .rows_affected();

        Ok(rows_affected as usize)
    }

#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
pub enum MemoriesUsageKind {
    MemoryMd,
    MemorySummary,
    RawMemories,
    RolloutSummaries,
    Skills,
}

impl MemoriesUsageKind {
    pub fn as_tag(self) -> &'static str {
        match self {
            Self::MemoryMd => "memory_md",
            Self::MemorySummary => "memory_summary",
            Self::RawMemories => "raw_memories",
            Self::RolloutSummaries => "rollout_summaries",
            Self::Skills => "skills",
        }
    }
}

pub fn memories_usage_from_command(command: &str) -> Vec<(MemoriesUsageKind, MemoryVersion)> {
    let commands = parse_shell_script(command);
    if commands
        .iter()
        .any(|command| matches!(command, ParsedCommand::Unknown { .. }))
    {
        return Vec::new();
    }

    commands
        .into_iter()
        .filter_map(|command| match command {
            ParsedCommand::Read { path, .. } => get_memory_usage(path.display().to_string()),
            ParsedCommand::Search { path } => path.and_then(get_memory_usage),
            ParsedCommand::ListFiles { .. } | ParsedCommand::Unknown { .. } => None,
        })
        .collect()
}

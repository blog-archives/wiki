> 本文以 [Codex 的 GPT-5.2 提示词](https://github.com/openai/codex/blob/a97cf1b72eaad05aa49847bc81d09ceac9327754/codex-rs/core/gpt_5_2_prompt.md)为案例，归纳其模块设计、行为约束与适用边界。

**一份面向执行的系统提示词，需要把「做好任务」展开为模型在具体情境下能够遵循的规则。** 收到请求后是否动手、改文件前读哪些约定、复杂任务如何维护计划、验证到哪里可以停、最后怎样交付，都需要明确的判断依据。Codex 这份提示词把这些决策写成了一套连续的工作流程。

**这些指令围绕一组判断展开，而且有先后依赖。** 先确认自己在什么环境里行动、受哪些约定约束，再决定这次做不做、做到哪，是否需要计划，怎样验证和交付，最后落到具体的工具调用。简单问题可以直接回答，单步修改可以跳过计划，复杂任务才需要持续更新阶段。

| 模块 | 模型需要作出的判断 | 提示词具体写到哪里 |
| --- | --- | --- |
| 身份与能力 | 我在什么环境里，能通过什么方式行动？ | CLI 场景、上下文来源、终端与补丁能力、审批可能性 |
| 指令适用范围 | 当前文件受哪些项目约定约束？ | 目录作用域、嵌套覆盖、直接指令优先、查找时机 |
| 自主性与完成条件 | 该直接执行，还是只讨论？何时结束？ | 默认实施、意图例外、遇阻自解、贯穿实施与验证 |
| 执行边界 | 应该改什么，改到多大？ | 根因修复、既有风格、最小范围、禁止顺手扩张 |
| 计划 | 是否需要拆分，如何反映真实进度？ | 触发条件、正反例、状态转换、范围变化与收尾 |
| 验证 | 验什么、何时验、投入多少？ | 先局部后扩大、项目基础设施、审批模式、停止条件 |
| 沟通与交付 | 用户需要知道什么，怎样呈现？ | 假设与前提、结果与限制、篇幅分级、可定位的文件引用 |
| 工具规范 | 如何把行动意图变成有效调用？ | 搜索工具选择、读取并行、补丁语法、计划参数 |

## 从这个案例提炼的设计方法

**值得迁移的是把高层目标逐步展开为判断条件、行动规则和结束标准。** 例如「自主完成」展开为默认实施、讨论场景例外、遇阻尝试解决、实施后验证并交付；「维护计划」展开为适用情境、拆分示例、状态更新和范围变更；「验证充分」展开为局部起步、逐步扩大、基础设施边界和成本控制。

**不同模块需要不同形式的具体性。** 身份模块说清环境即可，优先级需要作用域与覆盖关系，计划需要状态和正反例，工具需要调用语法，输出需要能被界面正确呈现的格式。提示词的细度取决于模型在此处容易作错什么决定，各章不必写同样多的规则。

**提示词规定期望行为，运行时负责它能够实际强制的边界。** 这份样本展示了如何指导模型，但单靠文本不能证明状态合法性、权限隔离或测试结果真实性已经由程序保障。需要强保证的约束，应进一步落实为工具校验、权限控制或可核实的执行结果。

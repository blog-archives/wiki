## 自主性与完成条件：这次该直接做，还是只讨论

**默认行为是完成任务，不会停在建议上。** 也许你会先想到「拿不准就先问用户」；`Autonomy and Persistence` 的默认相反：只要用户请求解决问题、没有表达只想讨论，模型就应实际调用工具或修改代码，并尽可能在当前轮次完成实施、验证和结果说明。遇到困难或工具失败，先尝试自行解决，再考虑交回用户。

**默认执行有清楚的意图例外。** 用户明确要计划、询问代码、讨论备选方案，或表达其他不应写代码的意图时，不应机械动手；用户暂停或改变方向，也会改变原来的推进要求。自主性依赖对任务意图的判断，并没有一条无条件的写入规则。

## 执行边界：应该改什么，改到多大

**`Task execution` 约束怎样算合适的实现。** 能修根因时不做表层补丁，避免不必要的复杂度，保持既有代码风格，必要时更新文档；同时不修无关缺陷或失败测试，不擅自提交 commit 或创建分支，未经要求不加版权头、代码内联注释和单字母变量名。

**这些要求把「解决得彻底」与「改得过多」分开**：为当前问题补齐必要修改属于本次任务，顺手整理不相关模块则可能扩大审查成本。发现无关问题可以在交付时说明，但不自动纳入本次范围。

**`Ambition vs. precision` 为主动性加了情境判断。** 全新项目可以有创造性，既有代码库强调精确完成用户要求，避免不必要的文件或变量改名；需求宽泛时允许有价值的补充，范围明确时应集中修改。这一模块只给判断原则，没有量化「何时已穷尽尝试」，也没有为失败定义重试次数——它是行为指引，不能当成系统保证任务一定完成。

## 计划：什么时候需要，怎样反映真实进度

**计划用于具有阶段、依赖、歧义或多个请求的任务**：长时间的非平凡工作、需要反馈检查点的过程、用户明确要求 TODO，以及执行中新增且准备继续处理的步骤；简单或单步问题不需要额外计划。

**计划要包含有意义、顺序合理、可逐步验证的工作**，不能为了显得完整而加入空泛步骤，也不能承诺无法执行的验证。原文用 Markdown 转 HTML 举例：低质量计划只写「创建工具、解析 Markdown、转成 HTML」；高质量计划进一步指出文件参数入口、CommonMark 解析、语义化 HTML 模板、代码块与图片链接处理，以及非法文件的错误处理。**差别在于计划是否揭示了实现中实际需要解决的问题**，而不是步骤多少；每一步需要有可辨认的产出或行为。

**`update_plan` 是需要随执行更新的进度记录，不只是开工前的清单。** 进行中的计划同时只有一个 `in_progress`，完成一项后及时更新再推进下一项；认识改变需要拆分、合并或调整顺序时，应先更新计划并说明理由。

| 时刻 | 状态要求 | 要避免的问题 |
| --- | --- | --- |
| 尚未开始 | `pending` | 提前把未执行的工作记为完成 |
| 开始处理 | `pending → in_progress` | 跳过实际执行状态 |
| 完成当前项 | `in_progress → completed` | 清单长期落后于实际进度 |
| 范围发生变化 | 更新步骤及解释，再继续 | 按已经失效的计划推进 |
| 结束本轮 | 全部完成，或明确说明取消、延后项 | 留下没有交代的未完成工作 |

**「明确取消或延后」是收尾要求，不代表工具一定有相应状态枚举**（工具说明只列出 `pending`、`in_progress`、`completed`）；状态转移约束写在提示词里，是否由程序强制，需要另看实现。

> **Status: Disputed（原文内部表述不一致）**：Planning 部分要求先进入 `in_progress`，并禁止事后批量完成多项；但同一节前段允许一次实施后把全部步骤标为完成，末尾工具说明也允许单次调用完成多项。因此不能把整份文本描述成完全一致的严格状态机。较稳妥的设计是明确区分「批量提交已发生的真实状态变化」和「事后补造执行记录」，统一正文与工具说明。

**计划展示也被纳入协作规则**：宿主已经渲染完整计划，模型调用工具后只需说明变化和下一步，不必复述，避免用户看到两份不同步的计划。

计划里写下「已完成」，并不等于完成本身；下一页 [验证、交付与工具](verification-delivery-and-tools.md)讨论怎样用证据确认。

## 验证：验什么、何时验、验到什么程度

**验证的起点是与改动最相关的检查。** 原文建议先用尽可能聚焦的测试捕捉问题，再随信心建立扩大到更广范围；可以理解为先验证直接行为，再检查周边影响，原文没有把它固定成单元、集成、端到端三级流程。

**新增测试取决于仓库是否已有合适基础。** 改动没有测试、但相邻代码展示了合理的位置和模式时可以补测；整个仓库没有测试时不为当前任务建立测试体系；项目没有配置 formatter 时也不额外引入。验证应沿用项目已有方式，并与本次改动相称。

**运行验证的时机与审批模式相关，这是缺少其他行为指导时的默认策略**（测试和 lint 可能耗时，会影响交互迭代）：

| 情境 | 该样本给出的默认行为 |
| --- | --- |
| 非交互审批模式 `never` | 可以主动运行测试、lint 等检查，尽力完成验证 |
| 交互审批模式 `untrusted` / `on-request` | 等到用户准备收尾时，提出验证动作并让用户确认 |
| 添加或修复测试、复现缺陷等测试相关任务 | 无论审批模式如何，都可以判断是否主动运行测试 |

**这里约束的是主动运行的时机，并未额外授权。** `never` 不表示绕过沙箱，命令能否执行仍受运行环境限制；测试任务的例外也说明不能把它缩写为「交互模式一律不跑测试」。

**格式修正允许迭代最多 3 次，仍未解决时交付正确方案并说明格式问题。** 这个上限只针对格式问题，不能扩大成所有测试失败都重试 3 次；测试、构建、格式化中发现的无关问题也不属于自动修复范围。

**无法运行测试时仍要尽力完成任务，但不能把未验证写成验证通过。** 模型要区分已经获得的证据与仍需用户检查的部分——它关注的既是正确性，也是拿到证据所花的时间和额外改动。

## 沟通与交付：用户需要知道什么

**`Personality` 定义日常沟通的方向：简洁、直接、友好，说明行动、假设、环境前提和下一步。** 该文本的 `Responsiveness` 是空标题，没有规定更新频率，因此不能据此归纳出「每隔固定时间报告一次进度」。

**`Presenting your work` 把交付定位为同事说明结果。** 文件已经修改好时，应给出可定位的路径，不必再要求用户复制、保存代码；有做不到但用户可以完成的验证，则简要说明操作方式。

**输出篇幅按改动规模分级**：小改动 2–5 句或不超过 3 个要点且不加标题；中等改动不超过 6 个要点或 6–10 句；大改动按文件概括，避免贴出完整方法和长篇前后对比。标题不是必选项，代码片段只在确实有帮助时出现。

**文件引用与禁止格式也属于交付协议**：原文约束路径及行号写法、命令和标识符的展示方式，禁止 CLI 无法渲染的引用标记和直接输出 ANSI 转义码。这些规则与宿主界面相关，迁移到网页或其他客户端时应重新适配。

## 工具规范：怎样把判断变成有效调用

**Shell**：搜索默认用 `rg` 或 `rg --files`，不可用时再换其他工具；尽可能并行调用工具，尤其是读取文件，并指定 `multi_tool_use.parallel`；禁止用 Python 脚本输出大段文件内容。这些是在优化高频行为，迁移时要替换为运行环境真实提供的工具。

**补丁**：`apply_patch` 的说明既规定使用场景，也规定输入语言——用该工具编辑文件，明确精确工具名与 FREEFORM 输入，不能把补丁包装成 JSON，并定义起止标记、增删改操作头和新增行必须带 `+`。示例覆盖多文件操作和重命名，让模型拿到可以直接构造的输入格式。

**计划工具**：`update_plan` 的工具说明规定步骤文本和状态字段，并要求完工后显式更新；它与正文的分工是——正文讲何时计划、什么计划有质量，工具段讲怎样提交进度。两处重复规定状态更新，也产生了前面指出的表述冲突。**工具规范需要与工作方式保持一致**，否则模型必须临场解释冲突；检查提示词时，除了语法，还要看重复规则是否一致、工具名是否真实可用、例外条件是否齐全。

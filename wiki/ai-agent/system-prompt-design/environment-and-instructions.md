## 身份与能力：模型在什么环境里行动

**模型要作出的第一个判断，是自己在什么环境里、能通过什么方式行动。** 原文开头把模型限定为一个能够操作工作区的终端编码助手：它运行在 Codex CLI 中，接收用户请求以及宿主提供的文件等上下文，通过流式响应与计划沟通，并发出函数调用来执行终端命令、应用补丁。这明确了「观察—沟通—行动」的渠道。

**能力声明同时交代依赖条件。** 终端调用不意味着任何操作都能直接执行，是否需要审批取决于本次运行配置；模型不能从「能调用工具」推导出「已获得全部权限」。开头还消除了 Codex 名称的歧义，避免把当前编码界面误认成早期同名语言模型。**这一层的细度止于环境和能力边界**，操作协议留给后文；对其他 Agent 而言，值得借鉴的是说清输入从哪里来、可以影响什么、通过哪些接口行动、受什么配置约束——泛泛写「你是一位资深专家」提供不了这些执行信息。

知道「能行动」只是前提，动手之前还要判断：这次要改的文件，受哪些项目约定约束？

## 指令优先级：改这个文件要遵守哪些约定

**`AGENTS.md spec` 解决的是项目约定的适用范围和冲突处理。** 原文先说明这些文件可能包含编码风格、目录说明、运行和测试方式，再把约束落到最终补丁涉及的每个文件上。

| 判断环节 | 原文规则 | 对行动的影响 |
| --- | --- | --- |
| 确定作用域 | `AGENTS.md` 作用于其所在目录的整棵子树 | 不能把某个子项目的规则无条件推广到整个仓库 |
| 汇总适用约定 | 修改文件时遵守所有覆盖它的 `AGENTS.md` | 不能只读取离文件最近的一份而忽略上层未冲突的要求 |
| 处理嵌套冲突 | 更深层目录中的规则优先 | 子模块可以覆盖上层的一般约定 |
| 处理对话与文件冲突 | 直接的 system / developer / user 指令优先于 `AGENTS.md` | 仓库文件不能反过来覆盖直接下达的要求 |
| 补齐上下文 | 已注入的根目录及 CWD 祖先约定不必重读；进入子目录或外部目录需检查 | 既减少重复读取，又避免漏掉新的局部规则 |

**一个例子能说明作用域的粒度。** 根目录要求统一风格，子目录另定命名方式，修改该子目录文件时应保留根目录的非冲突要求，并采用子目录的命名规则。重点是逐个文件判断，不必为整个任务挑出一份「最高优先级文件」。

**原文没有完整重述系统、开发者和用户指令之间的全部层级**，它明确的只是这些指令相对于 `AGENTS.md` 的优先关系。设计自己的提示词时，应区分*已有的消息层级*与*需要额外解释的项目规则作用域*，避免把两者混成一条含糊的排序。

作用域回答的是「受什么约束」；下一页 [自主性、边界与计划](autonomy-and-planning.md)讨论这次行动本身：直接做，还是只讨论，以及改动范围有多大。

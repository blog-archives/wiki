> 本文根据最初提供的 [预算源码](../../raw/2026-09-22-153917.md#q3)、[估算链路](../../raw/2026-09-22-153918.md#q5)与 [压缩源码](../../raw/2026-09-22-153919.md#q1)整理，并补查上游实现。

**历史可以持续保存，模型每次能读取的上下文却有上限。** 因此，[存储](context-storage.md)解决“信息放在哪里”，窗口维护解决“下一次请求带上哪些内容”。Codex 在写入时限制大结果，在执行间隙检查容量，必要时缩减或重建当前窗口。

## 预算检查：计算占用，再比较阈值

**预算检查要回答：当前上下文占了多少空间，是否需要先压缩再继续。** 为此，程序设置一个压缩阈值，并计算用来与它比较的 token 用量。

以一次工具调用为例，可以把核心思路简化为：

```text
最近一次模型返回的用量（usage）+ 随后新增工具结果等内容的 token 估算 → 与压缩阈值比较
```

**已有统计直接用，尚未统计的内容再估算。** 模型返回“读取文件”的工具调用后，Codex 才执行读取、取得文件内容。这些内容还没有包含在刚才的 usage 中，因此由程序按内容长度近似换算 token，再加到已有用量上。

**参与比较的是相加后的用量。** 达到阈值且还需要继续执行时，就先压缩，再发起下一次模型调用。阈值用于控制何时减量，不必等到模型请求真正超限报错。[计量与阈值源码](../../raw/2026-09-22-153918.md#q5)。

## 时间节点：写入时限长，步骤结束后检查

**一次用户请求可以包含多次模型调用；主循环的检查发生在每个模型步骤结束后，而不是等整个任务完成。** 典型工具循环如下：

```text
调用模型，取得响应和 usage
    ↓
执行工具，将结果按截断策略写入当前历史
    ↓
将最近一次 usage 与此后新增内容的估算合并
    ↓
用合并后的窗口用量与阈值比较
    ↓
还需要继续，并且比较结果已到限或显式请求新窗口？
    ├─ 否：继续正常执行或结束本轮
    └─ 是：先压缩 / 重建窗口，再发起下一次模型调用
```

这是 `run_turn` 中的实际顺序：采样与工具处理完成后取得 `token_status`，再判断 `needs_follow_up && (新窗口请求 || token_limit_reached)`。**它既是上一步完成后的检查，也是下一次普通模型请求前的处理；不需要等服务端报超限才开始压缩。** [循环源码](../../raw/2026-09-22-153917.md#q3)。

此外还有两个轮次边界检查：

| 时间点 | 条件与处理 |
| --- | --- |
| 新一轮开始 | 按已有历史计算的窗口用量达到阈值时先压缩；模型切换也可能需要先处理旧窗口 |
| 一轮结束 | 配置了结束时压缩阈值、达到阈值，且未启用 TokenBudget、没有待处理输入、未取消时，可执行压缩 |

**轮前检查并不等于已经预估了这次尚未写入的新输入。** 该位置位于新用户消息和上下文更新写入之前，源码仍有 TODO 要补这部分预判。因此，不能把整个流程说成“每次请求前都精确算好了完整 Prompt”。[轮次边界源码](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs)。

## 怎样减量：局部截断与整窗替换

**Codex 组合使用不同层次的处理，并不是超限后统一删除最旧的若干条消息。**

| 方式 | 在什么时候用 | 具体处理什么 |
| --- | --- | --- |
| 写入时截断 | 工具结果记录进当前历史时 | 按 `TruncationPolicy` 限制单条输出，控制一次调用带来的突增 |
| 压缩请求前裁剪 | 远程压缩的输入估算仍超过窗口时 | 在历史副本中缩短可重写的工具输出，让压缩请求本身尽量装得下 |
| 模型摘要 | 走本地或远程摘要压缩路径时 | 用压缩后的条目替换旧历史；本地路径生成摘要，并按预算保留部分近期用户消息 |
| 新窗口重建 | 启用 TokenBudget 的压缩路径时 | 跳过模型摘要，重建当前指令与环境，并按配置保留部分 developer 消息 |

前两种控制内容体积，后两种替换整个当前窗口。**“本地摘要”仍会调用模型，只是由客户端组织流程；TokenBudget 的窗口重建则不自动生成历史摘要。** 后者能腾出空间，但后续工作能否延续，依赖必要状态是否已保存并带入新窗口。[截断与摘要源码](../../raw/2026-09-22-153919.md#q1)、[窗口重建源码](../../raw/2026-09-22-153917.md#q4)、[TokenBudget 实现](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact_token_budget.rs)。

这里的窗口重建不同于固定保留最后若干条的 **滑动窗口**。界面的历史分页也只是显示旧消息，不能当作模型自动按需取回历史的机制。

## 处理之后：用新历史继续，承担信息损失

**压缩成功后，替换当前历史、记录恢复基线、更新用量，再用新窗口继续调用模型。** 它缩短的是后续请求携带的上下文，不会清零任务累计消耗，也不代表历史文件被整体删除。

截断可能丢失细节，摘要可能遗漏约束，重建窗口可能丢失进度；摘要本身还增加模型调用。旧内容能否找回，取决于它是否另行保存，不能仅凭 rollout 存在就保证原文完整。下一篇 [上下文完整性](context-integrity.md)讨论如何检查这些损失。

> **Status: Disputed** — 原问答的部分概括与代码不符：用于阈值比较的用量包含 usage 基线与本地补估；远程压缩前裁剪逆序处理且遇不可重写项即停止，不能称为统一“最旧优先”；`COMPACT_USER_MESSAGE_MAX_TOKENS` 限制的是保留用户消息的预算，不是摘要长度。本文以具体实现为准。

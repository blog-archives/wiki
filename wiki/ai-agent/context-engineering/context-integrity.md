**压缩解决“装不装得下”，完整性解决“留下的内容还能不能支持正确执行”。** 内容变短后，需要检查三个方面：工具调用与结果是否对应、用户要求是否仍然有效、关键结论是否还有依据。

## 具体怎么压缩：程序定规则，模型做整理

**摘要压缩不是让模型随意删消息，而是让模型提炼工作进展，再由程序组成新的上下文。** 以 Codex 的本地摘要路径为例，过程可以简化为：

```text
当前历史 + 专门的摘要提示词
    → 调用模型，生成交接摘要
    → 程序选取按预算保留的用户消息
    → 组合保留消息与摘要，按阶段补入当前指令和环境
    → 替换当前历史，供下一次请求使用
```

Codex 会复制当前历史，加入摘要提示词，单独发起一次模型请求；得到摘要后，按预算优先保留近期用户消息，再重建历史。当前指令与环境可能在重建时加入，也可能在下一轮重新注入。**摘要负责语义上的取舍，程序负责消息选择、结构和替换。** 这条路径不适用于跳过摘要的 TokenBudget 窗口重建。[摘要调用源码](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs)、[历史重建片段](../../raw/2026-09-22-153919.md#q1)。

### 提示词怎样指导取舍

**目标应是让后续模型能接着工作，而不是把对话重新讲一遍。** Codex 的默认提示词要求为接手任务的模型生成简洁、有结构的交接摘要，保留进度与关键决策、重要约束与偏好、明确的下一步，以及必需的数据和引用。[默认摘要提示词](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/compact/prompt.md)。

借鉴这个思路，可以使用下面的提示词。**这是面向自己实现 Agent 的示例，不是 Codex 原文：**

```text
请将以下历史整理成供另一个模型继续任务的交接摘要，不继续执行任务。

保留：当前目标和仍有效的要求；已完成工作及验证结果；
未完成事项、阻塞原因和下一步；必要的文件位置与关键证据。

合并重复讨论，省略已无后续作用的过程和冗长输出。
区分事实、猜测与待验证事项；保留会影响下一步决策的不确定性。
只发起但未确认结果的操作，不得写成“已完成”。
若要求已被明确修改，以当前有效要求为准；冲突不明时标注待确认。

按“目标与约束 / 已完成与证据 / 未完成与下一步”组织，尽量简洁。
```

### 压缩前后，内容怎样变化

下面是一个只读排查任务的设计示例，不是实际模型运行结果：

| 压缩前的历史 | 压缩后的交接内容 |
| --- | --- |
| 用户要求只读排查测试失败 | 目标：定位失败原因；约束：不修改文件 |
| 多次读取源码，返回大量重复片段 | 保留相关文件和函数位置，省略重复全文 |
| 测试输出含大量日志和一个关键错误 | 保留失败的测试、关键错误和日志位置 |
| 曾猜测是配置问题，但尚未验证 | 明确标注假设；下一步检查相应配置 |

**已经完成的工具交互可以转成“做了什么、得到什么证据”的摘要，不必永久保留每条原始调用。** 如果新窗口仍保留原始工具消息，就要维护调用与结果的配对；如果还有待返回的工具结果，实现上应保留其关联，或等结果完成后再压缩，不能只留下一个无法对应的结果。后者是设计方针，不是这段摘要代码自动保证的能力。

## 调用与结果：正文可以缩短，关系不能断

**工具调用和工具结果是一组有关联的记录。** 模型发出“读取文件”的调用，工具返回文件内容，两者通过 `call_id` 对应。截断文件内容时可以保留这个关联；删除历史时，则要避免只留下一个无法解释的结果。

Codex 在组装模型输入前会检查调用与结果的配对，为缺失结果的调用补齐相应记录，并清理孤立输出。**这种处理保证请求结构可用，不代表工具真的执行成功。** 缺失结果的占位记录不能当作成功证据，部分具名外部工具事件也有独立输出的规则。[配对处理源码](../../raw/2026-09-22-153919.md#q3)。

并发执行时，结果可能不按调用顺序返回，所以应靠调用身份关联，而不能只看消息位置。无论裁剪、重试还是恢复，都应保留“这个结果属于哪次操作”。

## 用户要求：仍然有效，比出现得晚更重要

**最近的消息不一定最重要，早期要求也可能一直约束整个任务。** 例如用户最开始说“只读检查，不修改文件”，即使后面出现了很多日志，这条要求也不能因为太旧而失效。

Codex 的本地摘要流程会按预算保留部分近期用户消息，并让模型总结历史；部分特性还会单独保留指定内容。它们有助于延续信息，但不能保证所有有效要求都完整留下。[要求保留机制](../../raw/2026-09-22-153919.md#q4)。

对于自己的 Agent，可以按下面的思路安排保留内容：

| 内容 | 为什么需要保留 |
| --- | --- |
| 当前目标与有效约束 | 防止换窗后改变任务方向或越过限制 |
| 已验证结论与证据位置 | 避免重复工作，并支持回查 |
| 未完成事项与阻塞条件 | 让后续执行知道从哪里继续 |
| 已撤销的要求与尚未验证的假设 | 避免把旧规则或猜测继续当作事实 |

这是设计建议，不是 Codex 已实现的统一状态字段。对必须严格执行的限制，还应使用相应的程序控制：例如只读任务可以限制写入权限。**让模型记住规则，与让工具遵守规则，是两层保障。**

## 验证：先看输入有没有保住，再看任务做得怎样

**内容仍在请求里，不代表模型一定会正确使用；请求变短，也不代表效果一定更好。** 因此，验证应分成两层：

| 层次 | 检查什么 | 怎么检查 |
| --- | --- | --- |
| 上下文构造 | 调用是否配对，目标、约束和证据是否保留 | 捕获压缩后的实际请求，检查内容和结构 |
| 任务效果 | 是否完成任务、遵守约束、减少重复与错误 | 让真实模型执行相同任务，比较不同上下文处理方式 |

例如检查“只读”要求：先确认它出现在压缩后的请求中，再观察后续是否发生写入。前者定位信息保留问题，后者检验实际行为。做对照时，应保持任务要求不变，只调整要研究的历史或证据内容。[测试与评测材料](../../raw/2026-09-22-153919.md#q5)。

**越重要、越需要反复更新的信息，越值得从普通历史中单独维护。** 下一篇 [任务状态](task-state.md)讨论怎样保存目标与进度，让它们跨越窗口继续生效。

> **Status: Disputed** — 原问答曾将部分保留类型概括为全部能力，但所附测试还包含指令恢复；应按具体场景理解。它还建议用固定模型回复比较任务成功率：固定回复只能验证客户端构造，不能检验模型对上下文变化的反应；加入新的矛盾用户指令，也会改变任务本身。

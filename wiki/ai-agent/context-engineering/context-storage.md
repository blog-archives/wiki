> 本文根据 DeepWiki 的 [Codex 历史持久化问答](../../raw/2026-09-21-221655.md#q7)、[上下文源码](../../raw/2026-09-22-153917.md)与 [任务状态问答](../../raw/2026-09-22-153920.md)整理。

**Agent 需要分别保存历史经历、当前模型输入和任务状态。** 历史用于回溯与恢复，当前输入服务于下一次决策，任务状态让程序直接取得目标、进度和预算。

| 保存什么 | 保存在哪里 | 主要用途 |
| --- | --- | --- |
| 会话历史 | 磁盘上的 rollout 文件 | 记录发生过什么，支持回溯与恢复 |
| 当前模型窗口 | 内存中的 `ContextManager` | 准备下一次模型请求的历史输入 |
| 持久目标与预算 | SQLite 的 `thread_goals` 表 | 查询和更新当前目标、状态及消耗 |
| 计划步骤 | 工具调用及计划历史事件 | 记录计划内容与步骤状态 |
| 正在执行的任务 | 内存中的 `ActiveTurn` 等对象 | 控制运行、等待、取消与清理 |

## Rollout：一个会话对应一份历史文件

### 保存在哪里，怎样对应

**在本地文件存储模式下，一个 thread（会话）对应一个 rollout 文件。** 同一会话内的多轮交互、模型请求和工具执行，持续写入这份文件。

- **保存位置**：Codex 的 sessions 目录，通常在 `~/.codex/sessions/` 下。
- **文件名称**：`rollout-<时间>-<会话标识>.jsonl`，目录可以按日期组织。
- **对应关系**：一个会话一份历史；一次用户输入或一次模型请求不单独对应一个文件。
- **上下文换窗**：仍属于原会话，在原历史中记录新的窗口基线。

**会话、单次执行和上下文窗口是三个不同的范围。** 会话可以持续多轮；一次执行可能多次调用模型；上下文窗口则决定某次调用能看到多少历史。文件跟随会话，窗口可以在会话内重建。[文件与记录结构](../../raw/2026-09-21-221655.md#q7)。

### 文件格式：每行一条 JSON 记录

**rollout 使用 JSONL 格式，新内容按顺序追加到文件末尾。** 每行记录包含时间、类型和具体内容；部分记录还带序号等元数据。

下面是省略可选字段的格式示意：

```jsonl
{"timestamp":"<时间>","type":"session_meta","payload":{"id":"<会话 ID>","cwd":"<工作目录>"}}
{"timestamp":"<时间>","type":"response_item","payload":{"type":"message","role":"user","content":[{"type":"input_text","text":"检查测试失败原因，只读，不修改。"}]}}
{"timestamp":"<时间>","type":"response_item","payload":{"type":"message","role":"assistant","content":[{"type":"output_text","text":"先检查测试代码和错误日志。"}]}}
```

| 字段 | 含义 |
| --- | --- |
| `timestamp` | 记录时间 |
| 外层 `type` | 记录类别，如会话信息、消息或执行事件 |
| `payload` | 该条记录的具体内容 |
| `payload.type` | 内容的进一步分类，如消息、工具调用或工具结果 |
| 消息的 `role`、`content` | 谁说的，以及说了什么 |

**JSONL 适合不断增长的会话历史：每次追加一行，无需重写整个文件。** 读取时逐条解析，既可以重建对话，也可以分析执行过程。[格式与示例](../../raw/2026-09-21-221655.md#q7)。

### 文件里存什么

**rollout 同时保存对话内容、工具执行记录和恢复所需的状态。** 用户看到的聊天文字只是其中一部分。

| 内容 | 主要记录类型 | 保存目的 |
| --- | --- | --- |
| 会话 ID、来源、初始目录 | `SessionMeta` | 确定会话身份与起始环境 |
| 用户消息、助手消息 | `ResponseItem` | 保留任务要求、补充信息和已有回答 |
| 工具名称、参数、调用 ID | `FunctionCall` 等调用项 | 记录请求执行的操作 |
| 工具输出、失败信息 | `FunctionCallOutput` 等结果项 | 保留执行结果，以 `call_id` 对应调用 |
| 开始、完成、中断等事件 | `EventMsg` | 判断执行是否结束、在哪里中断 |
| 模型、权限、环境等状态 | `TurnContext`、`WorldState` | 恢复相应执行条件与上下文基线 |
| 压缩后的窗口基线 | `Compacted` | 记住后续从哪份精简历史继续 |
| 用量、计划及目标更新 | 用量记录与相关事件 | 支持记账、展示与状态回溯 |

**工具调用和工具结果分开保存，才能区分“打算做什么”和“实际得到什么”。** 例如读取文件的调用已经发出，结果却可能是文件不存在；仅保存助手总结会丢失这个差别。执行开始、完成、中断也用明确事件记录，程序不必根据助手文字猜测状态。[记录类型与筛选规则](../../raw/2026-09-21-221655.md#q8)。

### 怎样写入

**历史采用追加写入，由后台 writer 串行处理。** 用户补充要求、工具返回结果、执行结束时，分别产生新的记录，保留变化过程。

```text
产生记录 → 筛选需要保存的内容 → 进入写入队列 → 追加到 rollout
```

**入队与写入完成是两个时刻。** 需要确保后续读取者能看到此前记录时，通过 `flush` 等待 writer 确认。例如中断通知可能触发客户端立即重读历史，就需要处理这个先后关系。[写入与 flush](../../raw/2026-09-21-221655.md#q6)。

持久化会筛选内容，部分流式增量和临时条目不会独立落盘。因此，rollout 保存的是需要保留的会话记录，并非整个运行过程的逐字录像。

## ContextManager：内存中的当前模型窗口

**`ContextManager` 保存下一次模型请求使用的历史，主要内容放在 `items` 序列中。** 它还维护 token 信息、历史版本和环境更新基线。新消息与工具结果进入这里后，就能参与后续决策。[上下文结构](../../raw/2026-09-22-153917.md#q6)。

```text
运行中：新消息 / 工具结果 → 当前窗口 → 组装 Prompt → 调用模型
重启后：rollout → 历史重建 → 当前窗口 → 组装 Prompt
```

### 为什么历史文件与当前窗口分开

**磁盘历史保留过去，内存窗口选择现在需要的信息。** 两者可以包含同一条工具结果，但保留标准不同。

| 情况 | rollout 历史 | 当前模型窗口 |
| --- | --- | --- |
| 新工具结果到达 | 按策略追加记录 | 加入后续决策所需的结果 |
| 执行中断 | 保存中断事件等信息 | 保留模型需要理解的中断信息 |
| 历史压缩 | 保留旧记录，追加压缩记录 | 用精简历史替换旧窗口 |
| 进程退出 | 文件继续存在 | 内存对象随进程消失 |
| 会话恢复 | 提供历史与检查点 | 根据读取结果重新构建 |

**当前窗口不是历史文件的完整缓存。** 执行事件可能只供程序读取，旧工具输出可能已经被摘要替代；模型不需要每次重读全部磁盘记录。内存窗口方便持续更新，磁盘历史则保证进程结束后还有恢复依据。[历史与模型输入的区别](../../raw/2026-09-21-221655.md#q10)。

### 恢复为什么需要检查点

**检查点保存“后来已经改用哪份历史继续”。** 恢复时，以适用的 `replacement_history` 为基线，再处理后续记录及回滚边界；没有可用检查点时，再走相应的历史重建路径。

如果忽略检查点，把压缩前的旧内容全部重新装回窗口，就恢复不出原来的上下文状态。检查点的生成方式见 [预算与压缩](budget-and-compaction.md)。

## 任务状态：当前值、计划与执行资源分别保存

### Goal：数据库保存当前目标与预算

**启用并创建持久 Goal 后，目标保存在 SQLite 的 `thread_goals` 表中，通过 `thread_id` 关联会话。** 程序可以直接查询、更新字段，不必每次从长对话中重新推断。[目标读写](../../raw/2026-09-22-153920.md#q1)。

| 字段 | 含义 |
| --- | --- |
| `thread_id`、`goal_id` | 所属会话与目标身份 |
| `objective` | 当前目标 |
| `status` | 活跃、暂停、阻塞、完成等状态 |
| `token_budget`、`tokens_used` | 目标预算与已用 token |
| `time_used_seconds` | 时间消耗 |
| 创建、更新时间 | 状态的时间信息 |

**这类数据需要精确查询、条件更新和事务，适合独立的结构化存储。** 模型窗口压缩后，目标和累计预算仍然存在；修改目标也不必覆盖原始用户消息。不过，Goal 不会自动把全部自然语言要求转成字段，普通会话也不必创建 Goal。

**数据库保存当前值，rollout 保存变化过程。** 目标更新可以同时形成 `ThreadGoalUpdated` 历史事件：查询“现在目标是什么”读当前行，回顾“目标怎样变过”读历史。这是职责分离，不要求同一信息只能出现一次。[目标更新事件](../../raw/2026-09-21-221655.md#q8)。

### Plan：步骤与状态进入会话历史

**Plan 保存步骤文字和步骤状态，可以通过工具调用及计划事件进入 rollout。** 其中 `ItemCompleted` 的 `TurnItem::Plan` 可以落盘，无需为此单独建立一张计划表。[计划持久化](../../raw/2026-09-21-221655.md#q9)。

保存计划用于记录和展示进度；让程序自动按步骤执行，还需要另外的调度逻辑。**“计划里写着下一步读日志”不等于执行器已经保存了一个可自动恢复的下一步动作。**

### ActiveTurn：内存控制当前执行

**`ActiveTurn` 等运行时对象保存当前任务及取消、等待所需的句柄。** 它们控制正在运行的程序，留在当前进程的内存里。

进程退出后，原任务和连接随之消失。恢复时读取持久化的身份、历史与设置，再创建新的执行任务；**恢复的是继续工作所需的数据，而不是旧进程的调用栈。** 具体流程见 [中断与恢复](../interrupt-resume/codex-interrupt-recovery.md)。

## 配置、工具和外部资料

**配置负责生成请求，外部资料保留原文，会话历史记录本次实际使用的内容。** 不必把所有信息都复制进 rollout。

| 内容 | 保存或存在的位置 | 进入请求的方式 |
| --- | --- | --- |
| 基础指令与会话设置 | `Session` 持有的配置及其来源 | 请求时渲染；恢复所需设置另有上下文记录 |
| 工具定义与实现 | 工具注册、路由及本步 `StepContext` | Prompt 带可见工具定义，执行时调用处理器 |
| 环境和权限 | 当前执行配置及状态快照 | 渲染初始说明或变化片段 |
| 仓库文件、外部资料 | 原文件或外部服务 | 读取后把相关结果加入历史 |
| 跨会话经验 | SQLite 候选记录、记忆目录中的 Markdown | 从历史提取，再由未来任务选择使用 |

**工具实现留在程序里，工具调用与结果留在历史里；文件全文留在工作区，本次读取的证据进入上下文。** 这样可以独立更新工具、配置和资料，也能回顾当时观察到了什么。跨任务经验的形成见 [长期记忆](long-term-memory.md)。

## 一个任务中，各份数据怎样配合

以“只读检查测试失败原因”为例，假设另外创建了持久 Goal。下面展示各层的逻辑变化，不表示它们在同一事务中更新。

| 时刻 | rollout | 当前模型窗口 | Goal 与运行时 |
| --- | --- | --- | --- |
| 接收任务 | 记录要求、上下文和执行边界 | 加入任务与环境 | 保存目标，启动执行 |
| 读取文件 | 追加调用和结果 | 加入读取证据 | 完成工具操作，继续循环 |
| 压缩历史 | 追加压缩记录与新基线 | 改用精简历史 | 目标与累计预算保留 |
| 中断退出 | 记录中断信息并处理写入确认 | 停止推进，退出后内存消失 | 清理执行资源；Goal 按自身规则处理 |
| 之后恢复 | 提供检查点、后续记录和设置 | 重建模型输入 | 读取 Goal，创建新的执行任务 |

**历史可回溯、窗口可精简、目标可独立更新、执行资源可重新创建，这就是分开保存的原因。** 历史可以继续增长，但模型每次能处理的窗口有限。接下来需要解决：什么时候减量、怎样选择保留内容，以及减量后能否继续正确工作。这就是下一篇 [预算与压缩](budget-and-compaction.md)的主题。

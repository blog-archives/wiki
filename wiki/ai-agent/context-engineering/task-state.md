**历史记录“过去发生了什么”，任务状态记录“现在要做什么、做到哪里”。** 长对话里会混合旧方案、失败尝试和已完成步骤。把需要持续维护的信息单独保存，可以减少恢复时重新推断的工作，也避免它们随着上下文压缩而丢失。

## 保存什么：目标、计划与执行记录各有职责

| 对象 | 主要内容 | Codex 中的保存方式 |
| --- | --- | --- |
| Goal | 当前目标、状态、任务预算与累计消耗 | SQLite 的 `thread_goals` 表 |
| Plan | 步骤与各步骤的状态 | 计划工具更新，相关记录可进入 rollout |
| 对话与工具历史 | 用户要求、调用、结果和执行经过 | rollout 历史文件 |
| 当前运行任务 | 正在执行的任务、取消与控制句柄 | 进程内的运行时状态 |

**它们分开，是因为更新方式和生命周期不同。** Goal 需要直接查询和持续记账；Plan 用于表达工作安排；历史保留经过和证据；运行时句柄只对当前进程有效。具体存储关系见 [上下文存储](context-storage.md)。

计划列出“下一步运行测试”，并不代表程序一定会自动执行它。**保存计划与调度执行是两件事。** 同样，Goal 的 `blocked` 状态只能表示暂时无法推进，阻塞原因、证据和产出位置仍可能需要从历史或文件读取。[Goal 与 Plan 材料](../../raw/2026-09-22-153920.md#q1)。

## 怎样更新：状态改变后，还要让下一步能读到

**状态要随着执行推进，并把影响下一步决策的变化带回模型。** 设计自己的 Agent 时，可以沿着下面这条链路理解：

```text
目标改变、步骤完成或发现阻塞
    → 更新相应状态与证据
    → 将当前目标、进度和下一步所需信息放入请求
    → 模型据此继续执行
```

Codex 的 Goal 由工具及生命周期逻辑维护，Plan 由模型调用计划工具更新。材料还描述了将目标更新、继续任务和预算限制转成提示消息的机制；这体现了 **“保存状态 → 转成模型可见内容”** 的分工，但未附完整的请求回注链路。[状态更新材料](../../raw/2026-09-22-153920.md#q1)。

**任务预算与窗口预算也要分开。** 窗口预算控制一次请求能携带多少内容，Goal 预算控制任务累计消耗。压缩可以腾出窗口空间，但不会把已经花掉的任务预算清零。

## 怎样恢复：恢复工作依据，再重新执行

**恢复任务需要同时找回目标、进度和证据。** Codex 从数据库恢复 Goal，从 rollout 和压缩检查点重建当前历史，再建立新的运行时任务继续推进；旧进程的调用栈和控制句柄不会因此原地恢复。[恢复流程](../../raw/2026-09-22-153920.md#q2)。

恢复后最需要确认的是：目标是否仍有效、哪些步骤有完成证据、还有什么未完成。只有一个“进行中”状态，或者只有一段历史摘要，都不足以回答全部问题。

**没有完成记录，不代表操作没有发生。** 例如工具已经写入文件，却在结果保存前退出。恢复后直接重做，可能造成重复操作。对不能重复的动作，应查询实际结果，或使用业务幂等键等机制；聊天历史和工具调用 ID 不能独自保证只执行一次。相关机制见 [中断恢复](../interrupt-resume/codex-interrupt-recovery.md)。

任务状态服务于同一个任务的延续；任务结束后，仍可能有经验值得用于其他任务。下一篇 [长期记忆](long-term-memory.md)讨论如何提取和复用这些信息。

> **Status: Disputed** — 原问答称计划“仅当轮通知、没有持久化”，但 [持久化源码](../../raw/2026-09-21-221655.md#q9)允许 Plan 事件写入 rollout；这仍不等于独立的执行状态机。原问答还将工具执行记录解释为“不会重复执行”，所附代码不足以支持这一保证。

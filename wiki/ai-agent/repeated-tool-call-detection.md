**模型可能因结果不满意或出错，对同一个工具反复发起参数完全相同的调用，形成没有进展的循环。** 直觉上可以给每次调用算一个「工具名 + 参数 + 返回结果」的指纹，指纹重复到一定次数就强制退出；但 Claude Code 与 Codex 都没有做这种前置查重，**实际防护只有工具调用次数/字节上限这一层兜底**。这个差距适合当作极端场景的面试题：先讲清两家为什么没做，再给出指纹方案的设计要点与边界。

## 问题：不同 call_id 的相同调用

关键前提是 **「相同调用」不等于「相同 call_id」**。每次工具调用都带一个由框架生成的唯一 `call_id`，模型完全可以连续发出 `call_id` 不同、但工具名与参数逐字节相同的调用。按 `call_id` 去重拦不住这种情况，只有按 **内容**（工具名 + 参数）比较才能识别。

问题分两种程度：一是模型自己没意识到重复，无意义地重跑；二是结果让它不满意，它换个 `call_id` 再试同样的调用，越试越不推进。两者都表现为「表面在动，任务不动」。

## 两家实际做了什么

### Claude Code：通用层没有，插件层只有一次认领

引擎层 **没有** 面向所有工具调用的通用重复检测。唯一相关的是 `security-guidance` 插件里的 `_claim_bash_hook_once`，它解决的问题很具体：`hooks.json` 下 `git commit:*` 与 `git push:*` 两条 `if` 配置会被独立触发，于是 `git commit -m x && git push` 这种复合命令会以 **同一个 `tool_use_id`** 把脚本拉起两次。第二次调用在「认领」竞争中失败，提前退出并上报 `bash_hook_dedup` 指标。

```python
if not _claim_bash_hook_once(input_data):
    print(json.dumps({"metrics": {"bash_hook_dedup": True}}), flush=True)
    sys.exit(0)
```

这是 **配置层面的去重，不是语义查重**：它按 `tool_use_id` 去重（同一个调用被触发两次），而不是按「工具名 + 参数」判断模型是否重复请求。`ToolUse` / `tool.call` 事件模型只记录 `tool_use_id`、`input`、`isRunning` 等字段，没有任何检测或拦截逻辑。

### Codex：记录、上限、一致性校验，都不是查重

Codex 有三处与「重复」沾边的机制，但逐一对照会发现都不是「发现重复就拒绝执行」：

1. **`ExecutedToolCallRecorder` 按 `call_id` 记录** 已执行的调用，用来往 prompt 里附加「已执行工具调用」元数据，提示模型别再重来。但存储 key 是 `call.call_id`，**两次参数完全相同、`call_id` 不同的调用会被当成两条独立记录**。

2. **容量上限只是兜底**。`MAX_PENDING_EXECUTED_TOOL_CALLS` 与若干字节上限限制的是 **记录本身** 的大小；达到上限后新记录被替换为截断标记 `ExecutedToolCall::truncated`。它防止元数据无限增长，**不阻止工具被执行**。

3. **`has_same_tool_calls` 是事后一致性校验**。它确实按内容比较（调用顺序、`name`、`arguments()`，忽略 `call_id`），但用在 prompt 裁剪/重放阶段：判断某个 code-mode cell 之前记录的调用集合与当前 metadata 是否一致，不一致就把该 cell 标成 `Incomplete` 触发 **重新展示**，而不是拒绝调用。

| 机制 | 是否按内容去重 | 作用点 | 目的 |
| --- | --- | --- | --- |
| `record_tool_call` | 否，按 `call_id` | 记录时 | 构造「已执行调用」元数据供模型参考 |
| `MAX_PENDING_EXECUTED_TOOL_CALLS` | 否，纯计数 | 记录时 | 防止记录无限增长 |
| `has_same_tool_calls` | 是，按 name+arguments | 裁剪/重放时 | 检测历史内容是否变化，标记 cell 未完成 |

另有两处更边缘的幂等保护：rollout-trace reducer 检测 **同一个 `call_id` 被复用但内容不同** 时报错（防止污染对话历史）；TUI 处理 `DynamicToolCall` 时若 `request_id` 已在处理中就直接返回（防止重复派发）。它们保护的是「同一标识的重复处理」，同样不是「相同内容的新调用」。

## 结论：只有兜底，没有查重

**两家都没有在工具真正执行前计算「工具名 + 参数」指纹并据此短路或拒绝调用。** Codex 的 `has_same_tool_calls` 是离指纹最近的东西，但它服务于历史一致性，不是执行前拦截；Claude Code 的去重只覆盖 `tool_use_id` 层面的插件配置问题。真正兜住无限循环的，只有 **工具调用次数/字节上限** 这类容量约束——它保证进程不会无限膨胀，但不保证任务在推进。

## 理论方案：给工具调用做指纹

如果要在应用层补上这道防线，核心是 **把「相同调用」的定义从标识换成内容**，并把它变成可计数、可反馈的信号：

1. **算指纹**。对工具名 + 规范化后的参数做哈希。参数要规范化（键排序、去空白、剥离时间戳/随机数这类每次都变的字段），否则模型微调一个无关字段就能绕过查重。返回结果是否入指纹要谨慎：结果本身会随环境变化，把结果纳入更适合识别「调用 + 结果都相同」的死循环，而不是识别「重复请求」。

2. **滑动窗口计数**。记录最近 N 次调用的指纹，或维护「同一指纹连续出现次数」。用 **连续次数** 比用窗口总数更贴近「卡住」的语义，避免把合法的周期性轮询误判。

3. **分级处置**。次数到达阈值后先 **给模型反馈**（在工具结果里提示「该调用已重复 K 次且结果相同」），给它一次换策略的机会；仍重复再 **强制退出** 当前 turn 并向上报告。有副作用的写操作应比只读操作更早触发。

4. **区分合法重复**。轮询等待、`git status` 式的心跳、带随机种子的重试都可能是正常行为。指纹方案要允许按工具配置豁免，或只在 **返回结果也相同** 时才判定无进展。

**面试里这样收口最稳**：承认生产级产品目前只做到容量兜底，指纹查重是理论上可行、工程上需要谨慎权衡的补丁；关键难点不在算哈希，而在区分「无意义的重复」和「合法的重复」，以及失败时是提示模型还是直接终止。

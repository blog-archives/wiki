> 本文以 [Codex 的 GPT-5.2 提示词](https://github.com/openai/codex/blob/a97cf1b72eaad05aa49847bc81d09ceac9327754/codex-rs/core/gpt_5_2_prompt.md)为案例，归纳其模块设计、行为约束与适用边界。

**一份面向执行的系统提示词，需要把“做好任务”展开为模型在具体情境下能够遵循的规则。** 收到请求后是否动手、改文件前读哪些约定、复杂任务如何维护计划、验证到哪里可以停、最后怎样交付，都需要有明确的判断依据。Codex 这份提示词的价值，在于把这些决策写进了一套连续的工作流程。

**来源状态**：本次未能在线读取指定提交，正文依据仓库历史中此前收录的[完整提示词文本](https://github.com/blog-archives/wiki/blob/7c89902/raw/ai-agent/2026-09-20-codex-system-prompt.md)重写，尚未与指定提交逐字核对。以下“原文”均指该历史文本；结论只用于解释这一提示词样本，不代表当前所有 Codex 模型或运行模式。文中的设计意义是归纳，不能据此断言运行时已有对应的强制校验。

## 整体组织：先确定角色，再定义工作流程，最后约束工具调用

**原文可以按身份与能力、工作方式、工具规范三个层次阅读，但真正可借鉴的是每层负责解决什么问题。** 开头声明运行环境和可用能力；`How you work` 规定任务推进与交付；`Tool Guidelines` 把抽象要求落实到具体工具的使用方式。工作方式又包含多个决策模块，不能只概括为“自主、规划、执行”。

| 模块 | 模型需要作出的判断 | 提示词具体写到哪里 |
| --- | --- | --- |
| 身份与能力 | 我在什么环境里，能通过什么方式行动？ | CLI 场景、上下文来源、终端与补丁能力、审批可能性 |
| 指令适用范围 | 当前文件受哪些项目约定约束？ | 目录作用域、嵌套覆盖、直接指令优先、查找时机 |
| 自主性与完成条件 | 该直接执行，还是只讨论？何时结束？ | 默认实施、意图例外、遇阻自解、贯穿实施与验证 |
| 计划 | 是否需要拆分，如何反映真实进度？ | 触发条件、正反例、状态转换、范围变化与收尾 |
| 执行边界 | 应该改什么，改到多大？ | 根因修复、既有风格、最小范围、禁止顺手扩张 |
| 验证 | 验什么、何时验、投入多少？ | 先局部后扩大、项目基础设施、审批模式、停止条件 |
| 沟通与交付 | 用户需要知道什么，怎样呈现？ | 假设与前提、结果与限制、篇幅分级、可定位的文件引用 |
| 工具规范 | 如何把行动意图变成有效调用？ | 搜索工具选择、读取并行、补丁语法、计划参数 |

**这些模块共同形成执行链，但不是每个任务都要走一遍相同仪式。** 简单问题可以直接回答，单步修改可以跳过计划；复杂任务才需要持续更新阶段。提示词既定义正常路径，也定义何时省略流程。

## 身份与能力：把角色放进具体运行环境

**开头首先限定模型扮演的是一个能够操作工作区的终端编码助手。** 原文说明 GPT-5.2 运行在 Codex CLI 中，接收用户请求以及宿主提供的文件等上下文，通过流式响应与计划和用户沟通，并发出函数调用来执行终端命令、应用补丁。这里的能力描述明确了“观察—沟通—行动”的渠道。

**能力声明同时交代依赖条件。** 终端调用不意味着任何操作都能直接执行；是否需要申请审批取决于本次运行配置。模型知道自己具备发起操作的接口，但不能从“能调用工具”推导出“已获得全部权限”。开头还消除了 Codex 名称的歧义，避免把当前编码界面误认成早期同名语言模型。

**这一模块的细度止于环境和能力边界，操作协议留给后文。** 对其他 Agent 而言，可借鉴的是明确输入从哪里来、可以影响什么、通过哪些接口行动，以及能力受什么配置约束；泛泛写“你是一位资深专家”无法提供这些执行信息。

## 指令优先级：把项目约定绑定到要修改的文件

**`AGENTS.md spec` 解决的是项目约定的适用范围和冲突处理。** 原文先解释这些文件可能包含编码风格、目录说明、运行和测试方式，再把约束落到最终补丁涉及的每个文件上。

| 判断环节 | 原文规则 | 对行动的影响 |
| --- | --- | --- |
| 确定作用域 | `AGENTS.md` 作用于其所在目录的整棵子树 | 不能把某个子项目的规则无条件推广到整个仓库 |
| 汇总适用约定 | 修改文件时遵守所有覆盖它的 `AGENTS.md` | 不能只读取离文件最近的一份而忽略上层未冲突的要求 |
| 处理嵌套冲突 | 更深层目录中的规则优先 | 子模块可以覆盖上层的一般约定 |
| 处理对话与文件冲突 | 直接的 system / developer / user 指令优先于 `AGENTS.md` | 仓库文件不能反过来覆盖直接下达的要求 |
| 补齐上下文 | 已注入的根目录及 CWD 祖先约定不必重读；进入子目录或外部目录需检查 | 既减少重复读取，又避免漏掉新的局部规则 |

**例如，根目录要求统一风格，子目录另定命名方式，修改该子目录文件时应保留根目录的非冲突要求，并采用子目录的命名规则。** 这个例子是对作用域规则的说明；重点是逐个文件判断，而不是给整个任务挑出一份“最高优先级文件”。

**这里并没有完整重述系统、开发者和用户指令之间的全部层级。** 原文明确的是它们相对于 `AGENTS.md` 的优先关系。设计自己的提示词时，应区分*已有的消息层级*与*需要额外解释的项目规则作用域*，避免把两者混成一条含糊的排序。

## 自主性与执行边界：默认推进，同时控制改动范围

### 把用户的实施意图转成实际行动

**`Autonomy and Persistence` 把默认行为设为完成任务，而不是提交一份建议就停下。** 如果用户请求解决问题，且没有表达只想讨论，模型应实际调用工具或修改代码，并尽可能在当前轮次完成实施、验证和结果说明。遇到困难或工具失败，应先尝试自行解决，而不是立即把工作交回用户。

**默认执行有清楚的意图例外。** 用户明确要计划、询问代码、讨论备选方案，或表达其他不应写代码的意图时，不应机械地动手。用户暂停或改变方向，也会改变原来的推进要求。自主性依赖对任务意图的判断，不是一条无条件写入规则。

### 用工程准则限制“主动”的范围

**`Task execution` 进一步约束怎样算合适的实现。** 能修根因时不做表层补丁，避免不必要的复杂度，保持既有代码风格，必要时更新文档；同时不修无关缺陷或失败测试，不擅自提交 Git commit 或创建分支。原文还明确限制未经要求的版权头、代码内联注释和单字母变量名。

**这些要求把“解决得彻底”与“改得过多”分开。** 为当前问题补齐必要修改属于任务闭环，顺手整理不相关模块则可能扩大审查成本。发现无关问题可以在交付时说明，但不自动把它纳入本次范围。

### 根据项目阶段调整主动程度

**`Ambition vs. precision` 为主动性增加了情境判断。** 全新项目可以有创造性，既有代码库则强调精确地完成用户要求，避免不必要的文件或变量改名。需求宽泛时允许有价值的补充，范围明确时应集中修改。

**这一模块给出了判断原则，但没有量化“何时已穷尽尝试”。** 它也没有为所有失败定义重试次数或恢复路径。设计上应把它理解为模型的行为指引，不能仅凭这些措辞就声称系统保证任务一定完成。

## 计划：同时规定何时使用、怎样拆分和怎样维护状态

### 先判断计划能否减少不确定性

**原文把计划用于具有阶段、依赖、歧义或多个请求的任务。** 长时间的非平凡工作、需要反馈检查点的过程、用户明确要求 TODO，以及执行中新增且准备继续处理的步骤，都属于使用计划的情形。简单或单步问题则不需要额外计划。

**计划必须包含有意义、顺序合理、可以逐步验证的工作。** 不能为了显得完整而加入空泛步骤，也不能承诺实际无法执行的验证。这同时约束了计划的价值和真实性。

### 用正反例说明什么粒度才够用

**原文用 CLI 转换、主题切换、实时聊天等正反例展示拆分粒度。** 以 Markdown 转 HTML 为例，低质量计划只覆盖“创建工具、解析 Markdown、转成 HTML”；高质量计划进一步指出文件参数入口、CommonMark 解析、语义化 HTML 模板、代码块与图片链接处理，以及非法文件的错误处理。

**差别在于计划是否揭示了实现中真正需要解决的问题。** 这些步骤让模型有机会提前发现输入处理、内容覆盖和异常路径，而泛化的“实现功能—检查结果”无法说明工作是否遗漏。步骤更长本身不构成高质量；每一步需要有可辨认的产出或行为。工具段另要求每项使用简短的一句话，原文给出的长度建议是不超过 5–7 个词。

### 让状态反映正在发生的工作

**`update_plan` 不只是开工前的清单，而是需要随执行更新的进度记录。** 原文要求进行中的计划同时只有一个 `in_progress`，完成一项后及时更新，再推进下一项；若认识改变，需要拆分、合并或调整顺序，应先更新计划并说明理由。

| 时刻 | 状态要求 | 要避免的问题 |
| --- | --- | --- |
| 尚未开始 | `pending` | 提前把未执行的工作记为完成 |
| 开始处理 | `pending → in_progress` | 跳过实际执行状态 |
| 完成当前项 | `in_progress → completed` | 清单长期落后于实际进度 |
| 范围发生变化 | 更新步骤及解释，再继续 | 按已经失效的计划推进 |
| 结束本轮 | 全部完成，或明确说明取消、延后项 | 留下没有交代的未完成工作 |

**“明确取消或延后”是收尾要求，不代表工具一定有相应状态枚举。** 这份文本在工具说明中列出的状态只有 `pending`、`in_progress`、`completed`。同样，状态转移约束写在提示词里，是否由程序强制执行，需要另外查看工具实现。

> **Status: Disputed（原文内部表述不一致）**：Planning 部分要求先进入 `in_progress`，并禁止事后批量完成多项；但同一节前段允许一次实施后把全部步骤标为完成，末尾工具说明也允许单次调用完成多项。因此，不能把整份文本描述成完全一致的严格状态机。较稳妥的设计是明确区分“批量提交已发生的真实状态变化”和“事后补造执行记录”，统一正文与工具说明。

**计划展示也被纳入协作规则。** 宿主已经渲染完整计划，模型调用工具后只需说明变化和下一步，不必再次复述。这避免用户同时看到两份冗余、甚至不同步的计划。

## 验证：把覆盖范围、执行时机和成本分开规定

### 先验证改动，再逐步扩大覆盖

**验证的起点是与改动最相关的检查。** 原文建议先用尽可能聚焦的测试捕捉问题，再随着信心建立扩大到更广范围。可以将这一策略理解为先验证直接行为，再检查周边影响；原文没有把它固定成必须依次执行的单元、集成、端到端测试三级流程。

**新增测试取决于仓库是否已有合适基础。** 改动没有测试，但相邻代码已经展示了合理的测试位置和模式，可以补测；整个仓库没有测试时，不为当前任务建立测试体系。项目没有配置 formatter 时，也不额外引入一个。验证应沿用项目已有方式，并与本次改动相称。

### 根据交互模式决定何时主动运行

**原文把运行验证的时机与审批模式联系起来，并明确这是缺少其他行为指导时的默认策略。** 因为测试和 lint 可能耗时，它会影响用户正在进行的交互迭代。

| 情境 | 该样本给出的默认行为 |
| --- | --- |
| 非交互审批模式 `never` | 可以主动运行测试、lint 等检查，尽力完成验证 |
| 交互审批模式 `untrusted` / `on-request` | 等到用户准备收尾时，提出验证动作并让用户确认 |
| 添加或修复测试、复现缺陷等测试相关任务 | 无论审批模式如何，都可以判断是否主动运行测试 |

**这里约束的是主动运行的时机，不是给模型额外授权。** `never` 也不表示绕过沙箱；任务是否能执行某个命令，仍受运行环境限制。原文对测试任务给出的例外，也说明不能把它缩写为“交互模式一律不跑测试”。

### 为验证设定范围和停止条件

**格式修正允许迭代最多 3 次；仍未解决时，应交付正确的方案并明确说明格式问题。** 这个上限只针对格式问题，不能扩大成所有测试失败最多重试 3 次。测试、运行、构建、格式化过程中发现的无关问题，同样不属于自动修复范围。

**无法运行测试时仍要尽力完成任务，但不能把未验证写成验证通过。** 结合交付章节对未完成验证的说明要求，这套设计要求模型区分已经获得的证据与仍需用户检查的部分。它关注的既是正确性，也是为得到这些证据付出的时间和额外改动。

## 沟通与交付：按用户需要的信息组织输出

**`Personality` 先定义日常沟通的方向：简洁、直接、友好，说明行动、假设、环境前提和下一步。** 这些约束帮助用户理解当前工作，但该文本的 `Responsiveness` 是空标题，没有进一步规定更新频率或触发条件。因此不能据此归纳出“每隔固定时间报告一次进度”。

**`Presenting your work` 把交付定位为同事说明结果。** 用户与 Agent 共用工作区，文件已经修改好时，应该给出可定位的路径，而不是再要求用户复制、保存代码。如果有做不到但用户可以完成的验证，则简要说明操作方式。

**输出篇幅依据改动规模分级，格式细到终端界面能否正常呈现。** 小改动要求 2–5 句或不超过 3 个要点且不加标题；中等改动限制为不超过 6 个要点或 6–10 句；大改动按文件概括，避免贴出完整方法和长篇前后对照。标题不是必选项，代码片段只有确实有帮助时才出现。

**文件引用、等宽文本和禁止格式也属于交付协议。** 原文约束路径及行号写法、命令和标识符的展示方式，禁止 CLI 无法渲染的引用标记与直接输出 ANSI 转义码。这些规则与具体宿主界面相关，迁移到网页或其他客户端时应重新适配，不能把旧 CLI 的格式要求当成通用写作标准。

**这一模块把“简洁”落实成可观察的输出形态。** 同时保留了复杂解释需要更多细节的例外，避免为了短而省略结论所需的证据或限制。

## 工具规范：从“可以调用”细化到“应该怎样调用”

### Shell：规定常见工作的默认路径

**搜索默认使用 `rg` 或 `rg --files`，不可用时再换其他工具。** 这给出了明确的首选与降级路径。原文还要求尽可能并行调用工具，尤其是读取文件，并指定使用 `multi_tool_use.parallel`；另外禁止用 Python 脚本输出大段文件内容。

**这些规则是在优化频繁出现的工具行为。** 搜索、读取占据大量上下文收集过程，写明默认方法可以减少反复选择。迁移时需要替换为当前运行环境真实提供的工具，不能照抄一个并不存在的并行接口。

### 补丁：提供足以构造调用的协议

**`apply_patch` 的说明既规定使用场景，也规定输入语言。** 原文要求用该工具编辑文件，明确精确工具名与 FREEFORM 输入，并说明不能把补丁包装成 JSON；随后定义补丁起止标记、添加／删除／更新文件的操作头，以及新增行必须带 `+` 的要求。

**示例覆盖多个文件操作，并展示更新时的重命名。** 这比“请谨慎修改文件”更具体：模型得到的是可以直接构造的输入格式，也能知道新建文件并不意味着可以省略新增行标记。这里的格式约束由提示词解释，实际能否解析则取决于工具。

### 计划工具：把行为要求接到结构化参数

**`update_plan` 的工具说明规定步骤文本和状态字段，并要求完工后显式更新。** 它与前面的 Planning 分工明确：正文解释何时计划、什么计划有质量，工具段解释怎样提交计划和进度。不过两处重复规定状态更新，也产生了前文指出的表述冲突。

**工具规范需要与工作方式保持一致。** 如果正文要求一种更新节奏，工具段却给出另一种，模型必须临场解释冲突。对提示词的检查除了语法，还应覆盖重复规则的一致性、工具名是否真实可用、例外条件是否齐全。

## 从这个案例提炼的设计方法

**值得迁移的是把高层目标逐步展开为判断条件、行动规则和结束标准。** 例如“自主完成”展开为默认实施、讨论场景例外、遇阻尝试解决、实施后验证并交付；“维护计划”展开为适用情境、拆分示例、状态更新和范围变更；“验证充分”展开为局部起步、逐步扩大、基础设施边界和成本控制。

**不同模块需要不同形式的具体性。** 身份模块说清环境即可，优先级需要作用域与覆盖关系，计划需要状态和正反例，工具需要调用语法，输出需要能被界面正确呈现的格式。提示词的细度取决于模型在此处容易作错什么决定，而不是每章都写同样多的规则。

**提示词规定期望行为，运行时负责它能够实际强制的边界。** 这份样本展示了如何指导模型，但单靠文本不能证明状态合法性、权限隔离或测试结果真实性已经由程序保障。需要强保证的约束，应进一步落实为工具校验、权限控制或可核实的执行结果。
